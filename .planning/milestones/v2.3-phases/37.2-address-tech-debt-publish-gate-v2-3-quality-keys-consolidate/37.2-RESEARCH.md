## Summary

**W1.** The gate's `QUALITY_SUB_KEYS` (line 23) holds six keys. The emitter (`ActivityQualitySignals`, `src/analytics/pace-quality.ts:607`) writes 11 keys on every row's `quality` and on every shard's `signals`. The five unchecked: `unreliableSegments`, `pauseClassification`, `forgottenStop`, plus the derived `anySevere` and `notComputableReason`. The audit's fourth name, `pauseIntervals`, is NOT a `quality` sub-key. It is a top-level key of the pace-quality shard (`PaceQualityShard`), next to a top-level `unreliableSegments` ARRAY (different shape from `signals.unreliableSegments`, the signal object) and two `...Truncated` booleans. The 0-grep-hit claim holds: none of the four names appears in the gate file. All keys are unconditional. I counted 1955/1955 index rows and 1955/1955 shards in the built `dist/widgets` carrying every key, including not-computable activities (the not-computable constructors emit all keys). So the gate may require every key on every row, with no conditional logic.

**W3.** `consolidateExports` classifies every export run before any import (id match, then exact-epoch `archiveByEpoch`, else `missing`). It never calls `findNearMatch`. The `archiveByEpoch.set` at line 264 runs only after the classification loop finished, so it does NOT dedupe within an export. Only one source (`strava`) is ever processed, so that line is effectively dead. `findNearMatch` returns `undefined` for an exact (offset 0) match by design, so the exact-epoch lookup must stay as the caller's own path, exactly as `fit-import.ts:256-266` does. ROADMAP SC3's wording "instead of the exact-epoch lookup" cannot be literal. Follow the fit-import shape: exact first, then `findNearMatch`. The current archive has zero export rows within the window of an existing record (measured, below), so SC5 is expected to hold trivially.

**Primary recommendation:** Put the key lists in a new plain-ESM `scripts/lib/quality-keys.mjs` imported by the gate. A vitest file under `scripts/` imports that list and the real emitter (`../src/analytics/pace-quality.js`, precedent: `scripts/compute-*-recount.test.mjs` import `../src`), compares them as SETS (key order differs between computable and not-computable output), and the gate gets planted-removal subprocess tests run against SHADOW trees (never the real `dist/widgets`). Wire consolidate as: id, then exact epoch, then `findNearMatch`. Extend the 37.1 guard `required`/`needsCall` with `consolidate.ts`.

### Pattern 1: emitter keys read at runtime, compared as sets
The gate cannot import TS and has no exports (it runs `main()` on import), so the shared list must live in a separate `.mjs`. Type erasure means keys must come from emitter OUTPUT, not from the interface.

```js
// Verified in this session against dist/: key ORDER differs between computable and not-computable output
// (join()ed key strings were unequal), so compare sorted sets.
import { computePaceQualitySignals, buildPaceQualityShard } from '../src/analytics/pace-quality.js';
const md = { deviceName: 'x', sourceProvider: 'intervals', elapsedTimeSec: 300, movingTimeSec: 300, startLatlng: [], endLatlng: [] };
const t = Array.from({ length: 300 }, (_, i) => i), d = t.map(i => i * 3);   // passes validateStreamSeries
const signalKeys = [computePaceQualitySignals({ t, d }, md), computePaceQualitySignals(null, md)].map(o => Object.keys(o).sort());
const shardKeys  = [buildPaceQualityShard('1', { t, d }, md), buildPaceQualityShard('1', null, md),
                    buildPaceQualityShard('1', { t: [1], d: [1] }, md)].map(o => Object.keys(o).sort());
// expect each signalKeys[i] toEqual [...QUALITY_SUB_KEYS].sort(); each shardKeys[i] toEqual [...PACE_QUALITY_SHARD_KEYS].sort()
// Also assert computable !== not-computable branch (notComputableReason null vs non-null) so both branches are really exercised.
```
`CanonicalStream` may need more fields than `{t,d}` for typing; the call worked untyped at runtime. Planner: confirm it type-checks under the `.mjs` import or keep the fixture minimal.

### Pattern 2: planted-removal against a SHADOW tree (from `verify-dashboard-publish-stats.test.mjs`)
mkdtemp root; symlink every real `dist/widgets` entry; shadow only the touched directory levels (`data/` -> `dashboard/` for the index row case; `data/` -> `stats/` -> `pace-quality/` for the shard case, writing a REAL file for the mutated shard and symlinking the others); run the verifier with `cwd` = the tmp root; `rmSync` the tmp root in `finally`. The gate resolves `ROOT = <cwd>/dist/widgets`. Use `describe.skipIf(!existsSync(dist/widgets/index.html))` like the siblings; CI runs `build-widgets` before `test:logic`, so the cases do not skip there (daily-refresh.yml lines 243-261). Avoid the Case G precedent of rewriting the real `index.json` in place; it restores in a `finally` but it is the pattern the stats test header explicitly rejects.

Shard sample ids: the gate derives them from the parsed index (`Math.min(1,n-1)`, `Math.floor(n/3)`, `Math.max(0,n-2)`, deduped). The test must derive them the same way (D-10 precedent, no pinned id). Mutate the first sampled shard.

### Anti-patterns
- Comparing key lists by array order or by `join()`.
- Hand-typing the expected key list in the test and calling that the independent value. It must come from the emitter (and, as a third anchor under `skipIf`, from the real built row/shard key set).
- An exempt/allow list in the drift test (it is a second list that can drift). If a key must be exempt, put it in the shared module with a comment, not in the test.
- Running `consolidateExports()` with default paths (rewrites tracked `data/provenance.json`, which is already stale, and could write `data/activities`).

## Common Pitfalls

1. **Key order differs.** Computable vs not-computable `signals` have different key order. Compare sorted sets.
2. **Two `unreliableSegments`.** `signals.unreliableSegments` (object) vs shard top-level `unreliableSegments` (array). Keep separate lists and separate messages; a planted removal of one must not be masked by the other being present.
3. **`pauseIntervals` is not a quality sub-key.** Putting it in `QUALITY_SUB_KEYS` would fail every row. It belongs to the shard list only.
4. **Gate imports the TS emitter?** It cannot (no TS loader, runs `main()` at import, Node built-ins only). Don't refactor `main()`; use the shared `.mjs`.
5. **Shard sampling.** The gate checks only 3 shards. A planted removal in a non-sampled shard is invisible. Derive the sampled ids in the test the same way and mutate one of them.
6. **Message-text coupling** (Case G line 261). See W1.
7. **`-t` filter vacuity.** A filter matching 0 tests exits 0. Record matched counts (table below). Counts were measured with vitest's "N passed | M skipped".
8. **Tests skip silently without a build.** The gate tests are `skipIf(!existsSync(dist/widgets/index.html))`. In a worktree executor they skip vacuously (memory: worktree executors need a primary checkout for checkpoint plans). The drift test itself must NOT depend on `dist` so it always runs.
9. **Exact vs near.** `findNearMatch` ignores offset 0. Dropping the exact lookup would import every exact duplicate (53 rows today). Keep id -> exact -> near order.
10. **Provenance for near rows.** `ProvenanceEntry.matched_by` is a closed union in `consolidate.ts` and duplicated in `src/streams/backfill-streams.ts:33`. Adding a literal means editing both; avoid unless needed (Open Questions).
11. **Real `data/provenance.json` is tracked and stale.** Never run default-path consolidation as verification.

## Open Questions

1. **Near-matched row: provenance link or not?** What we know: exact start_date rows are linked as `matched_by: 'start_date'` with the export's `strava_id`/`original`/`gear`. A near row cannot honestly use that label, and a 30-120 s offset is weaker evidence of "same activity" than the dedupe decision itself. Recommendation: skip, log ids/date/signed delta, add `matched_by_near` (or `near_skipped`) to `sourceSummaries.strava` only when > 0, and write no provenance entry. Confirm in plan review (A1).
2. **Full 16 shard keys vs v2.3 four?** Recommendation: all 16 (A4).
3. **Should the Case G assertion text be preserved?** Recommendation: change the gate message to name the key and update Case G in the same commit (declared in `files_modified`).

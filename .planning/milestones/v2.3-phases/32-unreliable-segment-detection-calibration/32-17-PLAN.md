<objective>
Close CR-01 from the round-2 code review (`32-REVIEW.md`), the one Critical the gap-closure round
introduced into itself, plus the residual WR-01 warning.

CR-01: plan 32-13 closed gap #3 by widening `mapGapToIndices` to `gi` = FIRST index at
`span.startSec`, `gj` = LAST index at `span.endSec`. That is correct for a single gap span. For two
ADJACENT spans (`gapA.endSec === gapB.startSec`) whose shared boundary is a duplicated timestamp in
`t`, the FIRST-at-start search for the second gap and the LAST-at-end search for the first gap
resolve to DIFFERENT indices. The two mapped ranges overlap, the chain-building loop does not merge
overlapping-but-unequal ranges, and the shared interval's real distance is counted in BOTH segments.

Reproduced against the compiled `dist/analytics/unreliable-segments.js` by the reviewer and
independently re-reproduced by the orchestrator:

    t    = [0, 1, 5, 5, 10, 11]
    d    = [0, 20, 25, 45, 50, 140]
    gaps = [{ startSec: 1, endSec: 5 }, { startSec: 5, endSec: 10 }]
    params = { speedLimitMps: 7.35, excessFloorMetres: 3, hiddenPauseMinMetres: 1e9 }

    -> seg0 startIndex 0 endIndex 3 metres 45
    -> seg1 startIndex 2 endIndex 5 metres 115     (overlaps seg0 at indices [2,3])
       sum 160 m  vs  stream actual d[5]-d[0] = 140 m   -> 20 m double-counted

This falsifies the module's own "maximal contiguous chain" invariant (`unreliable-segments.ts:175`)
and the phase goal's requirement that segments conserve real distance and time.

WR-01: `buildActivityFinding` in `scripts/validate-unreliable-segments-1hz.mjs` still dereferences
`activityDoc.start_date` unguarded, three lines below the field 32-15 fixed for CR-03, so its
never-throws docblock is still not fully true.
</objective>

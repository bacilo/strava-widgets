<objective>
Give the detector one gap-boundary definition. `mapGapToIndices` picks the LAST index at
`span.startSec` and the FIRST index at `span.endSec`; `isGapPair` uses an inclusive test that
treats the duplicate-timestamp pair itself as inside the gap. The two disagree whenever a duplicate
timestamp sits exactly on a gap boundary, and the gap's own metres and seconds are then dropped
from the segment while its mechanism label flips from gap-adjacent to isolated-jump.

Purpose: this is GAP 3, and it is a direct violation of the phase goal's "segments that conserve
real distance/time" and of D-06/D-07's touching-only adjacency rule. It is latent on today's
archive — 72 of 1,874 committed streams already carry duplicate timestamps, which
`validateStreamSeries` explicitly documents as VALID input, and none currently lands exactly on a
gap boundary — but this module becomes the single source Phases 33, 35 and 36 read, and the archive
grows nightly.

Output: `mapGapToIndices` aligned with `isGapPair`, both verifier fixtures pinned as permanent
regression tests, and the change measured against the committed archive before it is trusted.

Runs in wave 2 because it writes the same two files as 32-11 (GAP 1). Do not merge the two: 32-11's
shape guards must be in the tree first so this plan's fixtures exercise the guarded entry path.
</objective>

<interfaces>
The two disagreeing definitions, from the committed source:
- `isGapPair` (~line 199-206): pair `i` is inside gap `g` iff `g.startSec <= t[i] && t[i+1] <= g.endSec`. Under `{t:[0,1,1,13], gaps:[{startSec:1,endSec:13}]}` this is TRUE for pair 1 (t=1..1) and pair 2 (t=1..13), so `advanceSteps` discards both.
- `mapGapToIndices` (~line 351-379): `gi` = the LAST index with `t[gi] === span.startSec` (index 2 here), `gj` = the FIRST index with `t[gj] === span.endSec` (index 3 here). The gap block becomes [2,3] and does not touch the burst block [0,1], so no chaining occurs.

Target convention (derived during planning, arithmetic checked by hand on both fixtures): `gi` =
the FIRST index with `t[gi] === span.startSec`, `gj` = the LAST index with `t[gj] === span.endSec`.
Under fixture A this gives the gap block [1,3], which touches the burst block [0,1], producing one
chained segment [0,3]: metres d[3]-d[0] = 21, seconds t[3]-t[0] = 13, gapCount 1, burstMetres 20,
gapMetres 1, burstSeconds 1, gapSeconds 12, mechanism `gap-adjacent`. Under fixture B (the same
activity without the duplicate sample) the gap block is [1,2] and the segment is [0,2] with the
same mechanism and the same 21 m / 13 s totals. The two now agree, which is the invariant.

Why this direction and not the other: `isGapPair` is the definition `advanceSteps` already enforces
and the one `classifyGaps` semantics arrive with, and widening the gap block can only ever ADD the
duplicate pair's own zero-duration, zero-distance contribution to the gap side — it cannot move
metres between the burst and gap tallies. Narrowing `isGapPair` instead would reclassify a pair
`advanceSteps` currently discards as a covered step, changing folded-step output archive-wide.

Mechanism labels are unchanged by this plan: `gap-adjacent` when `gapCount > 0`, else `hidden-pause`
at or above `params.hiddenPauseMinMetres` (D-08), else `isolated-jump` (D-03).
</interfaces>

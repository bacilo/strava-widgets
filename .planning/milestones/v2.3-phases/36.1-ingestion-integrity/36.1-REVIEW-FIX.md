### CR-01: `import-fit` writes the Garmin account email into committed, public records

**Files modified:** `src/exports/fit-import.ts`, `src/exports/fit-import.test.ts`, `src/exports/consolidate.ts`, `src/exports/consolidate.test.ts`
**Commit:** a1f6870d
**Applied fix:**
- `importFit` refuses an `@` in the `fitPath` as given, or in the resolved path relative to the source root. This covers a neutral symlink that points at an email-named file. The check runs right after path containment, before the file is read and before anything is written.
- `external_id` is now derived from the id: `<garminId>.fit`, or `<garminId>.fit.gz`. It no longer comes from the filename.
- A defensive check refuses `@` in the derived `original` or `external_id`.
- `safeOriginalFile` in `consolidate.ts` now returns no link when `original_file` contains `@`.
- Tests:
  - A planted `user@example.com_123.fit` is refused. An independent recursive listing of the temp dir shows only the planted file and the pre-seeded provenance, and the provenance bytes are unchanged.
  - Also refused: an `@` in a directory segment, and a neutral symlink pointing at an email-named file.
  - consolidate drops an `original_file` that contains `@`, and the written document contains no `@`.
  - All the new tests fail when run against the pre-fix code.

**Design decision:** `original` and `original_file` keep their canonical `<source>:<relative path>` form. `backfill-streams.ts` (`resolveOriginalPath`) resolves that value to the file under `export_data/`, so an id-derived name would break the locator. The refusal is what guarantees no email reaches it.

**Committed record decision:**

- I re-imported the real FIT into a temp dir with the new code. The provenance entry and the stream are byte-identical to the committed ones. The only difference is `external_id`: the new code gives `25116720114.fit`, and the record holds `25116720114_ACTIVITY.fit`.
- The committed value contains no email, and no consumer re-derives `external_id`, so I left the record unchanged. **For you to decide:** whether to rewrite it so it matches a fresh import.

**Re-derivation check:**
- The plan-06 re-derivation (`consolidateExports`, run on a temp copy) still links `25116720114` to `garmin:_extracted/single_25116720114/25116720114_ACTIVITY.fit`.
- The re-derived document as a whole differs from the committed `data/provenance.json`, but the differences come from the committed file being stale, not from this fix:
  - `archive_total` is 1955, against 1866 committed.

### WR-07: `importFit` can fail after writing; this breaks the "refused before the first write" contract

**Files modified:** `src/exports/fit-import.ts`, `src/exports/fit-import.test.ts`
**Commit:** 4f54f3aa
**Applied fix:**
- Before any write, `importFit` now:
  - reads and validates the provenance document: it must be valid JSON, an object and not an array, and `activities` must be an object
  - loads the manifest and checks its `activities` object
  - stages both updates in memory
- Write order is now stream, manifest, provenance, then the activity record last. The activity record is the dedupe key, so an interrupted run stays importable.
- Tests:
  - Truncated, array, and `{"activities": []}` provenance files are each refused. No activity, stream or manifest is written, and the provenance bytes are unchanged. After the file is repaired, the import succeeds. These 3 tests fail against the old code.
  - A corrupt-manifest refusal is also tested. This is a regression guard: the old code already refused this case.

### WR-10: Garmin ids longer than 16 digits produce a record whose `id` does not match its filename

**Files modified:** `src/exports/fit-import.ts`, `src/exports/fit-import.test.ts`
**Commit:** 84e69490
**Applied fix:**
- The id stays a string for the filename and `garmin_activity_id`.
- `importFit` now refuses, before any read or write, an id where either:
  - `Number(id)` is not a safe integer, or
  - `String(Number(id)) !== id`
  
  That covers ids above `MAX_SAFE_INTEGER` and ids with a leading zero.
- Tests refuse `9007199254740993`, a 20-digit id and `0123`. Each test independently checks that the id does not round-trip, and asserts nothing is written. These tests fail against the old code.
- `Number.MAX_SAFE_INTEGER` is accepted, with `String(rec.id)`, the filename and `garmin_activity_id` all in agreement.
- The committed `25116720114` is unaffected.
- Not fixed here: the Garmin reconcile adapter takes `activityId` through `JSON.parse`, so a summary file with an id above 2^53 would already be rounded before it reaches `String(id)`. That path was not in the cited lines.

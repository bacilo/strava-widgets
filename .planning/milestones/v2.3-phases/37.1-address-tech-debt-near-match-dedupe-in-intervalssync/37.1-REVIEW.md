**Reviewed:** 2026-11-26

## Summary

Scope: `git diff 5233487c..HEAD -- src` (8 files). No tests were run.

**Window boundary.** No defect found. The old importer rule was `delta >= 1 && delta <= NEAR_MATCH_TOLERANCE_S`. `findNearMatch` skips when `abs < 1 || abs > tolerance`. That is the same rule for every real number, not only integers: inclusive at ±120, exclusive at 0, and a non-finite value on either side never matches, as before. Behavioural rows pin both edges with literals: 120/-120 match and 121/-121 do not, in the importer, in IntervalsSync and in reconcile. The signed `deltaS` convention (new minus existing) matches reconcile.

**Exact and near ordering.** In `intervals-sync.ts`, the exact check (`existing.has(epoch)`, line 149) runs before the near check, so a delivery that exactly matches any record on disk is skipped silently. That is the intended behaviour. The test written to pin this ordering cannot fail, though (WR-04).

**Structural guards.** The planted-literal and import/call mutation rows can fail; I checked that each mutation actually changes the scanned text. The guard is much narrower than its doc comment says (WR-03), and reconcile still runs its own copy of the comparison, which no guard can see (WR-02).

There are no Critical findings. The main concerns are:
- the tie-break is nondeterministic and does not match reconcile's
- the "one shared rule" claim is only partly enforced
- a near-skip leaves no durable record anywhere

## Warnings

### WR-01: Tie-break depends on directory order and disagrees with reconcile's "earlier wins"

**File:** `src/exports/near-match.ts:46`, `src/sync/intervals-sync.ts:85-104`, `src/exports/fit-import.ts:258-261`, `src/exports/reconcile.ts:135`
**Issue:** `findNearMatch` keeps the first candidate when two are equally close (`abs < Math.abs(best.deltaS)`). The candidate order comes from `fs.readdir`: `FileStore.listFiles` in IntervalsSync, and Map insertion order, also from `readdirSync`, in the importer. Directory order is not guaranteed and differs between filesystems (APFS on a laptop, ext4 in CI). Two FIT records at E-10 and E+10 can therefore give different `existingId` and `deltaS` values on different machines. `reconcile()` has an explicit rule ("ties go to the earlier one", line 135), so the module described as "the one shared near-match rule" breaks ties differently from reconcile. The test at `near-match.test.ts:99` cannot tell these rules apart. Its tied candidates come in the order `near1` (E-10) then `near2` (E+10), so "first in list" and "earlier epoch" both choose `near1`.
**Fix:** Make the tie-break deterministic and the same as reconcile's, then add a row that puts the later candidate first:
```ts
if (best === undefined || abs < Math.abs(best.deltaS) ||
    (abs === Math.abs(best.deltaS) && c.epoch < best.epoch)) {
  best = { id: c.id, epoch: c.epoch, deltaS };
}
```
```ts
// test: later candidate listed first must still lose the tie
expect(findNearMatch(E, [{ id: 'late', epoch: E + 10 }, { id: 'early', epoch: E - 10 }])?.id).toBe('early');
```

### WR-02: reconcile.ts keeps its own copy of the window comparison

**File:** `src/exports/reconcile.ts:135-152`
**Issue:** Only the constant is shared with reconcile. Its comparison, `Math.abs(best - run.startEpoch) <= tolerance` after an exact-match `continue`, is still written by hand and does not call `findNearMatch`. The structural guard leaves reconcile out of `needsCall` (`near-match.test.ts:156`). The literal-120 scan cannot catch a change from `<=` to `<`, or a dropped exclusion of 0. Only reconcile's own behavioural rows would catch that kind of drift. This contradicts the module's claim that it is "the one shared near-match rule", and it is the drift that this tech-debt phase was meant to remove.
**Fix:** Do one of the following:
- Have reconcile call `findNearMatch(run.startEpoch, candidates, tolerance)`, after fixing WR-01 so that the tie-break is the same. Then add `'reconcile.ts'` to `needsCall`.
- If performance needs the lowerBound path, narrow the docstring to "the shared window constant". Add a differential test that runs reconcile and `findNearMatch` over the same randomized epochs and asserts they agree on near or not-near and on `deltaS`.

### WR-03: Structural guard scans 3 files and misses common spellings, yet claims to cover all of src/

**File:** `src/exports/near-match.ts:13-14`, `src/exports/near-match.test.ts:29,59-63`
**Issue:** The doc comment says: "This is the only definition of the window in src/. A test fails if another source file carries its own copy." The guard only reads `fit-import.ts`, `reconcile.ts` and `intervals-sync.ts`. It would not catch a new private window in any other file, for example `consolidate.ts`, which already builds its own epoch index and keeps its own `'garmin-export'` check (IN-02), or in `index.ts`. Even inside the three scanned files, the regex `(?<![\w.$])120(?![\w.])` does not match `120_000` or `120000` (milliseconds), `2 * 60`, `120n` or `0x78`.
**Fix:** Do one of the following:
- Scan every non-test `.ts` file under `src/` for `NEAR_MATCH_TOLERANCE_S =`, and for `120`/`120_?000` next to epoch or start words, with an allowlist for known unrelated literals.
- Reword the doc comment to name the three files the guard actually covers.

Add planted rows for `120_000` and `2 * 60`. If the guard is meant to catch them, those rows should fail against the current regex.

### WR-04: The exact-before-near ordering test cannot fail

**File:** `src/sync/intervals-sync.test.ts:285-293`
**Issue:** "skips an exact-start duplicate of a FIT-imported record without reporting a near match" seeds a FIT record at E and delivers at E. `findNearMatch` excludes offset 0 by design. If the two checks were swapped so that near ran first, the delivery would still not be near, the exact check would still skip it, `skipped` would still be 1, and no near line would be logged. Every assertion still passes. The ordering only shows when a delivery exactly matches a non-FIT record and is also within 120 s of a FIT record. No test covers that case.
**Fix:** Add a row that does depend on the order:
```ts
it('exact match on a non-FIT record wins over a near FIT record (no near report)', async () => {
  seed('30000000001', at(30));                                    // intervals/Strava record, exact
  seed('25000000001', E, { source_provider: 'garmin-export' });  // FIT record 30 s away
  const { sync } = build([delivery('i2001', at(30))]);
  const res = await sync.syncNewActivities();
  expect(res.skipped).toBe(1);
  expect(res.nearMatches).toEqual([]);   // fails if near check runs first
});
```

### WR-05: A near-skip leaves no durable record; the report exists only in console output

**File:** `src/sync/intervals-sync.ts:156-168`, `src/index.ts:437-441`
**Issue:** A skipped delivery is never written and never advances the watermark. `nearMatches` is only printed to stdout. The class doc says "the 1-day watermark overlap re-reports the same skip on the next night", but that only holds until a later run is written and the watermark moves more than a day past the skipped start. After that the skip is never reported again. If a skipped delivery is actually a separate run (for example a short warm-up recorded within 2 minutes of the FIT start), the only trace is a nightly CI log that rotates away. Nothing in `data/` lets anyone audit or recover it.
**Fix:** Save the skips: append `{intervalsId, existingId, deltaS, startDate}` to a small JSON ledger, for example `data/near-match-skips.json`, keyed by `intervalsId` so the write is idempotent. Alternatively, record it in the sync state. Then correct the docstring's "re-reports" claim.

### IN-01: `skipped` now mixes three causes, and the summary text omits near-matches

**File:** `src/sync/intervals-sync.ts:239`, `src/index.ts:436-437`
**Issue:** `skipped` counts non-runs, exact duplicates and near-matches. The CLI prints "Skipped (duplicates/non-runs): N" and then prints the near count as a separate line, so near-matches are counted twice across the two lines. **Fix:** Change the label to "(duplicates/near-matches/non-runs)", or report the three counts separately.

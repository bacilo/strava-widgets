### Locked (from ROADMAP.md / REQUIREMENTS.md)
- ING-05: IntervalsSync and the FIT importer share one near-match rule. An intervals.icu delivery whose start lies within the importer's window of a FIT-imported record is treated as a duplicate and reported, not written as a second record. Deliveries outside the window are still written.
- SC1: within the window of a FIT-imported record (either side, including +1 s and the far edge) creates no second record in `data/activities/` or `data/streams/`; the skip is reported in the sync output by both ids and the offset.
- SC2: outside the window, or near a record that was not FIT-imported, is still written. Both directions shown in tests.
- SC3: importer and IntervalsSync read the window from one shared definition; a test fails if either side carries its own copy.
- SC4: the 36.1 CAN-FAIL test in `fit-import.test.ts` is updated deliberately; the new assertions are shown failing against the pre-change IntervalsSync first.
- SC5: the archive's existing near matches in `data/reconciliation/garmin.json` are counted and dispositioned from the file's actual contents; no existing archive record is rewritten or deleted.

## Summary

The defect is confirmed by reading the code. `IntervalsSync.existingStartEpochs()` (`src/sync/intervals-sync.ts:57-73`) returns a `Set<number>` of floor-seconds, and the loop skips only on `existing.has(epoch)` (line 114). `importFit` (`src/exports/fit-import.ts:254-265`) returns `duplicate` on an exact epoch and throws `near-match` for any archive record with `1 <= |delta| <= NEAR_MATCH_TOLERANCE_S`. The constant is already a single exported value, `NEAR_MATCH_TOLERANCE_S = 120` in `src/exports/reconcile.ts:24`, imported by `fit-import.ts:17` and used as the default in `reconcile()` (line 92). So the importer and the reconciler already share the definition; IntervalsSync is the only consumer without it. The work is: give IntervalsSync a near-match check against FIT-imported records, report it, and prove the shared definition.

Only one FIT-imported record exists in the real archive: `25116720114` (`source_provider: 'garmin-export'`, start `2026-11-18T06:25:50Z`). The two near matches in `data/reconciliation/garmin.json` (count verified: exactly 2) both involve Strava-origin records, not FIT-imported ones, so the new rule changes nothing for them. No two archive records lie within 120 s of each other (closest pair: 159 s). No archive record needs rewriting.

**Primary recommendation:** Skip (do not replace) any intervals.icu delivery whose start is within 1..120 s (inclusive) of an archive record whose `source_provider === 'garmin-export'`. Make the check a pure helper in a new neutral module that also owns the constant, re-export the constant from `reconcile.ts`, return the skips as a `nearMatches` array on the sync result, log one line per skip, and prove the red/green order by committing the new tests before the implementation.

## Recommended design (prescriptive)

### D1. Identify FIT-imported records by `source_provider === 'garmin-export'` on the record
The importer writes it on the record itself (`fit-import.ts:113`), the sync loop already opens every record, and consolidate.ts already uses this exact test. Do not use provenance.json (stale, shared `imported` label, a separate file) or `external_id` (set for strava-export and Garmin ping ids too). Define the predicate once next to the constant: `export const FIT_IMPORT_PROVIDERS = ['garmin-export'] as const`.
Open choice for the user: the 36.1 review (WR-06 fix text) also listed `strava-export`. Those 4 records take start times from the Strava CSV, which is the same Strava-vs-Garmin drift class. They are all earlier than the intervals.icu era's last weeks and ROADMAP wording says "FIT-imported", so recommend `garmin-export` only; adding `'strava-export'` is a one-token change, but it widens SC1/SC2 wording and needs an amended criterion. `[ASSUMED]`, see A1.

### D2. Skip, do not replace
Replacing would rewrite or delete `data/activities/25116720114.json`, its stream, its manifest entry, its provenance link and every derived artifact keyed by that id (the id appears in `data/provenance.json`, `data/streams/`, `data/stats/best-efforts*`, `data/stats/pace-quality/`, `data/geo/activity-cities.json`, `data/dashboard/index.json`, `data/stats/age-grading.json`; grep confirmed). SC5 forbids rewriting existing records. The FIT stream is also the original device recording, which is at least as high fidelity as the intervals.icu derived stream. Skip is the only option consistent with the criteria, and it also saves the per-activity streams request because the skip precedes `fetchGeometry`.

### D3. Scope: FIT-imported records only, not every archive record
Reasons: (1) SC2 says so, and the user confirmed the criteria. (2) intervals.icu can legitimately hold two runs less than 120 s apart; a near match against its own earlier records is not ambiguous in the way a FIT file versus an unrelated source is. (3) An intra-batch rule would drop the second of two real deliveries. So: compare only against records read from disk with `source_provider` in `FIT_IMPORT_PROVIDERS`, never against epochs added during the current batch. Asymmetry with the importer (which refuses near any record) is deliberate: the importer is an operator tool where refusing is cheap and safe; the nightly sync is unattended and must not silently swallow data.
Honest caveat: the two Strava-origin near pairs (M1) show a duplicate hazard that exists for Strava-origin records too (a full-history re-sync, `last_sync_timestamp` 0, would re-deliver 2025-04 runs at Garmin starts 46 s from the archive's Strava starts). That is out of the stated scope; the planner may add an optional report-only line for near matches to non-FIT records (log, but still write) without breaking SC2. Mark it optional.

### D4. Shared definition
Create `src/exports/near-match.ts` (neutral, no `fs`) exporting `NEAR_MATCH_TOLERANCE_S = 120`, `FIT_IMPORT_PROVIDERS`, and a pure `findNearMatch(epoch, candidates, tolerance = NEAR_MATCH_TOLERANCE_S)` returning the nearest `{ id, epoch, deltaS }` with `1 <= |delta| <= tolerance` (inclusive, signed `epoch - candidate`, matching `reconcile()`'s `deltaS = run.startEpoch - best`) or `undefined`. `reconcile.ts` re-exports the constant (`export { NEAR_MATCH_TOLERANCE_S } from './near-match.js'`) so `reconcile.test.ts:25` and existing imports keep working. `fit-import.ts` and `intervals-sync.ts` import from `near-match.js`. Using the helper in `fit-import.ts` is optional; at minimum both import the constant. Do not keep `export const NEAR_MATCH_TOLERANCE_S = 120` in two files.
Alternative with less churn: leave the constant in `reconcile.ts` and import it into `intervals-sync.ts`. It works, but couples the sync to the reconcile module (which imports `fs`/`path`), so the neutral module is recommended.

### D5. Reporting
- Result: `{ newRuns, totalFetched, skipped, nearMatches }` where `nearMatches: Array<{ intervalsId: string; existingId: string; deltaS: number; startDate: string }>`. `skipped` keeps counting them, so existing consumers and the `skipped` arithmetic stay valid.
- Log (console.log, same convention as the `  + date name (km)` line): `  ~ near-match skip: ${activity.id} (${activity.start_date}) is ${signed}s from FIT-imported ${existingId}; not written`.
- `src/index.ts` summary: add `Near-match skipped (FIT-imported): ${result.nearMatches.length}` after the existing three lines, with the ids listed when non-zero. There is no workflow-level surface beyond logs, so the log line plus summary is the whole reporting surface.
- A skip does not advance `maxTimestamp` or call `syncStateManager.save` (same as an exact skip). The 1-day watermark overlap will re-deliver and re-skip it on later nights; the log line will repeat for up to about a day. That is acceptable and should be stated in the docs comment, not suppressed.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Window value | A second `120` or `2 * 60` in sync | `NEAR_MATCH_TOLERANCE_S` from the shared module | SC3 |
| Nearest-candidate search | A new scan in each consumer | One pure `findNearMatch` (linear scan is fine: at most a handful of FIT-imported records) | Two diverging implementations is the bug being fixed |
| FIT-imported test | provenance.json lookup | `source_provider` on the record | M2 |

## Common Pitfalls

### P1: Window edges and sign
`reconcile()` and the importer use inclusive `<= 120` and exclude 0 (exact is handled earlier). A sync that uses `<` would let +120 through. Test +1, -1, +120, -120 as skipped and +121, -121 as written.

### P2: Near check against batch-added epochs
`existing.add(epoch)` adds intervals-sourced epochs during the loop. If the near check uses that set, two real runs 60 s apart in one delivery lose the second. Use only the FIT-imported index loaded from disk.

### P3: Skip placed after the geometry fetch
If the check sits after `fetchGeometry` the skip still costs an API call and may write `streams/<id>.json` and a manifest entry for a skipped activity (`upsertAvailable` runs before `writeJson` of the activity). Place it immediately after the exact check. The no-write test must also assert the manifest bytes and that `getAllStreams` was called 0 times.

### P4: `existingStartEpochs` swallows read errors
A corrupt FIT-imported record is silently absent from the index, so its near duplicate would be written. Either leave as is (consistent with the exact path) and note it, or log a warning for unreadable files. Do not make it throw: that would abort the nightly sync.

### P5: Test construction that proves nothing
- `vi.spyOn(fs, 'readFileSync')` does not see named imports (`import { readFileSync }`); build no-write guards from a directory snapshot (relative path plus content hash for activities, streams, manifest) taken before and after, as `fit-import.test.ts` `counts()` and its tree listing do.
- A `-t` filter matching 0 tests exits 0: record the expected matched count on every filtered row.
- A look-alike fixture can invert a result: the FIT-imported seed record in tests must be produced the way the importer writes it. Prefer driving the real `importFit` with `buildFit()` (as the existing nightly-dedupe describe does), plus a hand-seeded record carrying `source_provider: 'garmin-export'` for the edge-offset rows.
- No test may write to or git-checkout a tracked file under `data/`; all fixtures live in `fs.mkdtempSync(os.tmpdir())` dirs. The M1 real-file probe is read-only.

### P6: Updating the CAN-FAIL test silently
SC4 requires the update to be deliberate and the new assertions shown failing first. Do not edit the test and the implementation in one commit.

### P7: Double reporting
`skipped` must still include near skips (the index.ts label is "Skipped (duplicates/non-runs)"); do not also count them in `newRuns`.

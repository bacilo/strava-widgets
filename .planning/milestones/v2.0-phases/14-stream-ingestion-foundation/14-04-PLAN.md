<objective>
Persist intervals.icu streams for newly-synced activities inside the existing daily sync loop, and make CI actually commit them.

Purpose: STREAM-02 and STREAM-03. `IntervalsSync.syncNewActivities()` already fetches a streams response per activity for geometry — this plan makes that single request return every channel and extracts the stream from it, rather than issuing a second request per activity.
Output: an `allChannels` option on `IntervalsProvider.fetchGeometry`, extended `IntervalsSync`, that module's first test suite, and a corrected `file_pattern` in the daily workflow.

**Correction to CONTEXT.md:** its Integration Points section claims "`.github/workflows/daily-refresh.yml` commit pattern picks it up." It does not. The pattern is an explicit allowlist — `data/activities/*.json data/sync-state.json data/geo/*.json` — with no wildcard covering `data/streams/`. Without Task 3, every stream file CI produces is silently discarded on the next checkout. This repo already lost three months of deploys to exactly this bug class (STATE.md: a gitignored path in `file_pattern` froze gh-pages from Feb 23).

**Correction to an earlier draft of this plan (checker BLOCKER 1):** an earlier version proposed "widening the request" by passing the activity's full `raw.stream_types` list into `fetchGeometry`'s existing `streamTypes` option. That is a no-op twice over. The call site at `src/sync/intervals-sync.ts:106-108` **already** passes `raw.stream_types` unfiltered, and `fetchGeometry` narrows whatever it receives to `['latlng','lat','lng','position']` at `src/api/intervals-provider.ts:470-473` before building the query. Non-coordinate channels are therefore stripped *inside* the provider, before the HTTP request, regardless of the argument. `rawAll` (the unfiltered payload) is only populated on the exceptional `!validation.ok` branch, so on the common success path derivation would receive coordinate-only input and every persisted stream would have `channels.hr === false`, `channels.cadence === false`, `channels.elevation === false`. The narrowing must be bypassed at the request itself — see Task 1.
</objective>

Part A — bypass the coordinate narrowing at the request, in `src/api/intervals-provider.ts`.

Add a third option, `allChannels?: boolean`, to `fetchGeometry`'s options object type and its destructuring, defaulting to `false`. When it is false, behavior is byte-for-byte what it is today; `src/index.ts`'s diagnostic caller must be left unchanged.

When `allChannels` is true, `fetchGeometry` issues `this.client.getAllStreams(activityId)` as its one and only request instead of `this.client.getStreams(activityId, types)`, and assigns that unfiltered payload to BOTH `raw` and `rawAll` on the return object. It then skips the `if (!validation.ok)` refetch block entirely — that block exists to recover from a filtered request returning an incomplete coordinate series, and there is nothing left to widen when the first request was already unfiltered. Net request count is still exactly one per activity, and one rather than two on the previously-failing path.

Do NOT attempt to solve this by passing a wider `streamTypes` array. The `wanted`/`types` narrowing at lines 470-473 discards non-coordinate names before the query string is built, so a wider argument never reaches the API; and the sync call site already passes the full `raw.stream_types`. The fix has to be the request itself.

Coordinate extraction needs no change: `extractCoordinates` selects coordinate entries out of whatever payload it is handed, and per `intervals-client.ts`'s own doc comment the unfiltered response is the ground truth about what the activity has — so the geometry path gets strictly better input under this flag, not worse. Record that reasoning in a comment above the branch.

Part B — persist streams in `src/sync/intervals-sync.ts` without adding a network request.

Track whether any entry changed so a sync that adds nothing leaves the manifest untouched.

Change the existing `fetchGeometry` call at line 110 to pass `allChannels: true` alongside the `streamTypes` and `expectedMeters` it already passes.

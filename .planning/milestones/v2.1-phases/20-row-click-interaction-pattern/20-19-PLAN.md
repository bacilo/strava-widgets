<decision_conflict_resolved_here>
**D-16 point 2's stated mechanism defeats D-16 point 4's stated guarantee, and point 4 wins.**

Point 4 says the modifier-click and new-tab paths D-13 bought "all keep working untouched, because
`shouldNavigateOnRowClick` returns `false` for them and `preventDefault()` is *not* what opens the
tab". The first half of that sentence is correct and the second half is not: `preventDefault()` on a
`click` event cancels the browser's default activation behaviour for that anchor **including** the
Cmd/Ctrl+click new-tab open and the Shift+click new-window open. Applying point 2's mechanism
literally — `preventDefault()` whenever the predicate returns `false` — would therefore cancel
exactly the gestures point 4 promises to preserve, turning `20-VALIDATION.md`'s R23 and R24 (both
current PASSes, the entire yield of D-13 and plans 20-16/20-17) back into failures.

**Resolution, implemented in Task 1:** the anchor's click context is assembled from the event
exactly as `attachRowNavigation` does, with the classes the browser itself owns presented neutral
rather than read from the event — `insideAnchor: false` (D-16 point 2, explicit), plus `button: 0`
and all four modifier flags `false`. The predicate then decides only the two refusal classes the
browser cannot see for us: an active text selection (D-12) and a repeat click (D-14). A modifier
click never reaches `preventDefault()`, so the browser's own gesture handling is untouched and
point 4's guarantee holds literally.

This keeps `shouldNavigateOnRowClick` the single source of truth as D-16 point 3 requires: the
definitions of "drag-select in progress" and "repeat click" are not re-implemented in `records.ts`,
and the four modifier names are not duplicated there either. `button: 0` is additionally the honest
value — a `click` event only fires for the primary button; the middle button fires `auxclick`, which
D-12 leaves deliberately unhandled.

The executor must not "fix" the neutral fields to read `event.metaKey` and friends. Task 3 asserts
that `event.metaKey`, `event.ctrlKey`, `event.shiftKey`, `event.altKey` and `event.button` each
occur zero times in `records.ts`, with a failure message that says why, and plan 20-20's row R36 is
the rendered evidence that the browser's gestures still work.
</decision_conflict_resolved_here>

<residual_defect_this_plan_cannot_close>
**D-16 closes R31 completely and R32 only partly. Say so in the summary; do not claim otherwise.**

R31 (drag-select) is fully closed: `draggable = false` stops the anchor from starting a native link
drag, so the drag becomes a text selection, and the `hasTextSelection` refusal then suppresses the
navigation that would otherwise fire when the drag's release produces a click inside the anchor.

R32 (double-click) is not, and cannot be, closed by any mechanism this plan is permitted to use.
`MouseEvent.detail` is `1` on the **first** click of a double-click — the value is `2` only from the
second click onward — so at the moment the first click fires, it is indistinguishable from a single
click and the predicate correctly returns `true`. The browser then performs the anchor's default
navigation. D-14's `clickCount > 1` refusal can only refuse the second click, at both call sites:
this is a property of D-14 as locked, not something D-16 introduces or could repair. The only fix
that would suppress the first click is deferring navigation by the double-click threshold, which
`row-navigation.test.ts` explicitly forbids (zero `setTimeout` occurrences, with a stated reason) and
which would make every single click on the app feel broken.

What this plan therefore delivers for R32: the second click of a double-click no longer re-navigates,
and a double-click that lands after a drag-selection is refused. What it does not deliver: "the word
selects and the page stays on `#/records`". A double-click on these cells navigates on the first
click, exactly as it does on the Date cell, on `list.ts`'s Activity-cell link, and on every link on
the web.

This is a disposition question for the developer, not a defect the planner may define away. Plan
20-20's row **R35** puts it to them explicitly and records their yes or no. The executor of this plan
must state the residual in `20-19-SUMMARY.md` in these terms and must not record R32 as closed.
</residual_defect_this_plan_cannot_close>

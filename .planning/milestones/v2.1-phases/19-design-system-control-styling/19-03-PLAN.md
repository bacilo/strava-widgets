## Derived correction to D-06's stated cascade mechanism — read before Task 2

19-UI-SPEC.md § Button Baseline Contract asserts that the 12 existing button classes "keep overriding this baseline wherever they already declare a property (lower specificity than every existing class selector, so nothing currently rendered changes shape or colour)". **That statement is true for `button { … }` but false for `button:hover { … }`, and the difference is load-bearing.**

CSS specificity arithmetic, verified against the current file:

| Selector | Specificity | Beats a single class? |
|----------|-------------|----------------------|
| `button` | `0,0,1` | No — every class wins, exactly as the spec says |
| `button:hover` | `0,1,1` | **Yes** — a pseudo-class counts as a class, so `0,1,1` > `0,1,0` |
| `.pagination__button--current` | `0,1,0` | loses to `button:hover` |
| `.segmented__option--active` | `0,1,0` | loses to `button:hover` |
| `.calendar-day--tint-1..4` | `0,1,0` | loses to `button:hover` |
| `.cta:hover` | `0,2,0` | **beats** `button:hover` |

Four concrete consequences of writing `button:hover` bare, all verified against the real rules in `src/dashboard/styles.css`:

1. `.pagination__button--current` (line 556) declares `background: var(--accent-strong)` with `color: #ffffff`. A bare `button:hover` replaces that fill with the surface mix while the white text stays — white on approximately `#ebebec` in light theme, roughly 1.1:1. That is an unreadable control and it breaks 17-UI-SPEC's reservation of `--accent-strong` for exactly this state.
2. `.segmented__option--active` (line 794) has the same shape and the same failure.
3. `.calendar-day--tint-1..4` (lines 673-687) carry the accent distance-tint scale. A bare `button:hover` flattens the hovered day's tint to grey, destroying the scale reading precisely where the user is pointing.
4. `:disabled` declares no `background`, so a bare `button:hover` gives hover feedback to disabled controls — including pagination prev/next and the Banister toggle, two of the five states D-07 exists to mark as *not* interactive.

**None of this re-litigates D-06.** D-06's decision (one shared hover, the `color-mix(in srgb, var(--surface) 92%, var(--text))` formula, mixing toward `--text` so it darkens in light and lightens in dark) is implemented exactly as locked. Only the *selector* is corrected so the rule actually delivers D-05's own stated contract that existing classes keep their declared properties. The correction is `:where()`, which contributes **zero** specificity — so the corrected selector stays at `0,1,1`, identical to the bare form, and nothing else in the cascade shifts.

**D-06's second clause needs a second correction.** D-06 states the shared hover "also repairs `.cta:hover`". It cannot: `.cta:hover` is `0,2,0` and beats `button:hover`, and five of `.cta`'s ten sites are `<a>` elements (`list.ts:225`, `records.ts:391`, `records.ts:505`, `detail.ts:188`, `detail.ts:654`) that a `button` selector never reaches at all. The only cascade path to D-06's stated intent — "the primary CTA has hover feedback" — is editing `.cta:hover`'s own declaration, which Task 3 does, using the same `color-mix` technique but mixing from `var(--accent)` because `.cta`'s fill is accent, not surface. Mixing `--surface` into an accent-filled CTA would turn it grey under white text.

Both corrections are flagged as explicit call-out rows on plan 19-05's human checkpoint agenda so the developer sees the rendered result and can overrule.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `button:hover` at `0,1,1` → every single-class button modifier at `0,1,0` | The highest-leverage cascade boundary in the phase; a pseudo-class silently outranks every existing class modifier |

`.app-nav` (line 159-168) declares `position: sticky; top: 0` and no `z-index`. That is the whole defect.

**Both elements live in the root stacking context.** `src/dashboard/main.ts:22` mounts the nav into `#app-nav-root` and line 25 mounts views into `#app`; neither container, nor `.view` (styles.css:235-239 — `padding`, `max-width`, `margin-inline` only), declares `transform`, `opacity`, `filter` or `z-index`. So there is no intervening stacking context to contain a promoted focused element, and the nav and a focused control compete directly.

**Reachable without scrolling, too.** Several views call `heading.focus()` on a `tabindex="-1"` heading after keyboard navigation (`trends.ts:1212`, `detail.ts:662`, `calendar.ts:92,320`, `overview.ts:255`, `records.ts:163`). A keyboard-initiated programmatic focus matches `:focus-visible` in Chrome and Firefox, and `records.ts:163` focuses section headings that land directly under the sticky chrome.

**The `.splits-table__km` tie.** `:focus-visible` and `.splits-table__km` both declare `z-index: 1`, and `.splits-scroll` (`overflow-x: auto`, no `position`, no `z-index`) does **not** create a stacking context, so the tie is real and resolves by tree order. Today it is latent, not live: `src/dashboard/views/detail-sections.ts` builds the splits table from plain `<th>`/`<td>` text cells plus `.pace-bar` divs — no focusable descendant exists inside `.splits-scroll`. `.splits-scroll`'s own comment (styles.css:868-870) explicitly anticipates that changing. Resolving the tie now is a one-declaration change with no rendered effect today; leaving it means a focusable cell added later silently paints over the sticky km column.

**The intended ladder, to be written into the file as a comment and pinned by a test:**

| Layer | Rule | z-index | Why it sits there |
|-------|------|---------|-------------------|
| 4 (top) | `.app-nav` | 20 | Outermost global chrome; it is opaque and every route scrolls content under it |
| 3 | `.records-jump` | 10 | Section-level sticky jump bar; its `top` is computed at runtime from the live nav height, so it abuts the nav rather than overlapping it, and nav-over-jump-bar is the correct outcome if a resize ever transiently overlaps them |
| 2 | `.splits-table__km` | 2 | Sticky column inside one horizontal scroller; must outrank a focused cell in its own row for the same reason the jump bar outranks a focused control on its own page |
| 1 (bottom) | `:focus-visible` | 1 | Focused control, promoted by 19-07 above its unpositioned siblings and `z-index: auto` positioned neighbours |

Gaps are deliberate: 20/10/2/1 leaves room for a future layer between rungs without renumbering.

**What giving `.app-nav` a `z-index` changes about the nav itself.** `position: sticky` + a numeric `z-index` makes `.app-nav` a stacking context. Its focusable descendants (`.app-nav__toggle`, `.theme-toggle`, the `.app-nav__link` anchors) then resolve their `z-index: 1` *inside* that context — their rings still paint above nav siblings, and the whole nav paints at layer 20 above page content. `.app-nav` declares no `overflow`, so nothing inside it is newly clipped, and nav.ts appends only in-flow children (brand, toggle, links list, theme toggle) with no absolutely-positioned descendants. State this explicitly in the audit rather than assuming it.

**Gate-command hygiene.** The `<automated>` gates below use the delete-log / redirect / capture-status / require-both form specified in `19-06-PLAN.md` § `<groundwork>`. `A && B && cmd 2>&1 | tee log; ! grep -q needle log` **exits 0 even when `A`, `B` or `cmd` failed** — the `;` makes the grep the sole determinant of exit status, and `| tee` masks the build's own status anyway, so a log left by an earlier clean run answers for a run that never happened. `PIPESTATUS` is not the fix either: the developer's shell is zsh, where it is spelled `pipestatus` and is 1-indexed, so a bash-shaped `${PIPESTATUS[0]}` reads empty. Do not "simplify" these gates back into that shape.

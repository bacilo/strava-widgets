## Option (a), not option (b). Why, from 24-CONTEXT.md's own decisions.

`24-VERIFICATION.md` offers two acceptable dispositions: (a) pass `liveExclusions` into
`buildPrBadgeLabels` and suppress badges the live document excludes, or (b) document and
checkpoint-test the header-badge staleness window as accepted, disclosed behaviour.

Option (a) is correct here for three reasons taken from the phase's locked decisions:

1. **D-04 is unambiguous about semantics.** The developer's verbatim words: *"If an activity is
   excluded we should no longer use it to calculate PRs of any kind."* A rendered `PR — 400m`
   badge on an activity the developer has just excluded is exactly a PR claim of a kind.

2. **The rule already exists in this module and is only half-applied.** The current
   `buildPrBadgeLabels` docblock states: *"An effort with `excludedFromRecords === true` never
   produces a badge, even if `wasPRAtTheTime` is also true — an excluded effort did not set a
   record (T-18-HONEST-06)."* Extending that established rule from one document to the document
   that now drives the neighbouring badge is a generalisation, not a new policy.

3. **The existing staleness defence does not cover this case, by its own text.** The docblock at
   lines 83-92 defends a disagreement between the panel and the **Records screen** — two genuinely
   separate documents that have not converged, closed by "Recompute records" (D-07). It says
   nothing about two derivations made side by side from the same fetch in the same paint. Before
   Phase 24 no such window existed; 24-09 created it.

Option (b) would require documenting `PRExcluded — {reason}` in one table cell as intended
behaviour. That is not defensible against D-04.

**What option (a) must cover, and what the verification report under-specifies.** The `missing`
list names only `buildPrBadgeLabels`. But the contradiction R15 actually quoted —
`PRExcluded — ROUND2-2026-09-01 GPS device unreliable` — is the FLAGS CELL, produced by
`buildPrFlagsCell` from `row.isPr` and `row.excluded`. Fixing only the header would leave that exact
rendered string intact. WR-05's own fix note says so: *"Row-level `isPr` needs the same treatment or
an explicit note."* Both are therefore in scope for this plan.

**What stays out.** `effort.excludedFromRecords` and `effort.wasPRAtTheTime` remain the ONLY source
of truth for COMPUTED STATS — Records-screen rankings, promoted next-best efforts,
`compute-dashboard-index` counts, and the Activities-list badge at `list.ts:266`. Nothing here
recomputes a ranking in the browser. D-06 is untouched: `buildExclusionReasonIndex`,
`buildPrFlagsCell`, `buildPrTableRows` and `records.ts:534` keep their current signatures.

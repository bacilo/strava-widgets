<objective>
Add the week-start control itself: a `.segmented` Sunday/Monday toggle in the calendar header that
persists the choice and rebuilds the grid in place without moving focus. This completes CAL-01's
interaction half and is where CAL-03's shared control styling lands.

Purpose: plan 22-03 made the grid honour a week start it reads from storage, but nothing can change
it yet. This plan is deliberately small and separate so the toggle handler — the single riskiest
piece in the phase, given Phase 20's two shipped focus-theft regressions — gets its own review and
its own guard tests.

Output: the segmented control in `.calendar-header`, a synchronous `setWeekStart`, and a
source-structure guard section in `calendar.test.ts` that fails if the handler ever grows a
`focus()`, a `mount()` re-entry, or an `await`.

**Explicitly NOT in scope.** No new CSS — the `.segmented` block at `styles.css:899-954`, the shared
button hover with its existing `.segmented__option--active` exclusion at `styles.css:1382-1393`, and
the global two-tone `:focus-visible` ring at `styles.css:456-461` are all class-selector-based and
reach a third instance with zero opt-in. Adding a calendar-scoped segmented rule would be the drift
CR-02/CR-03 already caught once in this family of controls. No `<select>` (D-01). No URL parameter
(D-05). No change to the header's month total or caption — neither depends on the week start.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user click / key activation → `setWeekStart` | The only input is which of two buttons was pressed; the value passed is a literal `'sunday'` or `'monday'` chosen in the listener, never derived from the DOM |
| `setWeekStart` → `localStorage` | The one new write path in phase 22 |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-22-WK-01 | Tampering | the value written by `setWeekStart` | mitigate | The listeners pass compile-time literals, so the written value is always a valid `WeekStart`. The read side still allow-lists independently via `parseWeekStart`, so a value tampered with between sessions cannot re-enter the grid math |
| T-22-WK-02 | Denial of Service (client-side) | `writeWeekStart` on a throwing `setItem` | mitigate | `writeWeekStart` swallows the failure (plan 22-02), and it is called BEFORE the rebuild, so a quota-exceeded or private-mode write cannot abort the repaint. In that session the toggle still works visually; only persistence is lost |
| T-22-UI-01 | Denial of Service (UI availability) | the toggle rebuild path | mitigate | The handler is synchronous end to end — no `await`, no `navigateTo`, no `mount()` re-entry — so it cannot paint into a container the view no longer owns and cannot interleave with the awaited `loadIndex()` continuation the two `mountedContainer` guards protect. A guard test asserts `await` never appears in the handler body |
| T-22-A11Y-02 | Repudiation (announcement integrity) | `aria-pressed` on the two options | mitigate | Both options' `aria-pressed` are updated on every toggle, not just the one being activated — the invariant both shipped instances follow. A stale `aria-pressed="true"` on the deselected option would misreport state to assistive tech; the guard test asserts two `aria-pressed` writes exist |
| T-22-SC | Tampering | npm/pip/cargo installs | accept (not applicable) | Zero new packages in this phase; RESEARCH.md § Package Legitimacy Audit records "Not applicable". No install task exists in any phase-22 plan |
</threat_model>

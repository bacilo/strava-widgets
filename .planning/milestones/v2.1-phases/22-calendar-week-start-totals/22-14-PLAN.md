<objective>
Close `22-VERIFICATION.md`'s **Gap 2** / `22-REVIEW.md` **CR-01**: the header theme toggle is
permanently stuck on "light" whenever the storage handle is null or unusable.

Purpose: `nav.ts:210-215`'s `handleThemeToggleClick` re-derives the current mode from storage on every
click — `const current = readStoredMode(resolveStorage())`. Under blocked site data `resolveStorage()`
returns `null`, `readStoredMode(null)` returns `'auto'` unconditionally, and `cycleThemeMode('auto')`
returns `'light'` unconditionally, so click 1, click 2 and click N all apply light and dark is
unreachable. The same root cause independently breaks `watchSystemTheme`'s auto-only guard, so an OS
theme change silently overrides an explicit in-session choice.

This defect is **newly reachable because of this phase's own Round 3 fix**: before plan `22-11`, the
identical browser configuration crashed the module graph at `main.ts:19` and rendered a blank page, so
the toggle could never be clicked. Round 3 traded a blank page for a working page with a broken
control, and R22 never clicked the control it had just made reachable.

Output: a DOM-free `src/dashboard/nav-theme.ts` controller that owns the mode in memory, seeded once
at mount and reassigned on each click — the same `let weekStart` shape `calendar.ts:443` already uses,
which is exactly why the week-start toggle does NOT have this bug. Plus a unit test that fails against
the defective form, and a source guard that fails if a per-click storage read is ever reintroduced.

**Explicitly NOT in scope.** No jsdom, no new dependency, no change to `vitest.config.ts`. No change
to `theme.ts` (plan `22-13` already added the `isAuto` seam this plan consumes) and none to
`styles.css` (plan `22-15`). `index.html`'s inline pre-paint script is untouched. The D-15 fence
stands.
</objective>

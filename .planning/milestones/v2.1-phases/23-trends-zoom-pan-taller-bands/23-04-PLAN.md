<objective>
Create `src/dashboard/views/chart-zoom.ts` - the single module holding every piece of zoom wiring:
plugin configuration, the on-screen control cluster, the modifier hint, and the settle updater
that keeps the aria-label and the button states honest.

Purpose: D-04 requires the wiring to be extracted so a future phase can adopt it on the activity
detail view cheaply, and this phase's two hardest defects both live here. The first is
source-verified Pitfall 3: `chart.zoom()` and `chart.pan()` - the exact API the D-11 buttons call
- fire only `onZoom`/`onPan`, never `onZoomComplete`/`onPanComplete`. Wiring the aria-label and
Reset-visibility updates to the `*Complete` callbacks alone produces buttons that visibly move the
chart while the aria-label and Reset button silently never update, and this repo's DOM-less test
suite structurally cannot see it. The second is Pitfall 1: `limits.x: 'original'` resolves to the
scale's constructed bounds, which under D-06 is the opening window, not the archive - using the
sentinel would make "zoom out to see everything" impossible.

This plan creates one new file and touches nothing else, so it runs in parallel with plan 23-03.

Output: `src/dashboard/views/chart-zoom.ts`.

Plugin API facts, all read directly from `chartjs-plugin-zoom@2.2.0`'s shipped source by research
(HIGH confidence) - do not re-derive them from the docs site:
- `chart.zoom(factor)` and `chart.pan(delta)` fire `onZoom` / `onPan` ONLY. `onZoomComplete` /
  `onPanComplete` fire only from gesture paths (250 ms-debounced wheel, `mouseup` after drag,
  Hammer `panend`/`pinchend`) and from `chart.resetZoom()`.
- `chart.pan({x})`'s delta is in SCREEN PIXELS. A POSITIVE x reveals earlier / smaller-value data;
  a NEGATIVE x reveals later data.
- `limits.x.min/max: 'original'` is captured lazily on the first zoom/pan from
  `scale.options.min/max` at that moment.
- `zoom.wheel.modifierKey` is a single string, checked as `event[key + 'Key']`.
- `zoom.drag` (rectangle-select zoom) and `pan` are two independent gesture engines competing for
  the same physical drag. `pan` is what D-15 wants; `zoom.drag.enabled` must stay `false`.
- A plugin passed via a chart's own `plugins: [...]` array receives the identical `start`/`stop`
  lifecycle as a globally-registered one, and `chart.destroy()` fires `stop`, which removes the
  listeners and destroys the Hammer manager. No extra teardown code is needed for the plugin.

- `interface ZoomControlCluster { root, hint, panEarlier, panLater, zoomOut, zoomIn, reset }`

- `interface ZoomController { settle(source?: Chart): void; applyRange(range: ZoomRange): void; currentRange(): ZoomRange | null; destroy(): void }`

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser input events to chart scale bounds | Wheel, pointer and click events drive `scales.x.min/max`; all values are clamped by `limits` computed from the dataset, not from user input |
| Third-party plugin code inside the client bundle | `chartjs-plugin-zoom` and `hammerjs` attach DOM listeners to the canvas |
| Lazy chunk boundary | This module statically imports the plugin, so anything importing it inherits that weight |

<plan_decision>
**PD-01 — the activity name comes from `data/dashboard/index.json`, fetched client-side.**

D-12 requires "date + activity name" on each row. `data/stats/best-efforts.json` has no `name` field
(`ActivityBestEfforts` is `activityId`, `startDate`, `distanceSource`, `efforts`,
`excludedFromRecords`), so the name exists only in `data/dashboard/index.json`. Measured this session:
all 47 flagged ids join to an `index.json` row on `String(row.id)`, including `i`-prefixed
intervals.icu ids.

Resolution: the queue joins names from `data/dashboard/index.json`. Rationale:
- D-12 is a locked decision naming the activity name explicitly; dropping it would be scope reduction.
- D-08's literal constraint is "no new server read route" — this adds none. `index.json` is already
  public, already mirrored by `RECOMPUTE_DATA_DIRS`, already fetched by the dashboard itself, and
  stays current after a recompute exactly as the other two do.
- D-12's rejected alternative rejected `index.json` as a source of **device family and quality tier**
  — fields that do not drive the exclude decision. The name is a different case: it is required by
  the accepted half of the same decision.
- The join is name-only and non-load-bearing: a missing row degrades to the label
  `Activity <id>`, and the flagged SET is derived without `index.json` at all, so a failed third
  fetch cannot change which rows appear or how many.

This is nevertheless a third `fetch()` that D-08's two-file list did not spell out, so it is flagged
to the developer as an explicit row at plan 29-08's browser checkpoint. If the developer rejects it,
the revert is bounded: drop the third fetch and render the `Activity <id>` label — no other behavior
changes.
</plan_decision>

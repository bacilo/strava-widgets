<objective>
Render the demotion where a human can see it: on the activity detail view's Best Efforts panel with
its reason, and on the Records screen as a note naming why a table is empty or short.

Purpose: PR-03 requires a demoted effort be "always visible with the reason it was demoted", and
ROADMAP criterion 4 requires it be read in the browser rather than found in JSON. D-09 additionally
requires the `buildPrFlagsCell` hazard be FIXED rather than extended — the pattern map confirmed
each badge is already a separate DOM node, so the live defect is not string concatenation in JS but
that the cell's badge strings are decided inside a DOM builder this repository's `node`-environment
test suite can never read, and that bare `<span class="badge">` nodes with no explanation read as
one run-on claim in flowed text and to a screen reader (Phase 24 Round 2 R15's
`PRExcluded — {reason}`).

Output: a spec-driven PR-flags cell, a three-state Records empty state plus a short-table note, a
distinct demoted badge style, and the first source-wiring guards over both render paths.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| fetched `best-efforts.json` shard → rendered badge text | The browser renders `demotion.reason` and the exclusion reason, both originating in machine-written JSON that is served over HTTP and can be stale or hand-edited locally. |
| fetched document → Records empty-state and note text | The demoted count is derived in the browser from the fetched document. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28-04-A | Tampering | reason strings rendered into the DOM | mitigate | Every new string reaches the DOM through `textContent` or `appendAccessibleBadge`'s `textContent`, never `innerHTML`; the Task 2 guard asserts `innerHTML` appears zero times in `records.ts`, and `appendAccessibleBadge` is an existing, already-reviewed helper. |
| T-28-04-B | Denial of Service | rendering a stale shard with no `demotion` field | mitigate | `prFlagBadgeSpecs` and `countDemotedAtDistance` (plan 28-02) both read the field defensively, so a stale document yields no badge and a count of 0 rather than a TypeError — the Phase 26 CR-02 lesson, where a missing index field produced a runtime error on every row. |
| T-28-04-C | Information Disclosure | aria description ids colliding across badges | mitigate | The description id is built from `row.distance` plus `spec.descriptionIdSuffix`, asserted by the Task 1 guard, so two badges in one cell cannot share an id and mislabel each other to assistive technology. |
| T-28-04-D | Elevation of Privilege | a rendered control that writes | mitigate | D-11: every element added by this plan is text. The Task 2 guard's parameter-count and call-count assertions would not catch a new button, so the plan adds none and the summary must state that no `button`, `input` or event listener was introduced. |
| T-28-04-SC | Tampering | npm/pip/cargo installs | mitigate | Not applicable — zero packages installed. In particular no DOM-simulation library is added; the node-only test environment is preserved deliberately. |
</threat_model>

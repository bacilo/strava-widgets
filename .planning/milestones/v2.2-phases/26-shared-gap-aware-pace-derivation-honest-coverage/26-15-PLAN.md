<objective>
Close CR-02: a stale or partially-regenerated `index.json` must not paint a false "Pace disputed"
badge on every activity row and then throw a TypeError out of the list and overview render paths.

Purpose: `paceDisagreement` is this phase's new additive index field. `index.json` is a gitignored,
CI-regenerated, separately-cached artifact — `dashboard-index.types.ts` says so explicitly and even
ships `ParsedDashboardIndexRow` for exactly this hazard — but `index-client.ts` casts raw JSON to
the producer type, so a row can legitimately arrive without the key. `list.ts:341` and `:380` test
it with a strict `!== null`, and `undefined !== null` is `true`. `detail.ts:631` reads the same
field correctly with `?? null`, which shows the case was considered at one call site and missed at
the other. `26-VERIFICATION.md` records this under `deferred:` with the explicit disposition
"recommended as an immediate follow-up fix, not a later-phase deferral", and this project has a
recorded staged-build/browser-cache failure mode in which a stale `index.json` is precisely what
gets served.

Output: both call sites reading through one nullish-narrowing helper, a regression test that
constructs a row with the key genuinely absent, and a source guard so the strict form cannot return.
</objective>

**The two defective sites, verbatim.**

- `src/dashboard/views/list.ts:341`, inside `statusBadgeTexts(row: DashboardIndexRow): string[]` —
  `if (row.paceDisagreement !== null) { texts.push(PACE_DISPUTED_BADGE_TEXT); }`
- `src/dashboard/views/list.ts:380-381`, inside the unexported
  `appendStatusBadges(container, row, idPrefix)` —
  `} else if (text === PACE_DISPUTED_BADGE_TEXT && row.paceDisagreement !== null) { appendPaceDisputedBadge(container, idPrefix, row.paceDisagreement); }`

`appendPaceDisputedBadge` → `paceDisputedExplanation(disagreement)` → `disagreement.streamPaceSecPerKm`
is where the TypeError lands, inside the synchronous render path shared by `renderActivityRow`
(mobile card) and `buildTableRow` (desktop Status cell). `RowSurface` enumerates the four surfaces
this single dispatch reaches: `activity-card`, `activity-table`, `overview-prs`,
`overview-activities` (D-11).

**The correct precedent already in the codebase:** `src/dashboard/views/detail.ts:631` —
`const disagreement = indexClient.getRow(detail.id)?.paceDisagreement ?? null;`

**The type that exists for exactly this:** `src/analytics/dashboard-index.types.ts:130` —
`export type ParsedDashboardIndexRow = Partial<DashboardIndexRow> & { id: string };`
Its own doc comment states that serialization plus re-parse does not carry the producer's
required-key guarantee, so no key can be assumed present on the read side.

**Why no test caught it.** Every fixture in this repository sets the key explicitly — `list.test.ts`'s
`baseRow()` factory (~:402) ends with `paceDisagreement: null, ...overrides`, and
`list-logic.test.ts`, `calendar-logic.test.ts`, `overview.test.ts`, `trends-*.test.ts` and
`gear-aggregate-logic.test.ts` all do the same. Passing `{ paceDisagreement: undefined }` as an
override is NOT a faithful reproduction either — it is present-and-undefined, which behaves the same
here but is a different object shape from a parsed row that never carried the key. Build the fixture
by destructuring the key OFF a `baseRow()` result.

**Test-environment constraint.** `vitest.config.ts` sets `environment: 'node'`. There is no jsdom
and no headless browser anywhere in this repository — `list.ts:1220`, `row-navigation.test.ts:13`,
`overview.test.ts:28` and `list.test.ts:547` all say so in their own comments. `appendStatusBadges`
is unexported AND calls `document.createElement` through `appendBadge`, so it cannot be unit-tested
directly. That is why the fix below introduces one small exported pure helper: it makes the
narrowing itself testable in node, and it makes the two call sites structurally incapable of
disagreeing. `list.test.ts` already carries a local `stripComments` helper (~:590) and already
imports `readFileSync`, so the source-text guard needs no new machinery.

**Confirmed latent, not firing.** Today's `data/dashboard/index.json` has 1,890 rows and 0 rows
missing the key (verified in `26-VERIFICATION.md`'s Behavioral Spot-Checks). This fix is against the
stale-artifact path, not a currently-visible defect. Do not "verify" it by loading the live index —
that would prove nothing.

**Deliberately OUT OF SCOPE.** The review additionally recommends retyping
`src/dashboard/data/index-client.ts`'s rows as `ParsedDashboardIndexRow` instead of casting raw JSON
to the producer type. That is a type-level refactor whose blast radius is every consumer of
`getRows()`/`getRow()` — each would face newly-optional keys and need its own narrowing — and
`26-VERIFICATION.md`'s `deferred:` entry does not name it as part of CR-02's closure. Do not attempt
it here. Log it in `deferred-items.md` with this reasoning.

# Phase 20: Row-Click Interaction Pattern Verification Report

**Phase Goal:** Every row representing an activity, on every screen, is clickable through to that activity using the same pattern `list.ts` already established — propagated, not reinvented — and is keyboard-accessible rather than a click handler on a bare `<div>`.

## Summary

This is the fourth verification pass on Phase 20. The prior round scored 1/4 and named two problems: a CRITICAL focus-stealing regression in `list.ts` (`notedActivityId` leaking across unrelated navigations), and SC1's R18/R19 gap (five of six Records PR-table cells not opening a new tab/window on a modified click, because they carried no real anchor).

Both are genuinely, independently confirmed fixed this round, not taken on the SUMMARYs' word:

- **The `notedActivityId` focus-leak regression is closed.** `takeNotedActivityId()` (`list.ts:1114-1117`) is now the first statement of `mount()` (`list.ts:1252`), consumed unconditionally before any of the four exit paths can leak it. Confirmed by direct source read and by Round 4's R22 — a real browser sequence exercising the exact triggering path (detail view, back, zero-match filter, cleared filter) that found zero stray highlights and focus correctly on the page heading throughout.
- **R18/R19's original gap is closed on its own terms.** Plans 20-16/20-17 (D-13) gave every content-carrying cell of both Records tables a real `<a href>` at `tabIndex=-1`, sharing the Date cell's curated label. Round 4's R23/R24 are genuine PASSes: a real Cmd+click on a non-Date cell now opens a real background tab at the correct activity, and the originating tab does not navigate.
- **UX-02 reached a clean, fully-evidenced sweep for the first time.** Plan 20-18's disclosed fixture edit produced a badge-carrying Overview Recent Activities row; R26/R27 PASS with the badge text quoted verbatim, closing the prior round's R2/R16 dataset-coverage gap.

But the phase goal is still not achieved, for two independent reasons — one carried over almost unchanged (SC4's checkpoint itself recording FAIL) and one new, more severe finding this verification confirmed from the fresh `20-REVIEW.md`:

1. **D-13's real cell anchors, while closing R18/R19, opened two new confirmed defects (GAP 12) in the exact same checkpoint round.** Dragging inside a now-anchored Records cell starts a native link-drag instead of preserving a text selection (R31 FAIL), and double-clicking a value navigates away before word-select completes (R32 FAIL), because D-12's drag-select guard and D-14's double-click refusal both live exclusively in the row-level click listener, which a real anchor's native click/drag behavior bypasses entirely. Confirmed directly in `row-navigation.ts` and `records.ts`, and independently re-confirmed by this round's own real-browser checkpoint evidence.
2. **A newly-confirmed, spec-provable accessible-name defect (`20-REVIEW.md`'s CR-01) in the same D-13 anchors.** Every non-Date cell anchor in a Records PR-table or progression-table row carries the identical `aria-label` — the Date cell's own curated label, reused verbatim — so a screen reader announces the same phrase for every cell in a row and the Flags cell's own badge text is discarded entirely. This is the exact defect class this phase's own CR-02 already fixed once at row scope, reintroduced at cell scope, and is provable from the ARIA accessible-name computation algorithm alone (confirmed by direct source read, `records.ts:422-458` and `572-589` — no live browser needed to establish it, and it was independently corroborated live during the checkpoint: four cells of one row all carried the identical `aria-label`).

SC4's own recorded checkpoint verdict is unambiguous and is not this verifier's inference: `20-VALIDATION.md` Round 4 frontmatter reads `status: blocked`, `nyquist_compliant: false`, and its own Checkpoint Outcome section states "OVERALL ROUND 4 VERDICT: FAIL."

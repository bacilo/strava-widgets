# Phase 20 Plan 07: CR-02 Status-Badge Accessible-Name Gap Closure Summary

**Folded status-badge text (No streams/No HR, Low confidence, Excluded from records, N PR) into the whole-row aria-label on all three surfaces Phase 20 made row-anchors — the Activities mobile card, Overview Recent Activities (same renderer), and Overview Recent PRs — from one shared array that also renders the visible badges, so the two can never drift apart; records.ts confirmed unaffected and pinned so it stays that way.**

## Accomplishments

- `statusBadgeTexts(row)` is now the single source of truth for status-badge text on `list.ts`'s two surfaces — `appendStatusBadges` iterates it to build the visible `.badge` spans, and `activityRowAriaLabel` folds it into the composed `aria-label` via the new shared `composeRowAriaLabel(base, badgeTexts)`. The rendered badges and the announced badge text now literally cannot disagree.
- `renderActivityRow`'s row anchor sets `aria-label` from `activityRowAriaLabel(row)` and, when `row.lowConfidence` is true, also sets `aria-describedby` on itself — the low-confidence explanation now has a real announcement point, because a description is only announced when its host is announced, and on this surface the row anchor is the only element that gets announced.
- `appendStatusBadges` now takes a surface-unique `idPrefix` — `'activity-card-' + row.id` from `renderActivityRow`, `'activity-table-' + row.id` from `buildTableRow` — so the two layouts `#/list` renders simultaneously (CSS hides one via media query) never collide on one `<id>-low-confidence-desc` element id.
- `overview.ts`'s `renderRecentPrRow` now composes its accessible name via `recentPrRowAriaLabel(row)`, importing the shared `composeRowAriaLabel` from `list.ts`, folding in `recentPrBadgeText(row)` (`<n> PR`). This deliberately reverses plan 20-02 Task 3 step 3's "do not put the PR count in the label" instruction — that instruction predated CR-02's discovery that the badge was announced nowhere.
- `buildTableRow`'s Activity-cell `aria-label` and `records.ts` are both byte-identical to before this plan — on both surfaces the badges live in a sibling cell and are already announced by table navigation, so folding them into the anchor's label would double-announce them. This asymmetry is deliberate and is now pinned by a source-structure regression test.
- Added 21 new unit tests (`statusBadgeTexts`, `activityRowAriaLabel`, `composeRowAriaLabel`, `lowConfidenceDescriptionId` in `list.test.ts`; `recentPrBadgeText`/`recentPrRowAriaLabel` in the new `overview.test.ts`) plus 6 new source-structure guards in `row-semantics.test.ts`, including the `records.ts` non-regression guard. Both CR-02 mutations (dropping the fold in each of `activityRowAriaLabel` and `recentPrRowAriaLabel`) were executed and confirmed to fail the relevant tests, then reverted with `git diff --stat` empty afterward — proof the new assertions actually cover the defect CR-02 found.

- **Fold-into-the-label, not wrapper-div** — per the plan's explicit constraint, chosen because the wrapper-div alternative from `20-REVIEW.md` would have contradicted D-01/D-07 (the whole row IS the link), D-08 (`renderRecentPrRow`'s exact three children), and the `.activity-row` `display: flex` contract Phase 17 froze.

Documented as a deviation below because it changed how the corresponding `row-semantics.test.ts` guard had to be written.
- **This refines D-04, not overturns it** — the curated three-part base (`name`, formatted date, distance) is unchanged; only the status-badge texts are appended, and only where the badges are trapped inside the anchor (the card surfaces). `buildTableRow` and `records.ts` deliberately do NOT fold badges into their anchor labels.

**2. [Rule 1 - Bug, test-authoring, caught before commit] `row-semantics.test.ts`'s id-prefix guard would have false-failed against the correct, DRY implementation**

- **Found during:** Task 3, while writing the CR-02 source-structure guards
- **Issue:** The plan's directive ("comment-stripped list.ts contains the card id prefix exactly twice and the table id prefix exactly once") assumed the literal string `'activity-card-'`/`'activity-table-'` would be repeated inline at each call site. Task 1's implementation instead extracts `idPrefix` into one local variable in `renderActivityRow`, reused at both its `aria-describedby` and `appendStatusBadges` call sites — a correct, DRY choice, but it means the literal `'activity-card-'` substring appears only once in source, not twice. Separately, a bare substring count of `'activity-table-'` would match TWICE regardless of implementation choice, because `buildDesktopTable`'s pre-existing, unrelated `'activity-table-wrapper'` className literal already contains that substring — so the plan's assumed "exactly once" was never achievable via a naive substring count.
- **Fix:** Wrote the guard to match the id-prefix TEMPLATE LITERAL construction precisely (`` /`activity-card-\$\{row\.id\}`/g `` and the table equivalent) instead of the bare prefix substring. Each pattern matches exactly once in `list.ts`, confirming the two prefixes are present, single-defined, and different strings — the load-bearing property CR-02's fix actually needs (no id collision between the two simultaneously-rendered `#/list` layouts). Documented the reasoning inline in the test's own `it` description so a future reader does not "fix" it back to a bare substring count.
- **Files modified:** `src/dashboard/row-semantics.test.ts` (part of the planned Task 3 file set — no additional file touched).
- **Verification:** `npx vitest run src/dashboard/row-semantics.test.ts` → 22/22 passing, including this guard.
- **Committed in:** `169330e` (Task 3 commit).

**3. [Rule 1 - Bug, test-authoring, caught before commit] `row-semantics.test.ts`'s aria-label-adjacency guard initially matched the wrong occurrence**

- **Found during:** Task 3, first run of the full targeted suite
- **Issue:** The line-adjacency check for `overview.ts` (proving the sole `aria-label` occurrence sits on the same line as, or the line before, the `recentPrRowAriaLabel` call) used `Array.findIndex` for both the `aria-label` line and the `recentPrRowAriaLabel(` line. - **Fix:** Changed the usage-line lookup to take the LAST occurrence of `recentPrRowAriaLabel(` (the call site), via a `reduce` that keeps overwriting the found index. Verified the fix by re-running the suite: the guard now correctly identifies both occurrences are on the same line and passes.

# Phase 18 — UI Design Contract

> Visual and interaction contract for `#/records` and `#/trends`, plus the Phase 18
> additions to `#/activity/:id`. Generated by gsd-ui-researcher, verified by
> gsd-ui-checker. Cross-referenced by section number (`18-UI-SPEC § N`) from
> 18-VALIDATION.md and plan files, mirroring 17-UI-SPEC's convention.

This is **not** a new visual language. Phases 16–17 already shipped the design
system this phase must extend without deviation: `src/dashboard/styles.css` is
the single stylesheet, tokens are declared once (`:root` + two `[data-theme]`
blocks), views are light-DOM vanilla TS, and every existing formatter/badge/
chart-theming pattern is reused rather than forked. Section 14 (New CSS Class
Inventory) is the only place this document invents new classes; everywhere
else it names an existing class to reuse.

# Section Detail

## § 1 — Records page layout and the sticky jump list (D-02)

**Page structure.** `#/records` is a single `.view` (existing class, 1100px
max-width, centered, `--space-lg` padding) containing, in this order:

1. `<h1>` "Records" (existing heading pattern, `tabIndex=-1`, focused after mount)
2. The jump list (this section)
3. `<section id="records-superlatives">` — § 4a
4. `<section id="records-pr-tables">` — § 2, containing all 7 distance tables
5. `<section id="records-pr-evolution">` — § 3
6. `<section id="records-predictions">` — § 4b (Race Predictions / Riegel)

**Jump list has exactly 4 items** (one per top-level section above), **not**
one per PR-distance table — that would make the sticky bar 10+ items wide and
defeat its own purpose. Labels: "Superlatives", "PR Tables", "PR Evolution",
"Race Predictions".

**Markup:** `<nav class="records-jump" aria-label="Records sections">` containing
one `<button class="records-jump__link">` per section (see landmine below for
why these are `<button>`, not `<a href="#...">`).

**Sticky placement:** `position: sticky;` The `top` offset **must be computed
at runtime from the live `.app-nav` element's rendered height**
(`document.querySelector('.app-nav').getBoundingClientRect().height`), set as
an inline `style.top`, and **recomputed on window resize** (the responsive
nav collapse at 640px changes the nav's rendered height between the desktop
link row and the mobile hamburger row — see landmine below). Do not hardcode
a pixel value in CSS.

**Narrow-width behavior:** horizontal scroll row, reusing the exact technique
already proven for `.splits-scroll` (`overflow-x: auto;
-webkit-overflow-scrolling: touch;`), never wraps to multiple lines (a
wrapping sticky bar would eat an unpredictable and growing amount of vertical
space).

**Active-section highlighting:** an `IntersectionObserver` watching each of
the 4 `<section>` elements. The currently-intersecting section's jump button
gets `aria-current="location"` (the correct ARIA APG token for an in-page
table-of-contents link, distinct from `aria-current="page"` which `nav.ts`
already uses for the top-level route nav) and the same visual treatment as
`.app-nav__link[aria-current="page"]` (`color: var(--accent); border-bottom:
2px solid var(--accent);`).

**Click behavior:** clicking a jump button calls
`section.scrollIntoView({ behavior: 'smooth', block: 'start' })` then moves
focus to the section's own heading (`tabIndex=-1` + `.focus()`), matching the
existing `highlightAndFocus` pattern in `list.ts`. Buttons, not real anchors.

> **Landmine — hash-router collision.** The SPA router (`router.ts`) parses
> `location.hash` on every change to resolve a route (`#/records`,
> `#/trends?tab=volume`, …). A real `<a href="#records-pr-tables">` would
> **rewrite `location.hash` to `#records-pr-tables`**, which the router would
> try to parse as an unknown route and could 404 or blank the view. Every
> in-page jump control this phase adds — the Records jump list (this
> section) and the evolution grid's expand-on-click (§ 3, though that one
> uses native `<details>` and has no hash risk) — **must never be a real
> `href="#..."` anchor**. Use `scrollIntoView()` from a `<button>` instead.
> This is exactly the class of defect ("looks correct, silently breaks
> navigation") this phase's risk profile is most exposed to — flag it in the
> manual checkpoint (§ 16).

> **Landmine — nav height is not a constant.** `.app-nav` has no fixed
> height in `styles.css`; it is sized by its tallest child (the 44px
> theme-toggle button plus `--space-md` padding top/bottom), and its DOM
> content changes shape at the 640px breakpoint (full link row vs. hamburger
> row) per the existing `@media (max-width: 640px)` rule. A jump list with a
> hardcoded `top: 64px` will either gap or overlap depending on viewport
> width and must not be written that way.

Each distance gets its own `<section class="card detail-section"
id="pr-table-{slug}">` (slugs: `400m`, `1k`, `1mile`, `5k`, `10k`, `half`,

**One combined config notice**, not eight: if `data/stats/age-grading.json`
is absent/empty because `birthDate`/`sex` are unset (D-13), render **one**
`.config-notice` block directly under the `#records-pr-tables` heading

above. Every table's Age-Grade column still renders (header + em-dash cells)
— the column is never removed, only its values are absent, per D-13's "the
phase passes with the config unfilled."

**Column set, in order** (7 columns, deliberately echoing the splits table's
7-column precedent, § DETAIL-04):

| # | Column | Align | Format |
|---|--------|-------|--------|
| 1 | Rank | right | `#1`–`#10` |
| 2 | Time | right | new `formatEffortDuration(sec)` (§ 14 — NOT `formatDurationHms`, which always shows a leading `0:` hour) |
| 3 | Pace | right | `formatPace` (existing, reused) |
| 4 | Age-Grade | right | one decimal + `%`, em-dash when absent; 1k rows append `*` and the section carries the interpolation footnote (§ 6) |

**Marathon empty state (D-05):** `rankings.marathon` has zero entries today.

Copywriting Contract — **no** "Clear all" button (that's list-filter-specific

## § 3 — PR evolution small-multiples grid (D-06)

**Grid, deterministic breakpoints** (not fuzzy `auto-fit` — pinned so the
manual checkpoint is a simple count):

```css
.pr-evolution-grid { display: grid; grid-template-columns: 1fr; gap: var(--space-lg); }
@media (min-width: 640px)  { .pr-evolution-grid { grid-template-columns: repeat(2, 1fr); } }
@media (min-width: 1000px) { .pr-evolution-grid { grid-template-columns: repeat(3, 1fr); } }
```

7 cards → 1 column below 640px, 2 columns 640–999px (rows of 2,2,2,1), 3
columns at ≥1000px (rows of 3,3,1). **Falsifiable check:** resize to each
band and count columns.

**Card anatomy** (`.pr-evolution-card`, a `.card`):
1. `<h3 class="text-heading">` distance name ("5K")
2. `<div class="text-display">` **the current PR value as text**, e.g. "19:39" — this is the concrete fix for the "charts aren't directly comparable" risk: a reader gets the number from text, never only from reading pixel position on an unlabeled axis.
3. `<div class="text-label">` step count, e.g. "6 steps, 2019–2024"
4. The chart (`.pr-evolution-card__canvas-wrap`, `height: 160px`, `112px` at ≤380px viewport — mirrors `.chart-band__canvas-wrap`'s existing responsive rule)
5. A native `<details class="pr-evolution-card__details">` disclosure, **not** a hand-rolled `aria-expanded` button — native `<details>`/`<summary>` gives keyboard support, the expand/collapse triangle, and toggle semantics for free, and needs no animation (instant native show/hide is intentional; animating a variable-row table height risks another invisible-until-resize defect on top of the two this project already shipped).
   - `<summary>` text: "Show progression ({n} steps)"
   - Inside: a `.pr-table`-styled table, columns **Date | Time | Improvement | Run**. "Improvement" is signed, e.g. "−0:03" (new PR is 3s faster), using the same `formatEffortDuration` delta convention. "Run" is the "View Activity" CTA.

**Chart contract, per card, independently (never shared across cards):**
- Type: `line`, `stepped: 'after'` (record holds until the moment it falls).
- `x`: linear scale, epoch-ms `.d` values, ascending; tick callback formats as year only (`new Date(v).getUTCFullYear()`), matching `detail-charts.ts`'s tick-callback convention (no `TimeScale`, no date-adapter dependency).
- `y`: linear scale, **`reverse: true`** (faster = smaller = visually higher = "the record improved"), auto-ranged **independently per card** — `min`/`max` are never pinned or shared across the 7 instances. Tick callback: `formatEffortDuration`.
- Color: a single, uniform series color for all 7 cards (reuse `--chart-pace`) — color carries no comparative meaning here (see the Color section's rationale), the heading and the big text-display number carry the identity.
- `aria-label` on each `<canvas>`: `"{Distance} PR evolution chart, time by date"`.

**MUST NOT:** copy `detail-charts.ts`'s cross-band shared-domain pattern here.
That pattern exists there because 4 bands share one x-axis *meaning*
(distance/time along the same run). These 7 cards share **neither** x domain
(different date ranges per distance) **nor** y domain (44 seconds to 87
minutes) — pinning a shared scale would actively misrepresent the data.

**Lifecycle:** Records is one scrolling page (not tabbed) — mount all 7
Chart.js instances synchronously once data resolves; `destroy()` all 7 in the
view's `unmount()`. No tab-switch churn to handle here (contrast § 7).

## § 4 — Superlative tiles and Race Predictions (D-01, D-10, D-11)

### § 4a — Superlatives

Reuses the Overview headline-stats pattern **exactly**: one `.card` titled
"Superlatives" containing a `.stat-grid` of `buildStatCard`-shaped tiles
(`.text-display` value + `.text-label` label) — zero new CSS.

Tile set (D-01 leaves this open; resolved here):
- Biggest Week — km + "week of {date}"
- Biggest Month — km + month/year
- Longest Streak — days + date range
- Current Streak — days + "active" or "ended {date}" sub-label

### § 4b — Race Predictions (Riegel)

Two `.pr-table`-styled HTML tables — **not charts**. A prediction matrix is
inherently tabular (7×7 pairs); rendering it as a chart would need a
categorical palette this phase deliberately avoids (see Color section).

**Table 1 — "Standard (b = 1.06)":** rows = the 6 distances with a recorded
PR (400m, 1k, 1mile, 5k, 10k, half — **not** marathon, which has no PR to
predict *from*), columns = all 7 distances (predict *to*, including
marathon). The diagonal cell (predicting a distance from itself) shows the
actual PR time, styled `<em>` "(actual)" rather than a duplicate prediction.
The marathon **column** is the only place a marathon time appears anywhere
in Records — directly above the table, one `.text-body` line states the
exact "No marathon has been run yet…" copy from the Copywriting Contract, so
a reader never mistakes a Riegel estimate for a recorded time.

**Table 2 — fitted exponent (D-11 self-suppression):** same shape, rendered
**only** when `fitRiegelExponent`'s distinct-activity guard passes (≥3
distinct source activities). Above the table: `.text-label` "Fitted
exponent: b = {value} (from {list of distances})" — names the distances
verbatim, per D-11. When the guard fails, render **no table at all**, only
the exact suppression copy from the Copywriting Contract, naming the current
count (e.g. "currently 1") so the state is self-explanatory rather than a
silent gap.

## § 5 — Detail-view PR badge and best-efforts panel (D-08)

**Header badge.** Named per-distance ("PR — 5K"), one badge per PR-setting
distance this run achieved, rendered directly under the activity `<h1>` name
(above or beside the date line). **Reuses the plain `.badge` class
unchanged** — no accent color, no special "celebratory" treatment. This is a
deliberate consistency decision: `list.ts:130` and `overview.ts:95` already
render PR information (`"{n} PR"`) with the plain neutral `.badge` look:
introducing a second, more decorated badge style for the *same underlying
fact* (this run set a PR) in a third location would fragment the vocabulary
the phase brief explicitly asked to keep coherent. Only the **text** differs
by context ("2 PR" vs "PR — 5K"), never the visual weight.

`appendBadge` (currently a private, unexported helper in `list.ts`) should be
**exported** so `detail.ts` reuses it rather than duplicating a 5-line DOM
builder — the same single-source discipline already applied to
`formatActivityDate`/`formatPace`.

**Best-efforts panel.** New `<section class="card detail-section">` titled
"Best Efforts This Run", positioned **after** Splits/Breakdown and **before**
the closing "Back to Activities" CTA (supplementary content, not
headline — it doesn't block understanding pace/HR/route if it loads last).

Table (`.pr-table` reused): one row per distance this run produced **any**
effort for — not only PR-setting ones (D-08: "every effort this run produced
across all seven distances"). Columns: **Distance | Time | Pace | Age-Grade |
PR?**. PR-setting rows get a **permanent** highlight, a new modifier
`.pr-table__row--pr` using the identical `color-mix(in srgb, var(--accent)
15%, transparent)` formula as `.activity-table__row--highlight` but
**without** the 1.5s transition — that transition means "you just navigated
here," which is the wrong signal for a state that should look highlighted on
every visit, not just the first.

Empty case: a run with zero qualifying efforts at any distance (too short or
below the shortest effort threshold) renders the exact empty-state copy from
the Copywriting Contract rather than omitting the section.

## § 7 — Trends tab bar (D-02/D-03)

**ARIA pattern: real tablist**, not the `.segmented` group-of-toggle-buttons
pattern used elsewhere in this codebase (detail's x-axis toggle uses
`role="group"` + `aria-pressed`, which is correct for an independent toggle
but **wrong** for 5 mutually-exclusive views — this phase's tab bar needs
`role="tablist"` / `role="tab"` / `aria-selected` / `role="tabpanel"`).

**Visual treatment: reuse `.segmented`/`.segmented__option`/
`.segmented__option--active` verbatim** — no new CSS classes for the tab bar
itself. Only the ARIA attributes in the DOM differ from the existing x-axis
toggle; the pixels are identical, which keeps the two controls visually
consistent as "the same kind of thing" without inventing a second look.

```html
<div role="tablist" aria-label="Trends views" class="segmented">
  <button role="tab" id="tab-volume" aria-selected="true" aria-controls="tabpanel-volume"
          tabindex="0" class="segmented__option segmented__option--active">Volume</button>
  <button role="tab" id="tab-yoy" aria-selected="false" aria-controls="tabpanel-yoy"
          tabindex="-1" class="segmented__option">Year-over-Year</button>
  <!-- …cadence-hr, training-load, gear -->
</div>
```

**Keyboard model — roving tabindex, automatic activation** (WAI-ARIA APG
tablist pattern): only the active tab has `tabindex="0"`; Left/Right arrow
moves focus **and** activates the newly-focused tab immediately (matches how
a segmented control already behaves); Home/End jump to first/last tab.
Hand-wired — no library.

**5 persistent tabpanels**, not a rebuild-per-switch DOM shell: each
`<div role="tabpanel" id="tabpanel-{key}" aria-labelledby="tab-{key}"
tabindex="0">` exists from mount, inactive ones get the `hidden` attribute.
Chart.js instances inside a hidden panel are still **destroyed** on tab
switch (see below) — only the DOM shell persists, not the charts.

**Loading state:** before a tab's chart module resolves, its tabpanel shows
the exact existing `.loading-indicator` pattern (`role="status"`, text
"Loading {tab name}…") — identical markup to `list.ts`/`overview.ts`'s
existing loading indicator, not a new spinner. Guarded by the same
`requestToken` increment-and-compare pattern `detail.ts` already uses, so a
fast tab-to-tab switch never paints a superseded tab's content into the
wrong panel.

**Chart lifecycle across tab switches: destroy-and-rebuild** (RESEARCH
Pattern 2, option (a) — the lower-risk default). Every tab's Chart.js
instance(s) are destroyed when its tab is switched away from and rebuilt
when switched back to. This is the same discipline `detail-charts.ts`
already uses for every state change; keeping a hidden chart alive risks the
`chartArea` mis-measurement Chart.js is documented to have behind
`display:none` ancestors — a defect class this phase's risk profile does not
need to add.

**Query-string state:** `?tab=volume|yoy|cadence-hr|training-load|gear`,
allow-listed with default `volume` on any unrecognized value — mirrors
`list-logic.ts`'s `SORT_KEYS` allow-list pattern exactly (a new
`TREND_TAB_KEYS` constant in the trends logic module).

## § 8 — Volume tab (D-04)

**One chart, not two.** A single volume chart plus a `.segmented`
3-way granularity toggle ("Weekly" / "Monthly" / "Yearly", D-03's
"volume gets a weekly/monthly/yearly granularity toggle") swaps the chart's
underlying dataset — this keeps the tab to one live Chart.js instance
instead of three permanently-mounted ones, and matches D-03's "each tab owns
its own controls" framing more literally than three always-visible charts
would. `aria-label` changes with the granularity: "Weekly distance chart" /
"Monthly distance chart" / "Yearly distance chart".

**Year consistency heatmap (D-04), CSS grid (RESEARCH's recommended
default — no new dependency):**

```css
.year-heatmap {
  display: grid;
  grid-template-columns: repeat(53, 1fr);
  grid-template-rows: repeat(7, 1fr);
  gap: 2px;
}
.year-heatmap__cell {
  aspect-ratio: 1;
  min-width: 10px;
  min-height: 10px;
  border-radius: 2px;
}
```

**Color scale extends the calendar view's existing tint scale**
(`.calendar-day--tint-1..4`) with one addition: `--tint-0` = **no visible
accent at all** (`background: var(--surface)`, not the lightest accent
tint). This is the D-15-style "absence is visible, never filled" rule
applied here: a genuine rest day must look visually **empty**, not a very
faint version of "some distance," or a rest day and a low-mileage day become
indistinguishable at a glance.

**Year selector:** a native `<select>` (matches the codebase's
native-control preference — same choice already made for the mobile sort
dropdown and both date-range presets), labeled "Year", defaulting to the
most recent year with any activity.

**Accessibility — the heatmap is the one place in this phase closest to a
real WCAG failure mode if built naively:** 371 individually-focusable grid
cells is a documented anti-pattern (a keyboard user would need 371 Tab
presses to cross it). Required treatment:
- Cells are **not** individually focusable or interactive; hover gets a
  native `title="{date}: {km} km"` for pointer users only.
- The grid container gets one `aria-label` summarizing the year total (e.g.
  "2024 training consistency: 187 active days, 1,240 km").
- A `<details>` disclosure directly below the grid, `<summary>` "View as
  table", contains the **same day-by-day data as a real HTML table** (date,
  km) — this is the accessible-equivalent content the heatmap itself cannot
  provide, not a decorative extra.

## § 10 — Cadence & HR tab (TREND-03, client-computed)

**Two stacked mini-charts, one axis-gutter width, not one dual-axis chart.**
Dual-axis charts are a known readability anti-pattern this codebase has
already deliberately avoided once (D-19's "no competing right-hand tick
labels" rule for detail overlays). Reapply the same discipline here: monthly
avg cadence and monthly avg HR render as two separate, vertically-stacked
single-axis charts sharing one x-axis (month), using the **exact same
`Y_AXIS_WIDTH_PX`-style pinned-gutter technique** `detail-charts.ts`
introduced to fix Phase 17's GAP 2 (misaligned chart-band x-axes). Reusing
this fix preemptively, rather than re-discovering the same defect, is a
mandatory reuse, not a suggestion.

**Missing-month handling:** a month with zero qualifying activities (e.g. no
HR-stream runs that month) is a **gap** in the line (`spanGaps: false`), not
a zero value and not an interpolated line — the same "absence visible, never
filled" principle from D-15, applied here to a new context.

`aria-label`s: "Average cadence by month chart" / "Average heart rate by
month chart".

## § 11 — Training load tab (TREND-04, D-14/D-15/D-16)

**Chart:** one canvas, three series — CTL (filled area, `--load-ctl`), ATL
(plain line, `--load-atl`), TSB (plain line or zero-centered area,
`--load-tsb`) — reusing `detail-charts.ts`'s `Filler`-based fill technique
for CTL exactly as it already fills detail overlays.

**Edwards/Banister toggle (D-14):** `.segmented` two-option control (reused
class; `role="group"` + `aria-pressed` is the **correct** ARIA pattern here,
unlike the outer 5-way Trends tabs in § 7 — this is a genuine exclusive
two-state toggle, not a tablist), labeled "TRIMP model", default "Edwards"
per D-14. Switching is a **pure client-side re-render**: the UI assumes
`data/stats/training-load.json` carries **both** an Edwards series and a
Banister series in one document, so the toggle never refetches — this is a
data-contract expectation the planner should lock into the compute step's
schema even though the exact field names are Claude's Discretion per
RESEARCH.

**Default window:** last 12 months, with a `.segmented` 3-way control
("3mo" / "12mo" / "All") to widen — the underlying series always covers the
full archive (D-16); only the displayed window is scoped.

**Thin-HR-coverage shading (D-15):** a **local Chart.js plugin** (`afterDraw`
hook), the exact same technique `detail-charts.ts`'s crosshair plugin
already uses (registered per-chart-instance, not via `Chart.register`, no
npm dependency). Draws a **flat, low-opacity rectangle**
(`rgba(--text-secondary, 0.08)`) across x-ranges where the underlying data
marks a no-HR gap — a flat fill, not a diagonal hatch pattern, because a flat
rectangle is trivially verifiable in a screenshot and a hand-rolled hatch
pattern is one more hand-rolled canvas primitive this phase doesn't need to
risk getting subtly wrong. Directly below the chart, a `.text-label` caption
states the exact copy from the Copywriting Contract — the shading and the
words say the same thing twice, deliberately, since this is the phase's
single most load-bearing honesty requirement (the user's own verbatim
constraint).

**Missing-config notice (D-13):** if `birthDate`/`sex`/`restingHr` are
unset, Banister's toggle option is **disabled** (not hidden — the option
still exists so the user knows the model exists) and a `.config-notice`
renders the exact copy from the Copywriting Contract. Edwards stays fully
functional (D-14: "its only input is the five bpm boundaries already in
`athlete.json`").

`aria-label`: "Training load chart: CTL, ATL, and TSB over time".

## § 12 — Gear tab (TREND-05, D-17/D-18/D-19)

**Primary content: a sortable HTML table**, reusing `list.ts`'s
click-to-sort column-header pattern (`buildHeaderRow`'s shape, applied to a
tiny ≤17-row dataset — genuinely full reuse, not a re-derivation). Columns:
**Shoe | Distance | Runs | Avg Pace | Avg HR | Date Range | Coverage %**.

An **"Unknown" row always renders** when its count is > 0 (D-18) — no special
styling beyond the literal label "Unknown"; the row's mere presence, not a
color, is what makes the absence honest.

**Blank shoe-name fallback (D-19 leaves the exact fallback open — resolved
here):** all 16 shoe names are currently empty strings, and 17-D32/33
forbids ever rendering a raw `gear_id`. Fallback label: a **stable,
build-time-assigned anonymous ordinal**, `"Shoe 1"`…`"Shoe 16"`, ordered by
each shoe's first-use date. This satisfies "must work anyway" without ever
exposing an id, is deterministic, and is trivially unit-testable (pure
sort-and-number logic, no DOM). Once real names are filled into
`data/config/gear.json`, the ordinal is superseded automatically (the table
prefers `name` when non-empty).

**Secondary content: a bar chart**, one bar per shoe, height = total
distance, using `--cat-1..8` capped to the **top 8 shoes by distance**, plus
one merged **"Other ({m} shoes)"** bar in a neutral gray
(`var(--text-secondary)` at low opacity — deliberately outside the 8-color
budget, since "Other" is not itself a category). Caption below the chart:
"Top 8 shoes shown by distance; see the table below for all {n}." This is
the concrete, honest resolution to "what happens past ~8 categories" — the
full data is never hidden, only the chart's legend is bounded.

`aria-label`: "Total distance by shoe chart, top 8 shown".

## § 14 — Chart theming contract

**Extract, don't duplicate.** `detail-charts.ts` already contains
`resolveToken`, `resolveChannelPalette`, `resolveThemeColors`, and
`hexToRgba` — all four should move into a new shared module,
`src/dashboard/views/chart-theme.ts`, imported by **both**
`detail-charts.ts` and this phase's `records-charts.ts`/`trends-charts.ts`.
Every new chart in this phase resolves color via the same live-CSS-custom-
property mechanism `detail-charts.ts` proved, not a hardcoded light/dark
literal table (the pattern the *widget* system's `comparison-chart` /
`streak-widget` configs use, which is correct for Shadow-DOM widgets that
lack access to the dashboard's `data-theme` attribute, but would be a
regression here, where that access exists).

**Duration/percentage axis formatting is `ticks.callback` on a `'linear'`
scale, always** — never a `TimeScale`/date-adapter dependency (RESEARCH's
explicit, repeated finding: zero precedent for `TimeScale` in this codebase,
and no such dependency is installed). This is the single most likely spot
for an unfamiliar pattern to creep in; restating it as a hard requirement.

**New shared formatter needed:** `formatEffortDuration(sec: number): string`
— alongside `formatPace`/`formatActivityDate`/`formatDurationHms` in
`list.ts` (the established single-source-of-truth location). Unlike
`formatDurationHms`, it **omits the hour component when zero**
(`formatDurationHms(1179)` → `"0:19:39"`, wrong for a 5K PR; the new
formatter → `"19:39"`). Used by: PR tables (§ 2), evolution grid + its
progression tables (§ 3), Riegel matrix (§ 4b), best-efforts panel (§ 5).

**`.pr-table__row--pr`** (§ 5): identical `color-mix(in srgb, var(--accent)
15%, transparent)` background formula as `.activity-table__row--highlight`,
**without** its 1.5s `transition` — a permanent state marker, not a
"you-just-arrived" flash.

**Every new `<canvas>` gets an explicit `aria-label`** — the full list is
enumerated per-section above (§ 3, § 8, § 9, § 10, § 11, § 12); no chart in
this phase ships without one.

## § 16 — Accessibility baseline

- **Color contrast:** all pre-existing tokens (`--text` on `--bg`/`--surface`)
  are unchanged and were already established in Phases 16–17 — not
  re-litigated here. The **new** tokens (`--cat-1..8`, `--load-tsb`) are
  theme-invariant (declared once), so they must be manually checked for ≥3:1
  non-text contrast (WCAG 1.4.11, graphical objects) against **both**
  `--bg`/`--surface` pairs (light `#fff`/`#f5f5f7`, dark `#1a1a2e`/`#242444`)
  — flagged as a required item in the manual checkpoint below, since there is
  no automated canvas-contrast check available in this repo (no jsdom, no
  headless browser).
- **Tablist keyboard model (§ 7):** roving `tabindex`, automatic activation
  on Left/Right, Home/End jump to first/last. Distinct from the `.segmented`
  group-toggle pattern reused elsewhere in this phase (§ 8, § 11), which
  correctly keeps `role="group"`/`aria-pressed`.
- **Focus visibility:** the existing global `:focus-visible` rule
  (`outline: 2px solid var(--accent); outline-offset: 2px;`) applies
  automatically to every new interactive element in this phase **provided**
  they are real native interactive elements — `<button>`, `<summary>`,
  `<select>` — never a styled `<div>` with a click handler. This is a MUST,
  not a preference: the jump-list buttons (§ 1) and the evolution grid's
  disclosure (§ 3) both rely on this.
- **Accessible chart names:** every `<canvas>` gets an explicit `aria-label`
  — full inventory in § 14.
- **Tooltip-only information reachable without hover:** three concrete
  instances close this gap in this phase — the low-confidence badge's
  `sr-only` description (§ 6), the thin-HR-coverage caption text alongside
  the shading (§ 11), and the year heatmap's "View as table" disclosure
  (§ 8). None of these facts exist *only* inside a Chart.js tooltip or a
  native `title` attribute.

Create `src/dashboard/views/calendar.ts` exporting
`export function createCalendarView(deps: { indexClient: IndexClient }): DashboardView`.

Copy the mount skeleton from `list.ts` verbatim in shape: track `mountedContainer`, call
`ctx.container.replaceChildren()`, show a `.loading-indicator` with `role="status"` reading
`Loading calendar…`, `await indexClient.loadIndex()` inside a try/catch, and guard with
`mountedContainer !== ctx.container` after BOTH the catch and the success path (WR-01). On failure
render the same `.error-state` shape with the heading `Couldn't load the calendar` and body
`Check your connection and try again.` Use the SHARED `indexClient` passed in by the registry —
never construct a second `IndexClient` (17-RESEARCH.md Anti-Patterns: the index is 1.22 MB and
memoized once per session).

Resolve the month with `parseMonthParam(ctx.query.get('month'), new Date())`. Construct `new Date()`
here at the call site and pass it in; `parseMonthParam` itself stays deterministic.

Render, in order:
- `<h1 class="text-heading" tabindex="-1">` reading `Calendar`, focused programmatically after mount
  (17-UI-SPEC § 5 focus management).
- A `.calendar-header` containing: the month total as `<div class="text-display">` reading
  `{km} km` to one decimal, a `<div class="text-label">` caption reading `across {n} runs`, a
  `.calendar-nav` with a `‹ {previous month name}` button and a `{next month name} ›` button (both
  VISIBLE TEXT, not icon-only), and a `.calendar-jump` `<input type="month">` labelled
  `Jump to month`. Previous/next month names come from `monthLabel(shiftMonth(month, ±1))` with the
  year stripped when it matches the current month's year, or kept when it differs.
- A `.calendar-grid` with seven `.calendar-weekday` header cells (`Sun` through `Sat`; the CSS from
  plan 17-01 abbreviates them below ~400px) followed by the day cells from
  `buildMonthGrid(indexClient.getRows(), month).weeks` flattened in row-major order.
- Every day position renders a real `<button class="calendar-day">` for a consistent Tab order.
  A `null` grid position renders `.calendar-day--outside` with no content and `aria-hidden="true"`.
  A rest day (`runCount === 0`) renders `.calendar-day--rest` with the day number, a plain `–` in
  the distance slot, `aria-disabled="true"`, and no click handler. An active day renders the day
  number top-left (`.calendar-day__number`, Label typography), the day's total in
  `.calendar-day__distance` (Heading typography — D-14 requires it be readable without hover, since
  there is no hover on mobile), and, only when `runCount > 1`, a `.calendar-day__count` reading
  `×{n}` (Label typography).
- Tint: apply `.calendar-day--tint-{tintStep}` for steps 1 through 4; step 0 (rest) gets no tint
  class. Never override the text colour per tint step (17-UI-SPEC contrast directive).
- Each active cell gets an `aria-label` combining the full date, the total distance, and the run
  count, so the visual grid is comprehensible to assistive tech.

All navigation goes through `navigateTo(ROUTES.CALENDAR, new URLSearchParams({ month: formatMonthParam(next) }))`.
Never write `location.hash` directly and never mutate the grid DOM in place — the router re-mounts
the view, which re-reads the month from the URL. This is what makes `#/calendar?month=YYYY-MM`
bookmarkable (D-13).

The calendar must NOT read, import, or react to any list filter state (D-16): a filtered month grid
would show gaps that read as missed training. This module must not import anything from
`list-logic.ts`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Hash `?month=` parameter → grid construction | Attacker-controllable via a crafted or shared link |
| Athlete-authored `row.name` → multi-run picker rows | Untrusted free text, rendered through the shared card renderer |
| `activityIds` from the index → detail navigation | Values become `#/activity/{id}` hrefs |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17-URL-04 | Tampering | `?month=` driving the grid | mitigate | Consumed only through `parseMonthParam`, which allow-lists `/^\d{4}-\d{2}$/` with a 1–12 month range and a 1900–2999 year range and falls back to the current month (plan 17-03, unit-tested); no query value ever sizes a loop |
| T-17-VW-01 | Tampering (XSS) | Multi-run picker rows and day-cell `aria-label`s | mitigate | Picker rows are built by the existing `renderActivityRow`, which already writes `row.name` with `textContent`; `aria-label`s are set via `setAttribute`. Zero `innerHTML` in `calendar.ts` (asserted by grep) |
| T-17-VW-04 | Denial of Service (feature) | Stale render after fast month navigation | mitigate | The `mountedContainer !== ctx.container` guard is applied after both the catch and the success path, and the picker panel is cleared in `unmount()` (WR-01 lineage) |
| T-17-CAL-03 | Tampering | An `activityId` unknown to the index | mitigate | The picker looks each id up via `indexClient.getRow(id)` and skips a miss rather than rendering a broken row or throwing; the detail route's own `isValidActivityId` chokepoint still gates any fetch |
| T-17-REG-01 | Repudiation | Calendar silently reverting to a stub | mitigate | A Node-environment regression test asserts `STUB_PHASE` has no `ROUTES.CALENDAR` key while the two Phase 18 stubs still do |
| T-17-SC | Tampering | npm/pip/cargo installs | accept | No packages installed this phase (17-RESEARCH.md § Package Legitimacy Audit) |
</threat_model>

<objective>
Close two findings from `27-REVIEW.md`.

**G-04 (Critical).** `qualityBadgeSpecs` in `src/dashboard/views/list.ts` destructures
`const { decimation, gapProfile, impossibleSamples } = row.quality;` with no guard. It is reached
unconditionally from `activityRowAriaLabel` and `appendQualityBadges`, both called from every
row-render loop (`buildTableRow` and `renderActivityRow`) with no per-row try/catch, and is reused
by `overview.ts`. A row without `quality` therefore takes down the ENTIRE Activities list and
Overview render, not just one row.

Reproduced directly against the built bundle:
`TypeError: Cannot destructure property 'decimation' of 'row.quality' as it is undefined.`

This is not hypothetical. `dashboard-index.types.ts`'s own `ParsedDashboardIndexRow` doc comment
states "no key can be assumed present" — serialization plus re-parse does not carry the producer's
required-key guarantee. The compiler misses it because `qualityBadgeSpecs` is typed
`Pick<DashboardIndexRow, 'quality'>` (required) while the runtime value is a parsed row. A browser
holding a cached pre-Phase-27 `index.json` hits exactly this, and stale-cached `index.json` is a
recurring hazard in this project's own checkpoint history.

Three sibling call sites touched by this same phase already guard correctly and are the reference
for the fix: `list-logic.ts`'s `rowIsAnySevere` (`row.quality?.anySevere === true`), `detail.ts`
(`indexClient.getRow(detail.id)?.quality ?? null`), and `list.ts`'s own `rowPaceDisagreement`
(`row.paceDisagreement ?? null`).

**G-05 (Warning, WR-01 in the review).** `detail-sections.ts`'s `tieringExplanation` reads from
`EXPLANATION_PROBE_SPECS` and ends `?? ''`. The existing drift test catches a total failure only
through an accidental `''`-vs-`undefined` asymmetry rather than a direct assertion, and the probe
row object is hand-duplicated between production and test source. This sits in the surface ROADMAP
Criterion 3 ("badges explain, not just mark") depends on.
</objective>

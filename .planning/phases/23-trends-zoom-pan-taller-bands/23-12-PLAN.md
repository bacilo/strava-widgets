(Volume / Year-over-Year / Cadence & HR / Training Load / Gear), measured at width **412px**,

**Why 412 is a floor, not a coincidence.** `.segmented` is `display: inline-flex` with no
`flex-wrap`, so its shrink-to-fit width cannot go below its min-content contribution — the sum of
its five buttons' min-content widths. Round 2 measured the strip at `412` at an available width of
294 (viewport 390) and again at 334 (viewport 430): two data points, same number, so 412 IS the
min-content floor and the strip cannot reflow below it by construction. This is structurally the
same situation `.year-heatmap`'s 634px grid floor presented to R15, and it gets the same shipped
answer.

**Why the left offset is 48.** `index.html` has `<main id="app" class="view">` and `trends.ts`'s
`load()` creates a second `view.className = 'view'` div inside it. `.view` declares
`padding: var(--space-lg)` (24px), so the content inset is 24 + 24 = 48px each side and the usable
content width is `viewport − 96`: 294 / 297 / 316 / 334 at 390 / 393 / 412 / 430. R35(d) measured
`.year-heatmap-scroll` `clientWidth` at exactly `294`, `297`, `316`, `334` — the arithmetic is
confirmed by measurement, not asserted. `48 + 412 = 460` is precisely the `documentElement.scrollWidth`
R35(b) recorded at every width.

**Chosen approach: a scroll wrapper (`.trends-tablist-scroll`), the third instance of the shipped
`.splits-scroll` pattern.** Reasoning, with the rejected alternatives:

- **18-UI-SPEC § 7 holds.** § 7 requires the tab bar to reuse `.segmented` / `.segmented__option` /
  `.segmented__option--active` verbatim with "no new CSS classes for the tab bar itself". The
  wrapper is an ANCESTOR element; the bar's own class list, ARIA attributes and pixels are
  byte-unchanged, so § 7's constraint is satisfied rather than bent.
- **Keyboard behaviour improves rather than regresses.** § 7's roving-tabindex model gives the strip
  exactly ONE Tab stop (only the active tab has `tabIndex = 0`), and `switchTab(tab, true)` calls
  `nextButton.focus()`, so the browser's own scroll-into-view carries an off-screen tab into view on
  ArrowRight/ArrowLeft/Home/End. This is the direct answer to the objection `styles.css`'s calendar
  block records against a scroll wrapper ("focusable day buttons + a scroll container scroll-jumps
  focus on Tab") — the calendar has 28-31 Tab stops inside its container; the tablist has one.
- **Rejected A — `flex-wrap: wrap` on the five-tab strip.** `.segmented__option:first-child` and
  `:last-child` (specificity `0,1,1`) are what draw the joined-pill end caps, and
  `.segmented__option { border-radius: 0 }` squares everything else. On a wrapped second row the
  `:last-child` of row one is visually a row END with square corners and the `:first-child` of row
  two likewise — reintroducing exactly the notched-join defect class 19-REVIEW's CR-02 recorded and
  fixed. It would also need a new Trends-scoped selector, and `.segmented` is shared by seven live
  instances (this tablist, the granularity group, the load-window group, the TRIMP model group,
  `records.ts`'s scope toggle, `detail-charts.ts`'s x-axis toggle, `calendar.ts`'s week-start
  toggle).
- **Rejected B — shrink tab padding/font below 430px.** Arithmetic: `.segmented__option` declares
  `padding: var(--space-xs) var(--space-md)`, so the five options contribute `5 × 2 × 16 = 160px` of

  re-runs the precise mistake D-21 exists to prevent: pinning a fix to a breakpoint instead of
  removing the structural cause.
- **Rejected C — `overflow-x: auto` directly on `.segmented`.** It would clip the two-tone

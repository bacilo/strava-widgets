Verified during planning against the live repository. Do not re-derive any of this; verify it still holds and move on.

**The defect, exactly.** `src/dashboard/styles.css` lines 55-57 read (line 56 is the offender):

```
  /* Phase 19 — radius scale, theme-invariant (identical in light and dark),
     so declared only here, following the --space-*/--zone-*/--load-*
     precedent rather than the --chart-* per-theme precedent. */
```

`--space-*/` contains `*/`, which terminates the comment. `--zone-*/` is then live `:root` content and is not a valid custom-property name, so CSS error recovery discards tokens up to the next `;` — which lands at the end of `--radius-control: 4px`. `--radius-panel: 8px` (the next declaration) survives untouched.

**esbuild is importable today.** `require('esbuild')` resolves to `node_modules/esbuild/lib/main.js` at **0.27.3**, present in `package-lock.json` with an integrity hash, pulled in by `vite@7.3.1`. `npm ls esbuild` reports exactly one copy.

**Measured discrimination (broken source vs. the same source with the comment repaired):**

| Signal | BROKEN | FIXED | Usable? |
|--------|--------|-------|---------|
| `esbuild.transformSync(css, {loader:'css', minify:true}).warnings.length` | `1` (`css-syntax-error`, `Expected ":"`, line 56 col 59) | `0` | **YES** |
| `:root` body split on `;`, anchored `/^--radius-control\s*:/` on a trimmed fragment | `false` | `true` | **YES** |
| Stripped source (first-`*/`-wins) still contains `*/` | `true` | `false` | **YES** |
| Substring `'--radius-control: 4px'` anywhere in `:root` body | `true` | `true` | **NO — this is the trap** |
| Count of `;`-separated fragments in the `:root` body | `39` | `39` | **NO — identical** |

The last two rows are the failure modes to avoid. In particular `--radius-control:` **is still present as a substring in esbuild's minified output even while syntactically swallowed** — a substring check against esbuild's output fails in precisely the way the original assertion failed. Only `warnings.length` and anchored declaration-name matching discriminate. A declaration **count** does not discriminate either, because the leaked prose merges into one fragment with the swallowed declaration.

**The repair that produces 0 warnings:** replace the prose `--space-*/--zone-*/--load-*` with a form containing no `*/`, e.g. `--space-*, --zone-*, --load-*`. Verified to yield `warnings.length === 0`.

**Radius literal inventory.** `grep -n "border-radius: 4px" src/dashboard/styles.css` returns 5 lines: 288, 480, 575, 654, **809**. Only 809 (`.segmented`) is in scope — it is the rule block plan 19-04 actively edited (WR-01). `grep -c "var(--radius-control)"` currently returns `4`.

**Gate-command hygiene — applies to every `<automated>` block in plans 19-06, 19-07 and 19-09.** A gate written as

```
A && B && npm run build-widgets 2>&1 | tee /tmp/x.log; ! grep -q 'css-syntax-error' /tmp/x.log
```

**reports the wrong thing.** Two independent defects compound:

1. The `;` discards everything before it. The command's exit status is decided **solely** by the grep negation, so a failing `A` or `B` is invisible to the gate.
2. Even without the `;`, the exit status of `cmd | tee f` is `tee`'s status, not `cmd`'s. A failing build piped into `tee` still looks like success.

Together they mean that when the build fails — or never runs at all because an earlier command failed — a log file left behind by a previous clean run still lacks the needle, and the gate exits 0. Verified during planning: `false && echo skip; ! grep -q css-syntax-error stale.log` exits **0** in both bash and zsh. That is a green gate that verified nothing, which is the exact defect class this whole gap-closure phase exists to eliminate. It must not survive in the gate script of the plan that closes it.

**The correct form, used verbatim in the tasks below:** delete the log first so a stale file cannot answer for a run that never happened; **redirect** rather than pipe so the build's own status is observable; capture that status into a variable immediately; `cat` the log for visibility; and require **both** the captured status and the grep negation. Verified in bash and zsh across four cases — upstream failure with a stale log present (exit 1), build failure (exit 1), clean run (exit 0), and clean run with the needle present (exit 1).

`PIPESTATUS` is deliberately **not** used. The developer's shell is zsh, where the array is spelled `pipestatus` and is 1-indexed; a bash-shaped `${PIPESTATUS[0]}` expands to the empty string there, which was confirmed during planning. Sidestep the trap rather than writing shell-specific code. Do not "simplify" these commands back to the `; ! grep` shape.
</groundwork>

<decision id="GD-01">
## Declare `esbuild` as an explicit devDependency

**Decision:** add `"esbuild": "^0.27.3"` to `devDependencies` in `package.json` and import it directly in `styles.test.ts`.

**This is not a new package install.** esbuild 0.27.3 is already in `package-lock.json` with a registry URL and an integrity hash, resolved as `vite`'s own dependency. Declaring it adds a reference, not a package. The plan asserts this: the lockfile diff must introduce **zero** new `node_modules/*` entries.

**Rationale:**
1. `19-VALIDATION.md`'s "no new test dependency" constraint prohibits a DOM/rendering environment — jsdom, happy-dom, `@testing-library/*`, puppeteer, playwright — being used as an escape hatch from the human checkpoint. esbuild supplies no DOM, no CSSOM and no rendering, and cannot discharge a single Manual-Only row. It supplies parse-validity, which is exactly the signal GAP 1 proved was missing. The substantive constraint is honored, not bent.
2. **This decision supersedes `19-RESEARCH.md` § Package Legitimacy Audit.** That section predicted, for this phase, "no new `package.json` dependency, no new `devDependency`". As of this plan that prediction is **inaccurate as written**: one `devDependency` is being declared. State it plainly rather than framing it as unchanged. What survives is the audit's substantive ground, not its stated premise: **zero packages are downloaded**, because esbuild@0.27.3 is already resolved in `package-lock.json` with a registry URL and an integrity hash as `vite`'s dependency, so no unaudited package enters the tree and the slopcheck/registry-verification protocol still has nothing to check. Keep the distinction exact in every document this touches — the count of packages *fetched* is unchanged at zero; the set of *declared* dependencies grows by one. Task 1 Step 6 amends `19-VALIDATION.md` so no document is left asserting the superseded form.
3. Depending on it *transitively* is the fragile option, not the safe one: Vite's announced Rolldown migration would remove esbuild from the tree, and the gate would vanish with a `MODULE_NOT_FOUND` at some future upgrade. A declared dependency turns a silent disappearance into an explicit contract.

**Rejected alternatives, with reasons:**
- *Use esbuild transitively without declaring it* — a load-bearing gate hanging off another package's private dependency. Fragile for the reason in (3), and it would dodge the documentation reconciliation rather than resolve it.
- *Guarded optional import that skips when esbuild is absent* — reintroduces a silently-skipping assertion, which is the exact false-green pattern this plan exists to repair.
- *Add jsdom/happy-dom for a real CSSOM* — prohibited by `19-VALIDATION.md`, and would invite treating computed styles as proof of rendering.

**Blocking condition.** If `npm install` adds **any** new entry to `package-lock.json` beyond the `devDependencies` reference itself, STOP and escalate rather than proceeding — an unexpected package entering the tree is a supply-chain event, not a lockfile detail.

**Redundancy requirement.** Because a dependency can still disappear, the two dependency-free assertions in Task 2 must independently catch GAP 1's class. Both were verified during planning to discriminate on their own. The esbuild gate is the broader net; it is not the only net.
</decision>

<groundwork>
Verified during planning. The mechanism is fully diagnosed; the executor's job is to apply and audit the fix, not to re-diagnose it.

**DOM at the failure site** (`src/dashboard/views/detail-charts.ts:253-281`):

```
root
├─ div.segmented            (role=group, "Chart x-axis")
│   ├─ button.segmented__option.segmented__option--active   "Distance"
│   └─ button.segmented__option                             "Time"
└─ div.chart-stack
    └─ div.chart-band → div.chart-band__canvas-wrap
```

**Why the ring loses, by CSS 2.1 Appendix E paint order inside the shared stacking context:**

- `.segmented` is `display: inline-flex` (styles.css:806-810), so both option buttons are inline-level, non-positioned descendants. They paint in **step 7, in tree order**. "Time" is the later sibling, so its opaque `background: var(--surface)` paints over the right-hand overflow of "Distance"'s `box-shadow`. That is the "to the right by 'Time'" half.
- `.chart-band__canvas-wrap` declares `position: relative` (styles.css:774-777) with no `z-index`, so it is a positioned descendant painting in **step 8** — above every step-7 sibling. That is the "hidden in the bottom by the first chart" half.

A `box-shadow` is painted as part of its own element's box, so no ring can escape this without the focused element being promoted in paint order. This is a different mechanism from the `overflow: hidden` clip that plan 19-04 removed, and 19-04's fix remains necessary and correct — do not revert it.

**Existing positioned / layered rules in `styles.css`** (the complete inventory, `grep -n "position:\|z-index"`):

| Line | Rule | Declaration | Relevance |
|------|------|-------------|-----------|
| 166 | app nav | `position: sticky` | no z-index; a focused control promoted above it is acceptable and desirable |
| 775 | `.chart-band__canvas-wrap` | `position: relative` | **the occluder** — z-index auto, step 8 |
| 861-865 | `.splits-table__km` | `position: sticky; z-index: 1` | ties with a promoted focused element at 1; tree order decides |
| 878 | `.pace-bar` | `position: relative` | contains the only two `position: absolute` descendants; not focusable |
| 890, 899 | `.pace-bar__tick`, `.pace-bar__fill` | `position: absolute` | resolve against `.pace-bar`, which is already relative — unaffected |
| 980 | `.sr-only` | `position: absolute` | 1×1, `clip-path: inset(50%)`; its containing block is visually irrelevant |
| 996-997 | `.records-jump` | `position: sticky; z-index: 10` | **deliberate top layer** — must stay above a focused control elsewhere on the page |
| 1085 | `.pr-evolution-card__canvas-wrap` | `position: relative` | same class of occluder as the chart wrap; the same fix covers it |

**Recommended fix:** add `position: relative` and `z-index: 1` to the existing bare `:focus-visible` rule at `styles.css:357-360`. A positive z-index makes the focused element a stacking context painted in step 9 — above step 7 siblings and above step-8 positioned neighbours — while `1` stays below `.records-jump`'s deliberate `10`. `position: relative` with no offsets does not move anything: relative positioning does not affect layout flow.

**What this fix does not do:** relative positioning is still clipped by ancestor `overflow`. Plan 19-04's `.splits-scroll` padding and `.segmented` de-clip remain load-bearing.

**No automated proof of the rendered outcome is possible.** `vitest` runs `environment: 'node'`; there is no CSSOM and no rendering engine, and this phase authorizes no DOM test dependency. The assertions below prove the declarations exist and that the layer ordering invariant holds. Row 6 of the human checkpoint (plan 19-09) is the only proof that the ring is actually visible. Do not attempt to manufacture a rendering assertion.
</groundwork>

<decision id="GD-02">
## Keep the `button` baseline unscoped; correct its comment (WR-02)

**Decision:** leave the bare `button { … }` rule exactly as it is, and rewrite the comment above it so its factual claim is true.

The comment currently asserts "nothing currently rendered changes shape or color". That is false for `<button>` elements carrying no class, which receive their first-ever CSS from this rule: their font moves from the UA button default to the inherited 16px `--font-stack`, they gain a 32px min-height floor they never had, and their corners move from native button chrome to `var(--radius-control)`.

**Why not scope the rule.** Scoping it away from class-less buttons would re-open, on real shipped controls, precisely the inherited-font and cursor gap that D-05 created the baseline to close. The rule reaching those buttons is the intended behaviour; the comment is the defect.

**Why not give the buttons classes.** That would edit `calendar.ts` (and possibly `trends.ts`), directly contradicting D-05's "do not refactor the 31 `createElement('button')` sites", and widening Phase 19's file surface beyond the two files it has shipped all phase — for no verification benefit, since the rendered result would be identical.

**Establish the true list before writing the comment.** WR-02 names three sites (`calendar.ts:74` picker Close, `calendar.ts:257` and `:265` month-nav prev/next). A wider scan during planning, using a 12-line lookahead for a `className`/`classList` assignment on the same variable, surfaced four further candidates in `trends.ts` (lines 225, 815, 819, 882) whose class assignment appears to sit outside that window. The heuristic is not authoritative in either direction. The executor must resolve each of the seven candidates by reading the surrounding code and record the definitive list — this comment has already been wrong once, and a second wrong version is worse than none.
</decision>

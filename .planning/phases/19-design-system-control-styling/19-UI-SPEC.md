> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> This is a CSS-only phase: no new views, no new markup patterns, no new copy. Every decision below
> resolves a `19-CONTEXT.md` "Claude's Discretion" item into a concrete, checkable value, or restates a
> locked `D-NN` decision precisely enough for the planner/executor to implement without re-deriving it.
> There is no jsdom/headless browser in this repo — `styles.test.ts` text assertions guard against silent
> deletion only; the mandatory human browser checkpoint (success criterion 5) is the sole proof anything

| Token | Value | Usage |

**New non-spacing tokens this phase (radius, not spacing — D-13):**

| Token | Value | Replaces / normalizes |
|-------|-------|------------------------|
| `--radius-control` | `4px` | Names the value already used by `.filter-toggle`, `.pagination__button`, `.calendar-day`, `.segmented`, `.config-notice` (pre-phase) — no new number invented |

## Typography

Reused verbatim from `src/dashboard/styles.css` — **exactly 4 sizes, 2 weights, no additions** (unchanged since Phase 16).

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label | 14px | 400 | 1.5 |
| Heading | 20px | 600 | 1.2 |
| Display | 28px | 600 | 1.2 |

**Control typography contract (D-03, resolving how `font: inherit` behaves in practice):** the shared `input, select, textarea` baseline sets `font: inherit`, not a pinned size. This is deliberate — it means each of the 13 control-creation sites renders in whichever type role is contextually active at that DOM location (e.g. a search input inside `.list-toolbar` inherits whatever role its container declares). In every one of the 13 existing sites today, that resolved role is **Label (14px/400/1.5)** — every sibling control class already on those same sites (`.filter-toggle`, `.preset-chip`, `.sort-select`, `.calendar-jump`) is already pinned to 14px/400/1.5. Do not add a competing explicit `font-size` on the bare `input, select, textarea` rule; let inheritance do the work, and treat "resolves to Label everywhere today" as the checkable expectation at the human checkpoint, not as a rule to hard-code.

## Color

Reused verbatim from `src/dashboard/styles.css` — **no changes to the base semantic tokens, no new hue.** (18-UI-SPEC § 17 forbids a new spacing scale or 5th type role; this phase extends that discipline to color — no new token introduces a new hue, only new *formulas* referencing existing tokens.)

| Role | Light | Dark | Usage |
|------|-------|------|-------|
| Dominant (60%) `--bg` | `#ffffff` | `#1a1a2e` | Page background; **new this phase:** the fixed inner-halo color of the two-tone focus ring (D-09) |
| Secondary (30%) `--surface` | `#f5f5f7` | `#242444` | Cards, nav, chips; **new this phase:** default background of the shared control baseline (`input`/`select`/`textarea`) |
| Accent (10%) `--accent` | `#fc4c02` | `#ff6b35` | See "Accent reserved for" below — **unchanged list**, focus-ring outer ring is item 5, already on the list since Phase 16 |
| Text `--text` | `#333333` | `#e0e0e0` | Primary text; **new this phase:** the color mixed into the shared hover formula (D-06) |
| Text-secondary `--text-secondary` | `#666666` | `#a0a0b8` | Label-role text; **new this phase:** disabled-control text color (D-07) |
| Border `--border` | `#e5e5e5` | `#33334d` | Card/table borders; **new this phase:** default border of the shared control baseline |
| Destructive `--destructive` | `#dc2626` | `#f87171` | Reserved, **still not used in Phase 19** — no destructive UI actions in this phase's scope |

**Accent reserved for (unchanged from Phase 17 — nothing added, nothing removed):**
1. Active nav item indicator, theme toggle active icon, primary CTA
2. Loading indicator/spinner
3. Focus-visible outline ring (now the box-shadow ring's outer stop, D-09 — same reservation, new implementation)
4. Active sort-column direction arrow
5. Calendar distance tint scale, route-map polyline, pace-channel chart color

Do not use accent for control backgrounds, borders, disabled state, or hover state — the new formulas in this phase (D-06 hover, D-07 disabled) deliberately mix toward `--text`/`--text-secondary`, never `--accent`, to keep the reserved list exhaustive.

### NEW: Focus ring — two-tone box-shadow (D-09)

Replaces the existing `:focus-visible { outline: 2px solid var(--accent); outline-offset: 2px; }` rule **in place** (same location, `src/dashboard/styles.css` line ~332) — this is a modification, not an addition, and there is exactly one ring treatment globally (D-12: unscoped, so links and Phase 20's future clickable rows inherit it for free).

```css
:focus-visible {
  outline: none;
  box-shadow: 0 0 0 2px var(--bg), 0 0 0 4px var(--accent);
}
```

**`outline: none` is load-bearing, not cosmetic** — without it, browsers that supply a default UA focus outline (e.g. Chrome's native ring) will paint that outline *in addition to* the new box-shadow, producing a visible double ring. This is a concrete implementation risk worth calling out explicitly, not just an aesthetic nicety.

**Why this guarantees separation on any fill (including `--accent-strong`):** the inner 2px stop is always `--bg`, never the element's own background — so the ring is never accent-colored chrome sitting directly against an accent-colored fill. This is what turns UI-02's open-ended "meets non-text contrast requirements" into exactly two fixed, precomputed pairs (below) rather than one check per surface.

### NEW: Focus ring contrast computation (D-11 — discharges UI-02's contrast requirement)

Non-text contrast threshold: **3:1** (WCAG 2.1 SC 1.4.11). Computed via the standard WCAG relative-luminance formula, `--accent` against `--bg` (the ring's fixed neighbor in both themes, per the halo argument above):

| Theme | Ring color | Neighbor | Contrast ratio | Result |
|-------|-----------|----------|-----------------|--------|
| Light | `--accent` `#fc4c02` | `--bg` `#ffffff` | **3.40:1** | Clears 3:1, ~13% margin |
| Dark | `--accent` `#ff6b35` | `--bg` `#1a1a2e` | **6.02:1** | Clears 3:1 comfortably |

The light-theme margin is real but narrow (0.40 above the floor) — this is the pair to scrutinize first at the human checkpoint (tab through controls in light theme specifically and confirm the ring is clearly visible, not just technically passing). Do not add a contrast-computing helper to `styles.test.ts` (D-11's explicit choice — these two ratios are fixed by the token values above and change only if `--accent` or `--bg` themselves change, which is out of this phase's scope).

### NEW: Shared hover formula (D-06)

```css
color-mix(in srgb, var(--surface) 92%, var(--text))
```

Applies to the `button` baseline's `:hover` state (D-05) and, retrofitted, to `.activity-table tbody tr:hover` (D-08, replacing its current `color-mix(in srgb, var(--surface) 92%, black)`). Because `--text` flips per theme (`#333333` light / `#e0e0e0` dark), the mix darkens `--surface` in light and lightens it in dark — both correct directions. This also repairs `.cta:hover`, whose current rule (`background: var(--accent)`) is byte-identical to `.cta`'s own base declaration — the primary CTA has never had hover feedback until this phase.

**Row-hover retrofit is a correction, not a redesign (D-08):** the pre-phase formula mixes toward literal `black`, which over-darkens an already-dark `--surface` in dark theme. Light theme's rendered result is materially unchanged (`black` and `--text: #333333` mix to visually similar results at 8%). **Call this out explicitly at the human checkpoint** as a recorded, intentional deviation from "Activities visually unchanged" (success criterion 4) — the interaction model is untouched, only this one hover color is corrected.

### NEW: Disabled treatment (D-07)

```css
:disabled,
[aria-disabled="true"] {
  color: var(--text-secondary);
  opacity: 0.6;
  cursor: default;
}
```

Recommended values for CONTEXT.md's open discretion item: `opacity: 0.6` (not lower) — dims a control clearly below its enabled sibling while keeping its label legible enough to read *what* is disabled, which matters here specifically because two of the five live cases (pagination prev/next, calendar rest days) are disabled-but-still-informative, not disabled-and-irrelevant. `cursor: default` (not `not-allowed`) matches the existing `.calendar-day--rest` precedent already in the file.

Covers, without further changes needed at each site: pagination prev/next (`list.ts:491`, `list.ts:521`), the overlay-cap checkbox (`detail-charts.ts:340`), the Banister disabled toggle (`trends.ts:824`), calendar days (`calendar.ts:112` uses the `disabled` attribute, `calendar.ts:131` uses `aria-disabled` — both selectors are required, not redundant).

## Control Baseline Contract (UI-01 — D-01 through D-04)

**Attachment strategy:** bare element selectors, no `.control` class, zero TypeScript changes across the 9 view files / 13 control-creation sites (D-01). Any control added in Phases 20–25 (curation UI, week-start select, zoom controls) inherits this for free.

**Exact rule (resolves CONTEXT.md's "exact border, padding, background" discretion item):**

```css
input,
select,
textarea {
  border: 1px solid var(--border);
  background: var(--surface);
  color: var(--text);
  padding: var(--space-xs) var(--space-sm);
  border-radius: var(--radius-control);
  min-height: 32px;
  font: inherit;
}
```

- Border: `1px solid var(--border)` — matches the existing 1px/`--border` pattern already used by `.filter-toggle`, `.pagination__button`, `.calendar-day`, `.preset-chip`, `.chip`.
- Background: `var(--surface)` — the 30% secondary role, so inputs read as chrome sitting on the page, not as bare page background; consistent with every other control-like class in the file.
- Padding: `var(--space-xs) var(--space-sm)` (4px block / 8px inline) — enough horizontal breathing room for typed text without pushing height past the 32px min-height once combined with 14px line-height-1.5 text.
- Radius: `var(--radius-control)` (4px, new token) — matches the sibling button/chip classes already in the same toolbars.
- `min-height: 32px` — D-03, locked, aligns inputs with adjacent buttons in the Activities filter bar and Calendar header.
- `font: inherit` — D-03, locked; see Typography section above for what this resolves to in practice.

**Native chrome is explicitly out of scope (D-02, locked):** no `appearance: none`, no vendor pseudo-element rules (`::-webkit-calendar-picker-indicator`, `::-webkit-inner-spin-button`, `::-webkit-search-cancel-button`, etc.). `color-scheme: light`/`dark` is already declared per `[data-theme]` block, so native date pickers, number spinners, and the search clear-X already theme correctly at zero additional cost. Do not add these rules even if a native picker looks slightly inconsistent with the box around it — a half-restyled native picker is the documented worse outcome (CONTEXT.md Q2 notes).

**`type="button"` / `type="checkbox"` / `type="radio"` reset (resolves CONTEXT.md's `:not()`-vs-override discretion item):**

Recommendation: **a following override rule**, not `:not()` exclusions on the base selector.

```css
input[type="button"],
input[type="checkbox"],
input[type="radio"] {
  border: none;
  background: transparent;
  padding: 0;
  min-height: auto;
  width: auto;
}
```

Rationale: a `:not()` chain on the base selector grows harder to read every time a new `type` value needs excluding, and this codebase already has a precedent for "narrower rule wins by appearing later" (e.g. `.theme-toggle`/`.app-nav__toggle` override the general button treatment by specificity + position, not by `:not()`). An override rule is also easier to extend later (Phase 24's curation UI may add more checkbox/radio sites) without touching the base rule at all.

**Regression guard (D-04, locked):** extend `styles.test.ts` with assertions (via the existing `declarationsFor()` helper) that the `input, select, textarea` rule exists and declares `border`, `padding`, `background`, and `min-height`. This proves the rule was not silently deleted; it proves nothing about rendering — the human checkpoint remains the sole source of visual truth.

## Button Baseline Contract (UI-02 — D-05 through D-08)

**Depth: a quiet element baseline, not a `.btn` system (D-05, locked).** None of the 31 `createElement('button')` sites are refactored; none of the 12 existing button classes are renamed. This is the binding constraint that protects success criterion 4 (`list.ts` holds 22 of the 13 control + button sites and is the Phase 20 reference pattern).

```css
button {
  font: inherit;
  min-height: 32px;
  cursor: pointer;
  border-radius: var(--radius-control);
}

button:hover {
  background: color-mix(in srgb, var(--surface) 92%, var(--text));
}

:disabled,
[aria-disabled="true"] {
  color: var(--text-secondary);
  opacity: 0.6;
  cursor: default;
}
```

The 12 existing treatments below keep overriding this baseline wherever they already declare a property (lower specificity than every existing class selector, so nothing currently rendered changes shape or color — only the previously-undeclared gaps close):

`.cta`, `.filter-toggle`, `.preset-chip`, `.pagination__button`, `.segmented__option`, `.chip__remove`, `.chip-clear-all`, `.records-jump__link`, `.activity-table__sort-button`, `.calendar-day`, `.theme-toggle`, `.app-nav__toggle`.

**What this closes, concretely:**
- Inherited font (currently every button uses the OS UI font, not `--font-stack`, except where a class explicitly sets `font-size`/`font-weight`/`line-height` — none set `font-family`).
- Missing `cursor: pointer` on any button class that omits it.
- The dead `.cta:hover` bug (D-06) — `.cta` did not previously have a `button:hover` ancestor rule to inherit from; it gets real hover feedback for the first time.
- Five live disabled states rendering identically to enabled controls today (D-07) — see Color § Disabled treatment above for the exhaustive list of five sites.

**`.activity-table tbody tr:hover` retrofit (D-08, locked):** update its existing rule to the same `color-mix(in srgb, var(--surface) 92%, var(--text))` formula, replacing the current `black`-mix. See Color § Shared hover formula above for the full rationale and the required human-checkpoint call-out.

## Focus Ring Contract (UI-02 — D-09 through D-12)

See Color § "NEW: Focus ring" and "NEW: Focus ring contrast computation" above for the ring formula and the two precomputed contrast ratios. This section covers the container-clipping fix and the inheritance contract.

**Clipping fix — containers, not a second ring variant (D-10, locked):** an ancestor's `overflow` clips `box-shadow` exactly as it clipped `outline`, so the new ring alone does not survive `.segmented`'s `overflow: hidden` or the two horizontal scrollers.

1. **`.segmented`:** remove `overflow: hidden` (it existed only to clip children into rounded corners); move the corner radii onto the end children instead:
   ```css
   .segmented {
     /* overflow: hidden;  <- removed */
   }

   .segmented__option:first-child {
     border-radius: var(--radius-control) 0 0 var(--radius-control);
   }

   .segmented__option:last-child {
     border-radius: 0 var(--radius-control) var(--radius-control) 0;
   }
   ```
   This is CSS-only — no `detail-charts.ts` markup change required (the x-axis toggle is currently the only `.segmented` instance).

2. **`.records-jump`:** already has `padding: var(--space-sm)` (8px), which already exceeds the 4px the ring needs to paint unclipped inside the scroll box. **No change required here** — noted explicitly so the executor doesn't add redundant padding while implementing D-10's general instruction.

3. **`.splits-scroll`:** currently has **zero** padding (`overflow-x: auto; -webkit-overflow-scrolling: touch;` only). Add `padding: var(--space-xs)` (4px) so a focused element at either scroll edge (there are currently none focusable inside this specific wrapper, but the guard should exist for consistency and any future addition) has room for the ring to render unclipped.

**Inheritance contract (D-12, locked):** `:focus-visible` stays global and unscoped — no per-component opt-in. Links (`.app-nav__link`, `.cta`, `.detail-nav`) and any future interactive element (including Phase 20's clickable activity rows) inherit the ring automatically. Phase 20 may refine ring *placement* on full-width rows if the two-tone ring reads badly against a full-row hover background, but it does not need to add a new ring rule to get one.

**Overview gets the shared treatment and nothing else (D-14, locked):** `overview.ts` has zero form controls, so this phase's entire stake in Overview is whatever the shared card/spacing rules above cascade onto it automatically — no markup changes, no hierarchy fixes to the stacked-div PR rows (that's Phase 21).

<interfaces>
Real nav markup built by `src/dashboard/nav.ts` (class names copied verbatim, not invented):
`#app-nav-root` > `ul.app-nav__links` > `li` > `a.app-nav__link`.

Script-ordering fact verified in 29-RESEARCH.md § Architecture Pattern 2: `injectOverlayTag` inserts
the overlay as a CLASSIC script immediately before `</body>`, after `main.ts`'s DEFERRED module
script in source order. The classic script therefore executes first and registers listeners; the
deferred module script then runs `createNav(document.getElementById('app-nav-root')!)` synchronously
at module scope; `DOMContentLoaded` fires after both. A `DOMContentLoaded` listener registered by the
overlay is therefore guaranteed to see a mounted nav — no polling, no `MutationObserver` (which D-03
rejected for the panel seam for the same reasons).
</interfaces>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| curate overlay → published dashboard DOM | The overlay appends to the live nav; it must never throw into the dashboard's own event loop or become a second renderer |
| queue client source → the curate write API | The only sanctioned path is the imported transport; any direct `/__curate/...` fetch is a parallel write surface |
| curate-only source → the publish pipeline | No Vite/tsconfig/build-widgets input may reference the queue directory or its bundle output |

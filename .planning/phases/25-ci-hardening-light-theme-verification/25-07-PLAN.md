Why D-04 exists (`src/dashboard/theme.ts`): `readStoredMode` reads the persisted mode key BEFORE
consulting `prefers-color-scheme`. A browser profile whose in-page theme control has EVER been
touched ignores the OS setting entirely — and such a row looks identical to a passing one. The
key is `THEME_STORAGE_KEY = 'dashboard-theme'` (`theme.ts:30`).

Why D-05 exists (`src/dashboard/styles.css`):
  :18   light theme  --bg: #ffffff
  :105  dark theme   --bg: #1a1a2e
On a LIGHT OS a white first paint IS the correct final state, so the first-paint row cannot
discriminate a working pre-paint theme from a broken one. On a DARK OS a white first frame is an
unambiguous failure and #1a1a2e is an unambiguous pass. Legibility stays on light OS;
live-follow spans both.

Live-follow mechanism (`theme.ts:167`): a `matchMedia('(prefers-color-scheme: dark)')` change
listener updates the effective theme without a reload — but ONLY while mode is `'auto'`, which
requires cleared storage per D-04.

The pin landed in plan 25-05 (`src/dashboard/theme-bootstrap-parity.test.ts`) proves the inline
bootstrap and `theme.ts` agree at unit level. It does NOT prove anything about a real browser,
a real OS setting, or first paint. Do not treat it as substituting for any row here.

Precedent to mirror in structure and discipline — `.planning/phases/24-local-curation-mode/24-VALIDATION.md`
§ "Round 4 Checkpoint (R32-R35)": each row states its own discriminator, proves the discriminator
is REACHABLE before the row is presented, quotes an independently-derived value rather than the
UI agreeing with itself, and R34 is a human-hand row for the gesture automation cannot perform.

Verdict vocabulary established in Phase 20 and used since: PASS / FAIL / BLOCKED / NOT
EXERCISABLE. BLOCKED means the evidence offered was not the evidence the row required — it is
not a softer PASS.

Documented stale-cache trap in this repo: a cached `index.html` has produced false evidence

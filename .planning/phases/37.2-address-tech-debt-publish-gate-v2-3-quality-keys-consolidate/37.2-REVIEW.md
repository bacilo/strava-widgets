## Warnings

### WR-01: "exact epoch before the near rule" test passes under near-first ordering (vacuous ordering guard)

**File:** `src/exports/consolidate.test.ts:204-211` (code under test: `src/exports/consolidate.ts:226-243`)
**Issue:** The fixture is export rows `[{222, D2}, {888, D1}]` against archive `111@D1`, `222@D2` and two garmin records in 2020. In this fixture no archive candidate sits 1..120 s from D1. The only record near D1 is 111 at offset 0, and `findNearMatch` excludes offset 0 (`near-match.ts:52`). If the branches were swapped so that `findNearMatch` ran before `archiveByEpoch.has`, the near lookup would return `undefined` for row 888. Execution would fall through to the exact branch, and every assertion would still pass. So the test cannot tell exact-then-near from near-then-exact, even though its name says that is what it pins. The same is true of the by-id branch: no id-matched row has a near neighbour anywhere in the fixtures.
**Fix:** Add an archive record inside the window of the exact row, so that near-first ordering would skip it:
```ts
it('resolves an exact epoch by start_date before the near rule', async () => {
  const f = fixture([{ id: '222', date: D2 }, { id: '888', date: D1 }]);
  // decoy 30 s after 111: a near-first ordering would skip row 888 against it
  fs.writeFileSync(path.join(f.activitiesDir, '555.json'),
    JSON.stringify({ id: 555, start_date: '2011-08-16T18:56:02Z' }));
  const doc = JSON.parse(await run(f));
  expect(doc.activities['111']).toEqual(expect.objectContaining({ matched_by: 'start_date', strava_id: '888' }));
  expect('near_match_skipped' in doc.sources.strava).toBe(false);
});
```
Add a by-id twin with the same decoy. Then confirm that swapping the branches in a scratch copy turns both tests red.

### WR-02: Near candidates include records already claimed by another export row; the dropped row leaves no durable record

**File:** `src/exports/consolidate.ts:180-191, 233-243, 295`
**Issue:** `nearCandidates` holds every archive record, including records already matched exactly (by id or epoch) by a *different* row of the same export. The near test fixture (`consolidate.test.ts:184-192`) builds exactly that case. Export row 111 id-matches archive 111, and export row 777 is a distinct Strava activity ID 1..120 s away. Row 777 is skipped, so the test certifies dropping it. Under A1 the skip writes no provenance entry. The only trace is a console line plus an aggregate `near_match_skipped` count, with no IDs. By contrast, `intervals-sync.ts` records its skips durably in `near_match_skips`. If a run is wrongly skipped (for example, two genuine recordings started within 2 min of each other), nobody can audit or recover it after the console output is gone. Even when the skip is correct, the export's `original` file link for the archive record is lost, so that record stays in `archive_without_original`. A1/A2 were adopted deliberately, so this is a WARNING and not a BLOCKER. The combination was not considered in RESEARCH.md: open question 1 covers only provenance, and A2 covers only provider scope.
**Fix:** Keep A1/A2, but make the skip auditable and keep SC5 digest stability (the key is emitted only when the list is non-empty):
```ts
const nearSkips: Array<{ strava_id: string; archive_id: string; delta_s: number }> = [];
// in the near branch:
nearSkips.push({ strava_id: run.stravaId, archive_id: near.id, delta_s: near.deltaS });
// summary:
...(nearSkips.length > 0 ? { near_match_skipped: nearSkips.length, near_match_skips: nearSkips } : {}),
```
Optionally, leave out of `nearCandidates` any archive id already claimed by an exact match in this export. This needs a two-pass classification: exact for all rows first, then near against unclaimed records. Pin whichever rule you choose with a test.

### WR-03: The always-on drift layer never checks `buildPaceQualityShard`'s own computable `signals` literal

**File:** `scripts/verify-dashboard-publish-quality-keys.test.mjs:112-130` (emitter: `src/analytics/pace-quality.ts:2257-2269`)
**Issue:** `buildPaceQualityShard` builds the computable-branch `signals` object as its own literal, separate from the `return` in `computePaceQualitySignals` (`pace-quality.ts:1843-1855`). Layer 1 compares `QUALITY_SUB_KEYS` with `computableSignals` and `nullSignals`, and compares `PACE_QUALITY_SHARD_KEYS` with the shard's top level. It never compares against `keysOf(computableShard.signals)`. A key added to one literal and not the other is caught only by layer 2's dist anchor (line 183), which is `skipIf(!HAS_DIST)` and covers only the 3 sampled shards. The suite header says layer 1 alone is the drift check that always runs.
**Fix:**
```js
it('QUALITY_SUB_KEYS equals every shard branch signals key set', () => {
  for (const shard of [computableShard, nullShard, badShard]) {
    expect(diffKeySets(QUALITY_SUB_KEYS, keysOf(shard.signals))).toEqual({ missingFromList: [], notEmitted: [] });
  }
});
```

### WR-04: Planted removal mutates only `activities[0]`, so the gate's "every row" property is unproven

**File:** `scripts/verify-dashboard-publish-quality-keys.test.mjs:203, 266-280`; `scripts/verify-dashboard-publish-guard.test.mjs:241-243`
**Issue:** The gate's row check exists because "a partial rollout (some rows carrying the field, some not)" must fail on EVERY row (`verify-dashboard-publish.mjs:295-303`). Every planted row mutation, in both the new suite and Case G, deletes the key from `activities[0]` only. A gate that regressed to checking only the first row would still pass all 11 row cases and Case G. Examples: `const row = parsed.activities[0]`, or reusing `hasAnyQuality`-style `.some` logic where the first row decides. Every assertion here agrees with the gate's behaviour but none would detect a gate that stopped scanning past row 0.
**Fix:** Run the row cases on at least the last row (and ideally a middle row), and assert the named id:
```js
it.each(EMITTED_SIGNAL_KEYS.flatMap((k) => [[k, 'last'], [k, 'mid']]))('row quality without %s on the %s row fails', (key, where) => {
  const idx = where === 'last' ? cleanIndex.activities.length - 1 : Math.floor(cleanIndex.activities.length / 2);
  const id = cleanIndex.activities[idx].id;
  const { status, output } = withMutation(shadowIndexPath, cleanIndex, (m) => { delete m.activities[idx].quality[key]; }, (c, m) => {
    expect(key in c.activities[idx].quality).toBe(true);
    expect(key in m.activities[idx].quality).toBe(false);
  });
  expect(status, output).not.toBe(0);
  expect(output).toContain(`activity ${id} "quality" is missing sub-key "${key}"`);
});
```

### WR-05: The gate throws on a non-object `row.quality` instead of failing with a named reason

**File:** `scripts/verify-dashboard-publish.mjs:310-321`
**Issue:** The loop only treats `null`/`undefined` as "quality missing". If a row has `quality` set to a string, number or boolean (for example a serialisation bug that writes `"quality": "[object Object]"` or `true`), `key in row.quality` throws `TypeError: Cannot use 'in' operator`. That unwinds out of `main()`, `main().catch` prints a stack, and the process exits 1. The gate does fail closed, but it skips every remaining check, gives no `✗` line naming the row, and prints no `N check(s) passed, M failure(s)` tally. The file header (line 43) treats that kind of raw-stack exit as a defect. The rewritten loop was the place to close this. The shard path already guards `typeof parsedShard.signals !== 'object'` (line 886), so the two checks are now inconsistent.
**Fix:**
```js
if (row.quality === null || typeof row.quality !== 'object' || Array.isArray(row.quality)) {
  missingQualityId = row.id;
  qualityObjectMissing = true;
  break;
}
```
Update the message to `is missing "quality" or it is not an object`, and add one planted case (`quality: "x"`) asserting a non-zero exit with that message and a parseable tally.

### IN-01: Without a dist, nothing proves the gate actually consumes the shared lists

**File:** `scripts/verify-dashboard-publish-quality-keys.test.mjs:149, 162, 191`
**Issue:** Layer 1 proves that the shared lists match the emitter. Only layer 3 proves that the gate *uses* those lists, and layer 3 is `skipIf(!HAS_DIST)`. On a fresh checkout the suite goes green without ever touching the gate. Someone could put a hardcoded 6-key list back in the gate and every always-on test would stay green. CI is covered because it runs `build-widgets` before `test:logic`. `sampledShardIds` (line 156) copies the gate's sampling formula. If the two drift apart, the tests fail loudly rather than passing vacuously, but it is another copy of the gate's logic to keep in sync.
**Fix:** Add a cheap structural test that always runs. It should read `verify-dashboard-publish.mjs`, assert it imports `QUALITY_SUB_KEYS, PACE_QUALITY_SHARD_KEYS` from `./lib/quality-keys.mjs`, and assert it has no local `const QUALITY_SUB_KEYS =` and no array literal of the key names.

### IN-02: Planted cases don't check that the planted key is the only failure

**File:** `scripts/verify-dashboard-publish-quality-keys.test.mjs:278-279, 294-297, 312-315`
**Issue:** Each case asserts a non-zero exit and that the expected line appears. It does not assert `parseTally(output).failures === 1`, so collateral failures caused by the shadow-tree copy (for example re-serialisation of index.json) would go unnoticed. The clean-shadow test (line 260) covers this only if it runs and passes first.
**Fix:** Add `expect(parseTally(output)?.failures).toBe(1)` to each planted case.

### IN-03: The shard checks compute `.some` and then `.find` over the same predicate

**File:** `scripts/verify-dashboard-publish.mjs:877-878, 888-890`
**Issue:** The predicate is evaluated twice, and the two copies can drift apart if one is edited.
**Fix:** Compute `const missingTop = PACE_QUALITY_SHARD_KEYS.find(...)` once before the `if` chain and branch on `missingTop !== undefined`. Do the same for `missingSub`.

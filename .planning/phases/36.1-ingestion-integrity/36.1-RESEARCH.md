## Summary

**Three findings the planner must act on before writing tasks.**

1. **ING-01 is a CI-topology problem, and the pinned set is small.** The nightly job runs fetch, compute-all-stats, build-widgets, `npm test`, verify-dashboard, then commit, then deploy. Nothing is committed until every gate is green, so one red test discards the whole night's fetch (`.github/workflows/daily-refresh.yml`). I probed which tests move when the archive moves, by running the full suite (3971 tests, about 28 s) in a scratch copy with HEAD code and the `data/` tree from two older commits. With the pre-sync archive (1899 files, the 55-run delta) exactly ONE test failed: `src/analytics/compute-dashboard-index.test.ts > pace disagreement > flags EXACTLY the archive-wide count parsed from 35-CALIBRATION.md`. With an archive from 2026-08-31 (1883 files) the same test failed plus `compute-stream-checksums` live gate. That second failure is a false lead: it fails only because the probe deleted streams the checksum manifest lists, and the test explicitly tolerates NEW stream files (see its planted-edit proof), so a growing archive does not trip it. The one real drift-pinned row is therefore the count test, and it is an `it` inside a `describe` of mostly stable named-activity checks.

2. **The "known miss" Garmin 18180779941 is already in the archive.** `data/activities/18180779941.json` exists (`source_provider: strava-export`, start 2026-04-20T06:32:28Z, a Strava phone-app `.gpx`, imported by `consolidate-exports` on 2026-08-10; `data/provenance.json` shows `matched_by: imported`, `original: strava:activities/18180779941.gpx`). `export_data/strava/activities.csv` has it as Strava Activity ID 18180779941. So 18180779941 is a **Strava** activity id, not a Garmin Connect id, and it is not missing from the archive by id or by start epoch. A correct reconciler must NOT list it as missing. The ROADMAP/ING-02 wording "list is shown to contain Garmin 18180779941" is unsatisfiable as written unless the Garmin export's record of that morning has a different start time or id (to be settled by the real probe). The one run that is demonstrably absent from the archive today is the 2026-11-18 morning run: the archive has 2026-11-17T06:06:52Z and 2026-11-18T15:06:43Z and nothing in between on the 18th. That is the correct named input for the reachability proof. This needs a user decision (Open Question 1) and a plan row that states the expected classification of 18180779941 from the probe, not a pre-baked "must be missing".

3. **No Garmin export exists, and the old request cannot cover Nov 2026.** `export_data/` holds only `strava/` (coverage 2011-08-16 to 2026-08-08, 1865 runs). The Garmin export was requested 2026-08-09 (todo `2026-08-10-garmin-export-adapter-when-export-arrives.md`) and has not arrived after 108 days; it would predate 2026-11-18 anyway. A fresh request is needed now. Meanwhile ING-03 does not need the bulk export: the importer should accept a single FIT path, and the 2026-11-18 morning run can be exported as an original FIT from Garmin Connect for this purpose. The Strava export is useless as a discovery source today (`readStravaExportCsv` against the archive finds 0 missing, 0 near-matches), but it is a valid source to prove the reconciliation core and the audit writer end to end.

**Primary recommendation:** Split the suite into `test:logic` (blocking, before verify, commit and deploy) and `test:archive` (`continue-on-error`, summarised in the job summary, followed by a final `exit 1` step after deploy so the run is red but data is committed and the site is deployed). Build one source-agnostic reconciliation core with a Strava adapter proven now and a Garmin adapter gated behind a blocking export-request checkpoint plus a probe task. Build the FIT importer around "one FIT path in, one canonical activity plus stream out", deduplicated on `session.startTime` epoch, writing only through injected directories.

### Pattern 1: Two vitest configs, one partition
**What:** `*.archive.test.ts|mjs` marks files that read the live archive and compare to a figure held outside the test's own computation. Logic config excludes them (use `configDefaults.exclude` plus the glob, because setting `exclude` overrides the defaults). Archive config includes only them. `npm test` stays `vitest run` (everything), so local workflows and existing VALIDATION commands do not change.
**Guard (needed, or the split can silently drop tests):** assert from `vitest list --filesOnly` that logic and archive file sets are disjoint, their union equals the original default file set (108 files at HEAD), and the archive set is non-empty with a recorded matched-test count.
**Example:**
```ts
// vitest.logic.config.ts  (shape only)
import { defineConfig, configDefaults } from 'vitest/config';
import base from './vitest.config';
export default defineConfig({ test: { ...base.test, exclude: [...configDefaults.exclude, '**/*.archive.test.*'] } });
```

### Pattern 2: Non-blocking pinned suite, red job after deploy
**What:** `test:archive` runs with `continue-on-error: true` and an `id`. A step conclusion of `success` with outcome `failure` lets later steps run (job stays green until the final step). Final step `if: steps.archive_pinned.outcome == 'failure'` writes the failing names to `$GITHUB_STEP_SUMMARY` and `exit 1`. It sits AFTER Deploy.
**Pitfall:** `... | tee log` hides vitest's exit code unless the step sets `shell: bash` (which implies `-eo pipefail`) or the step uses `set -o pipefail`. Otherwise the archive failure becomes invisible. This is exactly the silent-pass failure the project keeps hitting.

### Pattern 3: Early data commit (recommended belt-and-braces)
**What:** Commit `data/activities`, `data/streams`, `data/sync-state.json` right after the fetch, before compute/build/tests, like the existing "Commit exclusion change" step does (with the same `[skip ci]` caveat: the token must be on the subject, and must never be quoted in any body that is not meant to suppress the run). Then ANY downstream failure (compute, build, verify, a logic test) no longer discards fetched runs. The later `Commit updated data` step then only carries geo and ceiling state. This closes the root cause "61 nights of fetched runs discarded", not only the one test. Tradeoff: a poisonous record is now committed before the build proves it is buildable, so a bad run keeps failing nightly builds until a human fixes it; the data is not lost, which is the point. This is an Open Decision (Q2). The split alone satisfies criterion 1.

### Pattern 4: Source-agnostic reconciliation core
**What:** `reconcile(exportRuns: {sourceId, startEpoch, activityType, distanceM, name}[], archive: {epoch, id}[], opts)` returns `{matchedExact, near[], missing[], ignoredTypes{type: count}, window{firstEpoch,lastEpoch}}`. The adapter owns file parsing; the core owns matching. Match = EXACT start epoch (the same key `IntervalsSync.existingStartEpochs()` uses, proven unique and exact on 113/113 and 1861/1865 rows). A run within a small tolerance but not exact is `near` and never silently deduped or imported.

### Anti-Patterns to Avoid
- **Blocking pre-fetch archive gate.** Running `test:archive` blocking on the committed tree before the fetch looks attractive ("genuine regression still blocks") but is a trap: after one drifted nightly commits fresh data, the committed tree is itself inconsistent, so the next night's pre-fetch gate fails and discards that night's fetch. The original bug returns. Archive-pinned must be non-blocking everywhere.
- **Moving the whole `describe('pace disagreement')`.** Only the count `it` (line 1572) is drift-sensitive. The named-activity rows (1646, 1665, 1678, 1717) read named streams that never change. Moving them weakens the blocking gate for no reason.
- **Auto-importing everything the reconciler lists.** The missing list will include 0-km blips and watch tests. Import is explicit per id.
- **Relaxing a pinned assertion to make it pass.** Recalibrate via the generator (as in quick 261125-cvq) or leave it red and reported.

## Common Pitfalls

### Pitfall 1: The success-criterion input is already in the archive
**What goes wrong:** A reconciler that finds 18180779941 present is "wrong" per the roadmap text, so someone loosens matching (e.g. matches by id only, or drops the archive's strava-export records) to make it appear missing.
**Why it happens:** The id is a Strava activity id. The Strava export file is `activities/18180779941.gpx`. The archive record exists.
**How to avoid:** Use the real probe: compute where the Garmin export's 2026-04-20 morning activity lands (matched exact, near, or missing), and write the row against that real classification. Use the 2026-11-18 morning run as the reachability target; compute its real start time from the export before fixing any expected value (reachability probes must use the named input).
**Warning signs:** A task that hard-codes "18180779941 must be in the missing list".

### Pitfall 2: Garmin export layout guessed
**What goes wrong:** An adapter is written against a described layout and silently finds nothing, so "0 missing" looks like completeness.
**How to avoid:** Blocking checkpoint to obtain the export, then a probe task that records the real tree, the real field names and a scrubbed fixture, committed before the adapter. An adapter that parses zero activities must fail, not report zero missing. Assert `exportRuns.length > 0` and that the window is derived from parsed data.

### Pitfall 3: Fail-open type filter
**What goes wrong:** `if (type === 'running') run else skip` hides `trail_running`, `treadmill_running`, `track_running`, `virtual_run` (names to verify in the probe). The audit says "0 missing" because the missing ones were classified non-run.
**How to avoid:** Fail closed. Treat any activity type containing "run" as run-like; count every ignored type in `ignoredTypes{type: count}` in the audit so an unexpected type is visible. Never an unconditional else that returns the benign label.

### Pitfall 4: Dedupe key drift
**What goes wrong:** Importer keys on `fileId.timeCreated` (2 s after start) or the first record timestamp, so the later intervals.icu run does not collide and a duplicate appears.
**Evidence:** In the decoded FIT, `session.startTime` = 13:55:40Z, `fileId.timeCreated` = 13:55:42Z. The intervals record `i174110410` has `start_date: 2026-04-29T13:55:40Z`. Exact equality with `session.startTime`. `[VERIFIED: decoded export_data/strava/activities/19410946914.fit.gz and data/activities/i174110410.json]`
**How to avoid:** `start_date = session.startTime.toISOString()` with `.000Z` collapsed to `Z` (second precision, same shape as the other writers). Multi-session FITs: fail closed (reject), do not pick the first.

### Pitfall 5: Imported summary fields differ from intervals.icu's definitions
For the same run (`i174110410` vs its FIT): distance 13437.17 equals `totalDistance` exactly; `elapsed_time` 4881 vs `totalElapsedTime` 4881.703 (the intervals value truncates, `consolidate.ts` rounds); `moving_time` 4586 vs `totalTimerTime` 4599.2; `total_elevation_gain` 40.6 vs `totalAscent` 62. An imported run will therefore not equal what intervals.icu would later have reported, and elevation-calibration constants were tuned on intervals/Strava values. Record `source_provider: 'garmin-export'` and the FIT-derived field origin so downstream analysis can tell them apart. `[VERIFIED: measured]`

### Pitfall 6: Possible third silent-loss path in the nightly sync (flag, do not fix without a decision)
`IntervalsSync` skips `activity.type !== 'Run'` and counts those as "skipped" together with already-present runs, so a `TrailRun` or `VirtualRun` type from intervals.icu would vanish without distinguishing it. The archive contains only `Run` (1954 of 1954), which is consistent with either "none exist" or "all dropped". Separately, the fetch window is the watermark minus 24 h by local date, so a run delivered later than that is never re-fetched. Both are `[ASSUMED]` hypotheses about why runs go missing; the reconciliation is exactly the instrument that will reveal whether they matter. Recommend recording them as follow-ups, and (cheap, low risk, decision needed) widening the overlap window, since dedupe by epoch makes re-fetching harmless.

### Pitfall 7: Audit not idempotent
**What goes wrong:** `generated_at`, HEAD hash or an absolute path inside the audit makes regeneration non-byte-identical (project lesson: prose corrections and generated artifacts revert or churn).
**How to avoid:** The audit is a pure function of (export bytes, archive state). No wall clock, no git hash, no absolute paths. The export date is derived from export content or passed as a recorded flag. Prove regen, commit, regen.

### Pitfall 8: Tests that write tracked files
**What goes wrong:** An importer test defaults to `data/activities` and writes a real record.
**How to avoid:** Importer takes injected `activitiesDir`, `streamsDir`, `manifestPath`, `provenancePath`; tests use `mkdtemp`. Never default these inside code reachable from a test without an explicit argument. Verify with `git status --porcelain -- data .planning` before and after the full suite (empty diff), not with an fs spy (named imports are invisible to `vi.spyOn(fs, ...)`).

### Pitfall 9: Id collision across namespaces
Router, curate server and four scripts validate ids with `/^i?\d{1,20}$/`. A Garmin-prefixed id (e.g. `g123`) would be rejected by the dashboard router and curation guard. Plain numeric Garmin ids share a numeric space with Strava ids. Recommend plain digits plus a hard collision check (refuse if `data/activities/<id>.json` exists or any record carries that id), with `garmin_activity_id` stored explicitly. Widening the regex means editing every mirrored copy and is a security-adjacent change; avoid.

### Pitfall 10: The count test's blind recalibration
When the archive-pinned count goes red, the fix is the generator (`compute-running-pace-dispute-calibration`), per quick 261125-cvq, and never a loosened `toBe`. The new reporting path must name the generator in its summary text so the red job is actionable.

### Garmin bulk-export structure (LOW to MEDIUM; must be probed)
Described by web sources, not observed: top-level `DI_CONNECT/`, with `DI-Connect-Fitness/` holding `*_summarizedActivities.json`, wrapped as `[{"summarizedActivitiesExport":[{...}]}]`; `DI-Connect-Uploaded-Files/` (or `DI-Connect-Fitness-Uploaded-Files/`, name varies by account) holding `UploadedFiles_*-_Part*.zip` that contain the original `.fit` files, named by upload time and not by activity id. Reported fields: `activityId`, `name`, `activityType` (e.g. `running`), `startTimeGmt` (epoch ms), `startTimeLocal`, `duration` (ms), `distance` (reported as centimetres in one third-party importer, which verified it against `avgSpeed`), `avgHr`. Consequence for the design: FIT files cannot be joined to summary rows by filename, so the adapter should join by FIT `session.startTime` epoch equal to `startTimeGmt/1000`, which is also the dedupe key. Every one of these names, units and the join must be confirmed by the probe, including whether the zips nest, whether the account uses `DI-Connect-Uploaded-Files`, the exact activityType strings for treadmill and trail, and whether the export carries a manifest with a generation date. Delivery time reported 24 to 48 h typically, up to 30 days for large accounts.

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Zip-slip on a malicious or malformed archive | Tampering | `execFile('unzip', ['-o','-d', fixedDir, zip])`, no shell string; extract into a dedicated dir; verify resolved output paths stay inside it |
| Command injection via export filenames | Tampering | Args array, never string interpolation |
| Path traversal via activity id into `data/activities/<id>.json` | Tampering | Digit-only id regex; refuse otherwise |
| Personal data in a public repo | Information Disclosure | `export_data/` is gitignored; Garmin account data (`DI_CONNECT` account/device/profile files) is never copied; the committed fixture and audit contain no coordinates, names of devices with serials, or account fields; streams carry no position (existing rule) |
| Poisoned FIT (huge, malformed) | Denial of Service | `isFIT()` and `checkIntegrity()` before `read()`; cap file size; per-file try/catch like backfill |
| `[skip ci]` token in a commit message | Denial of Service (silent) | Never quote the token in a commit body; the early-commit step must carry it only in its subject when intended |
| Workflow expression injection | Tampering | Keep inputs in `env:`, as the existing exclusion step does |

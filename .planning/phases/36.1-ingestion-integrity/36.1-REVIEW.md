## Summary

I reviewed the four parts of the phase:
- the CI split: early commit, blocking `test:logic`, reported `test:archive`, and a red step after deploy
- the reconcile core, its adapters, the committed audit, and the zero-import recount
- the FIT importer
- provenance re-derivation in `consolidate-exports`

The core step ordering in CI is correct:
- `shell: bash` supplies `pipefail` to the archive step.
- Deploy has no `if:` and no dependency on `archive_pinned`.
- The red step uses `outcome`, not `conclusion`.
- The skip-ci token appears only in bot commit subjects.

The committed `data/reconciliation/*.json` audits and `data/provenance.json` contain no email. The reconcile core fails closed on 0 runs and on unreadable archive files.

**Defects found:**
- **Blocker (privacy):** the FIT importer copies the source filename into public, committed fields without scrubbing it. In the real Garmin bulk export, every uploaded FIT file has the account email in its name. 22,625 such files are extracted locally under `export_data/garmin/_extracted/`.
- **The CI structure guard fails open:** four realistic workflow mutations each pass it with zero violations. I verified this by running `checkWorkflow` on each mutated text.
- **The early-commit "retry" described in the workflow comment does not exist.**
- **The importer's "refuse before the first write" contract is broken** on the provenance path.
- **Fallbacks that fail open:**
  - the Garmin summary-filename scrub
  - Strava rows whose date cannot be parsed
  - provenance for sources that are absent

Out of scope, but noted because it is exactly the fail-open class the phase is meant to catch: `src/api/intervals-provider.ts:552` maps a missing `type` to `'Run'`. IntervalsSync then counts an untyped activity as a run.

## Critical Issues

### CR-01: `import-fit` writes the Garmin account email into committed, public records

**File:** `src/exports/fit-import.ts:230-240` (also `:285`)

**Issue:** `externalId: path.basename(opts.fitPath)` and `original = \`${opts.source}:${rel}\`` are copied verbatim into three places:
- `data/activities/<id>.json`, as `external_id` and `original_file`
- `data/provenance.json`
- through `consolidate.ts:167`/`:273`, every later regeneration of `data/provenance.json`

All of these are committed to the public repo.

The Garmin bulk export names every uploaded FIT file `<account-email>_<n>.fit`. I counted 22,625 such files under `export_data/garmin/_extracted/UploadedFiles_0-_Part{1,2,3}/`, and `unzip -l` on `UploadedFiles_0-_Part1.zip` shows the same pattern.

The CLI help (`src/index.ts:617`) invites `import-fit <path-under-export_data/<source>/>`. The bulk export is the obvious place to pick a file. Importing any FIT from it would therefore publish the email in two committed files.

The one real import (`25116720114`) came from a single-activity download (`25116720114_ACTIVITY.fit`), so nothing has leaked yet. No test covers an email-bearing filename. `reconcile-exports.ts:22-27` shows the team already knows about this filename hazard, but the importer has no equivalent.

**Fix:** Never derive public fields from the raw filename. Refuse any path that contains `@`, and record a neutral name:
```ts
const rel = path.relative(sourceRoot, resolvedFit).split(path.sep).join('/');
if (/@/.test(rel)) {
  throw new Error('refusing: FIT path contains an account identifier (@); copy it to a neutral name first');
}
// external_id: a neutral, id-derived name instead of the basename
externalId: `${id}${resolvedFit.endsWith('.gz') ? '.fit.gz' : '.fit'}`,
```
Also add an `@` rejection to `safeOriginalFile` in `consolidate.ts:138`. Add a test that plants `a@b.c_123.fit` and asserts that `importFit` rejects it and writes nothing.

## Warnings

### WR-01: Early-commit "retry" is illusory; a push race plus a red logic suite still drops the night's commit

**File:** `.github/workflows/daily-refresh.yml:120-136`, `:278-286`

**Issue:** The comment says the later "Commit updated data and stats" step "acts as the retry". It does not.

When `commit_fetched` fails on a non-fast-forward push, git-auto-commit-action has already made the local commit. Only the push failed. When the later step runs:
- `data/activities`, `sync-state.json` and `data/streams` are clean, so the action reports "Working tree clean" and pushes nothing, unless geo or ceiling files changed.
- If they did change, it pushes the same un-rebased HEAD and loses the same race again.

If `test:logic` fails, the later step never runs at all. That is the exact failure this phase exists to prevent.

The only thing that actually recovers is next night's re-fetch, because `sync-state.json` was not persisted. That recovery is accidental and undocumented.

**Fix:** Fetch and merge before pushing in the early step. Per project memory, merge rather than rebase. Then correct the comment:
```yaml
      - name: Sync with origin before committing fetched data
        run: git pull --no-rebase --no-edit origin master
```
Alternatively, state in the comment that recovery relies on the unpersisted watermark causing a re-fetch, and drop the "retry" claim.

### WR-02: The workflow structure guard passes four mutations that break the rules it claims to enforce

**File:** `scripts/lib/workflow-gates.mjs:12`, `:39`, `:77-111`, `:121`

**Issue:** I ran `checkWorkflow` on four mutated versions of the real workflow, and each one returned `[]`:
1. **Unnamed bare test step.** Adding `      - run: npx vitest run` passes. `STEP_RE` only splits on `- name:`, so the unnamed step merges into the previous block. `extractRun` only matches `^\s+run:` and never `- run:`, so NO-BARE-TEST cannot see it.
2. **`shell: bash {0}` on `archive_pinned`.** The regex `/^\s+shell:\s*bash\b/` matches, but a custom shell string does not get GitHub's `-eo pipefail`. `tee` hides the vitest exit code again.
3. **`if: false` on `commit_fetched`.** EARLY-COMMIT never checks for an `if:` on that step.
4. **`run: npm run test:logic || true`.** LOGIC-BLOCKING checks for `continue-on-error` and `if:`, but not for shell-level exit suppression.

`daily-refresh-gates.test.mjs` plants one mutation per rule, so these holes are not exercised.

**Fix:**
- Split steps on `^ {6}- ` rather than on `- name:`, and treat `- run:` and `- uses:` as step starts.
- Require `shell` to be exactly `bash`: `/^\s+shell:\s*bash\s*$/m`.
- Flag any `if:` on `commit_fetched`.
- Reject `|| true`, `|| :` and `set +e` in the logic step's run body.

Add one planted mutation per hole to the test.

### WR-03: Garmin summary-filename scrub fails open

**File:** `src/exports/reconcile-exports.ts:23-27`; `src/exports/adapters/garmin.ts:42`

**Issue:** The adapter accepts any name ending in `_summarizedActivities.json`. `publicSummaryPath` only replaces the prefix when the name matches `_\d+_summarizedActivities\.json$`. When a Garmin export uses a different shape, the full name is written verbatim into `export_identity.summary_files[].path` of the committed audit. Examples of such shapes:
- `<email>_summarizedActivities.json`, with no page number
- a renamed page

That name contains the account email. The scrub is allow-and-hope instead of fail-closed.

**Fix:** Replace everything before the suffix unconditionally, and assert:
```ts
const base = path.basename(rel);
if (!base.endsWith(GARMIN_SUMMARY_SUFFIX)) throw new Error('unexpected summary file name');
const m = /(_\d+)?_summarizedActivities\.json$/.exec(base)!;
const pub = `<account>${m[0]}`;
if (pub.includes('@')) throw new Error('scrub failed');
```

### WR-04: `consolidate-exports` drops all Strava provenance when `export_data/strava` is absent

**File:** `src/exports/consolidate.ts:174-290`

**Issue:** `provenance` is rebuilt from scratch on every run. Only `garmin-export` records are re-derived (`:271-275`). `export_data/` is gitignored and local-only. Consider a run where `export_data/garmin` exists but `export_data/strava` does not, for example a fresh checkout that only has the newer Garmin export. That run rewrites the committed `data/provenance.json` without:
- the ~1,861 `strava_id`/`start_date` links
- the gear attributions
- the 4 Strava `matched_by: 'imported'` entries

All of them move into `archive_without_original`. No error or warning is raised.

The "survives re-runs" property is only tested with identical inputs (`consolidate.test.ts:106`). `backfill-streams.ts:199` reads this file.

**Fix:** Start from the existing document, and only overwrite entries for sources processed in this run:
```ts
const prior = fs.existsSync(provenancePath) ? JSON.parse(fs.readFileSync(provenancePath, 'utf-8')) : { activities: {} };
const provenance: Record<string, ProvenanceEntry> = {};
for (const [id, e] of Object.entries(prior.activities ?? {})) {
  const src = String((e as ProvenanceEntry).original ?? '').split(':')[0];
  if (!sources.includes(src)) provenance[id] = e as ProvenanceEntry;
}
```
Alternatively, refuse to write when a source that has prior entries is missing. Add a test that runs once with both sources and then once with only `garmin`.

### WR-05: Strava rows whose date cannot be parsed vanish silently from the reconcile completeness claim

**File:** `src/exports/consolidate.ts:88-91` (consumed by `src/exports/adapters/strava.ts:17`)

**Issue:** `readStravaExportCsv` calls `console.warn` and `continue`s on a `Run` row whose `Activity Date` it cannot parse. The adapter converts dropped run-like types into hard errors, but dropped rows are invisible to it. The audit's `export_runs` silently shrinks, and the run can never appear in `missing`. That is fail-open in exactly the code path that claims completeness.

The recount does throw on the same input (`compute-reconcile-recount.mjs:106`). However, the recount only runs when someone invokes it by hand.

**Fix:** Return a `skippedRuns` count from `readStravaExportCsv`, and make the adapter throw when it is non-zero:
```ts
if (skippedRuns.length > 0) throw new Error(`Strava CSV parser skipped ${skippedRuns.length} Run rows with unparseable dates; refusing to report completeness`);
```

### WR-06: Importer and nightly sync disagree on near-matches; a duplicate archive record is pinned as expected

**File:** `src/exports/fit-import.ts:217-224`; `src/sync/intervals-sync.ts:113-117`; `src/exports/fit-import.test.ts:371-376`

**Issue:** `importFit` refuses an import when an archive start lies within 1..120 s, because that is ambiguous. `IntervalsSync` dedupes on exact epoch only.

Consider an imported FIT whose start differs from intervals.icu's `start_date` for the same activity by 1 s or more. For example, Garmin's summary showed `-46/-47` s deltas for two runs in the committed audit. If intervals.icu later delivers that run inside the 1-day overlap window, it becomes a second archive record for the same run. That double-counts distance, PRs and totals.

The test `CAN-FAIL: start_date shifted by 1 s does create a record` asserts that this duplication happens, so it enshrines the defect rather than guarding against it.

**Fix:** Make IntervalsSync skip, and log, any fetched run within `NEAR_MATCH_TOLERANCE_S` of an archive record whose `source_provider` is `garmin-export` or `strava-export`. Invert the test so that a +1 s shift yields `newRuns === 0` plus a logged near-match.

### WR-07: `importFit` can fail after writing; this breaks the "refused before the first write" contract

**File:** `src/exports/fit-import.ts:259-286`

**Issue:** The write order is:
1. stream
2. manifest
3. activity
4. `JSON.parse` of the existing provenance file, which can throw

A corrupt or truncated `data/provenance.json` therefore leaves the stream, manifest and activity written, with no provenance entry. A re-run then hits the exact-epoch branch and returns `duplicate`, so the provenance link is never written by `import-fit`.

The header comment (`:27`) promises that "Everything ambiguous is refused with a thrown error BEFORE the first write".

**Fix:** Read and validate the provenance document, and load the manifest, before any write. Then write all four files. Write the activity record last so that a partial run stays importable:
```ts
const provDoc = fs.existsSync(provAbs) ? JSON.parse(fs.readFileSync(provAbs, 'utf-8')) : { activities: {} };
if (typeof provDoc !== 'object' || provDoc === null) throw new Error('provenance.json malformed');
// ...then the writes
```

### WR-08: Gzip decompression is uncapped; the size check guards only the compressed bytes

**File:** `src/exports/fit-import.ts:157-163`

**Issue:** `MAX_FIT_BYTES` is checked against `statSync(resolvedFit).size` before calling `gunzipSync(buf)`. A small `.fit.gz` can inflate to gigabytes and exhaust memory. The cap therefore does not bound what is decoded.

**Fix:**
```ts
if (resolvedFit.endsWith('.gz')) buf = gunzipSync(buf, { maxOutputLength: MAX_FIT_BYTES });
```
Wrap the call so that `ERR_BUFFER_TOO_LARGE` surfaces as `FIT file too large`.

### WR-09: FIT decode errors are discarded

**File:** `src/exports/fit-import.ts:169`

**Issue:** `decoder.read()` returns `{ messages, errors }`, and the code only takes `messages`. A file that passes the CRC check but has decode errors, such as an unknown or invalid definition or truncated messages, is imported with partial records or a partial session. The header's "everything ambiguous is refused" contract does not hold here.

**Fix:**
```ts
const { messages: rawMessages, errors } = decoder.read();
if (errors.length > 0) throw new Error(`FIT decode errors (${errors.length}): ${String(errors[0])}`);
```

### WR-10: Garmin ids longer than 16 digits produce a record whose `id` does not match its filename

**File:** `src/exports/fit-import.ts:95`, `:141`

**Issue:** The validation regex allows `^\d{1,20}$`, but the record stores `id: Number(ctx.garminId)`. Above `Number.MAX_SAFE_INTEGER` (2^53, 16 digits), `Number` rounds. The written `<id>.json` then contains a different numeric `id`. Every consumer that keys on `String(activity.id)` (for example `consolidate.ts:165`, `reconcile.ts:204`) then disagrees with the filename and with `garmin_activity_id`.

**Fix:** Reject ids that do not round-trip:
```ts
if (!Number.isSafeInteger(Number(opts.garminId))) throw new Error(`garmin id exceeds safe integer range: ${opts.garminId}`);
```

# Phase 35 — UI Design Contract

> Visual and interaction contract for Phase 35 (Stream-Derived Running Pace). Generated by
> gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Stack reality (confirmed by direct source read, not assumed):** identical to every prior
> phase's UI-SPEC in this repo (16, 17, 18, 19, 26) — a static, build-time-rendered SPA. No
> React/Vue, no component library, no CSS framework, no icon library, no `components.json`. Markup
> is produced by hand-written TypeScript DOM-builder functions under `src/dashboard/views/`,
> styled by one global stylesheet (`src/dashboard/styles.css`) that already declares a complete
> token set (spacing, typography, color, radius), frozen since Phase 19 and extended additively
> per phase. **This phase adds zero new tokens, zero new CSS classes, zero new colors, zero new
> icons/glyphs, and zero new dependencies.** Every visual element specified below reuses
> `buildStatCard`, `.text-label`, `.badge`/`appendAccessibleBadge`, or the existing splits-rebase
> footnote pattern already shipped by Phases 18/26/27/33/34. Where CONTEXT.md's D-10 (rendering
> placement/conditionality/copy) left a concrete shape to Claude's discretion, this spec commits to
> one shape — marked `[decided here]` — so the planner and executor have a single, unambiguous
> contract rather than a second design round mid-phase.
>
> **What this UI-SPEC does NOT decide** (explicitly out of scope for a design contract, owned by
> the phase's calibration machinery per 35-CONTEXT.md / 35-RESEARCH.md): the exact running-pace
> computation and its boundary rule (D-08's arithmetic), the eligibility-gate definition (D-02),
> the disagreement threshold's statistic family and cut value (D-05/D-07), and whether the
> comparison direction ships symmetric or slower-only (D-06). This spec supplies **copy templates
> for both directions** of D-06 so neither choice blocks implementation, and states everywhere a
> number is interpolated into copy which upstream value it must be.

**Why the Running Pace figure and its exclusion line stay neutral, not color-coded (a deliberate,
carried-forward decision):** identical reasoning to 26-UI-SPEC's D-08/D-11 decision — the running
pace and its exclusion statement are **disclosure, not alarm**. Every activity with a computable
stream gets one, including activities with nothing excluded at all (D-10's COV-02 always-on
precedent) — coding a routinely-present, often-healthy figure in a warning hue would misrepresent
a factual disclosure as a defect. The "Pace disputed" badge keeps its existing plain `.badge`
treatment (border + `--text-secondary`, no fill) — this phase widens WHICH activities get that
badge (D-03) and WHAT it compares against (D-01), never its visual treatment.

### Phase-specific rows

| Element | Copy |
|---------|------|
| **Running Pace tile — label** `[decided here]`, third stat tile in the existing `.stat-grid`, immediately after the metadata "Pace" tile (Distance → Moving Time → Pace → **Running Pace** → Elevation Gain → …) | `"Running Pace"` — matches the existing tile-label vocabulary (`"Pace"`, `"Distance"`, `"Moving Time"`), no qualifier needed since the exclusion line beneath it (next row) states what makes it different from "Pace". |
| **Running Pace tile — value, computable case** | `formatPace(runningPaceSecPerKm)` — the SAME formatter the metadata Pace tile already uses (`5:18/km`), so the two tiles are visually and numerically comparable at a glance, satisfying ROADMAP criterion 2's "the two figures visibly differ" (both render in `.text-display`, side by side). |
| **Running Pace tile — exclusion line, nonzero case (RPACE-02's "plain statement")** — a `<p class="text-label">` appended as the tile's third child (same position the Pace tile's disputed badge occupies, `.stat-grid > div`'s third child) | `"Excludes {metresText} over {durationText} of recording gaps, pauses and unreliable segments."` where `metresText = `${Math.round(excludedM)} m`` (matches `unreliableSegmentsBadgeContent`'s existing metres convention, `list.ts:643`) and `durationText = formatEffortDuration(excludedSec)` (matches the same function's duration convention, `list.ts:130`, e.g. `13:17`). Example on 3475724402 (probe reference only, not pinned): `"Excludes 2,253 m over 13:17 of recording gaps, pauses and unreliable segments."` The three named categories deliberately echo the coverage caption's own three non-covered terms (`coverageCaptionText`, `detail-sections.ts:99`) plus "unreliable" — **this sentence must never disagree with the coverage caption's own excluded-time terms**, per D-08's binding "must reconcile with what the coverage caption already discloses" constraint. This is a plain, always-visible sentence, not a hover tooltip — it satisfies RPACE-02's "plain statement" requirement literally, not via `title`/`aria-describedby` alone. |
| **Running Pace tile — exclusion line, zero case** (D-10's COV-02 always-on precedent: a term that disappears at zero stops meaning "zero" and starts meaning "unknown") | `"No time excluded — every second of this activity is covered."` Rendered whenever BOTH excluded metres and excluded seconds are exactly 0 — a genuinely clean stream states its own health, exactly like `coverageCaptionText` always rendering all four terms even at 0%. |
| **Running Pace tile — not-computable state** (D-08's "computable stream is defined, with the count of non-computable activities reported"; the probe found 1 of 1,874 not computable) | Value: `"—"` (the existing `DASH`/`formatOrDash` em dash, unchanged glyph). Exclusion-line slot: `"Not computable — {reason}"` — the SAME phrase template every other not-computable Quality Signals row already uses verbatim (`decimationRow`, `gapProfileRow`, `impossibleSamplesRow`, `unreliableSegmentsRow`, all in `detail-sections.ts`), reusing whatever reason string the existing not-computable classification already produces — no new reason vocabulary. |
| **Running Pace tile — omitted entirely** `[decided here]` | When `detail.stream === null` (no stream at all, not merely "not computable" — the existing `buildNoStreamSection` branch), the Running Pace tile is **not appended** to `.stat-grid`, exactly like the Gear tile's existing "append only when there is something to show" precedent (`detail.ts:739-741`). This is a genuinely different case from "not computable": no-stream activities already disclose that fact via `buildNoStreamSection`'s own copy, immediately below the stats card — a second "—" tile here would be redundant, not informative. |
| **Detail-view "Pace disputed" badge, third child of the existing metadata Pace tile** (RPACE-03; unchanged position, retargeted content per D-01/D-04) | `"Pace disputed — running {runningPaceFormatted}"` — replaces today's `"Pace disputed — stream-derived {formatted}"` verbatim string. The word **"running"**, not "stream-derived", because both the retired `streamPaceSecPerKm` (span-based) and the new running pace are technically "stream-derived" — the old phrase is now ambiguous between two different numbers, and 33-D-11's precedent ("copy that stops describing its own number is a correctness fix, not cosmetics") applies directly. The metadata tile's big `.text-display` value is unchanged (still the metadata pace) — this badge is the disclosure, not a substitution (D-10/ROADMAP criterion 4). |
| **Shared disclosure sentence** — read by BOTH the detail-view badge's `title`/`.sr-only` pair AND the row-surface badge's `title`/`.sr-only` pair, via the single `paceDisputedExplanation` function (`list.ts:307`) so the two surfaces cannot drift apart (unchanged single-source discipline) | **Primary template (slower-only direction, D-06's milestone-aligned reading):** `"Metadata pace disagrees with the running pace: {runningPaceFormatted} measured vs. {metadataPaceFormatted} shown"`. **Symmetric-direction template (only if D-06 ships symmetric):** append a direction clause so a reader is never misled about which way the pace moved — `"Metadata pace disagrees with the running pace: {runningPaceFormatted} measured vs. {metadataPaceFormatted} shown (running pace is {slower/faster})"`, where the bracketed word is computed from the sign of `runningPaceSecPerKm − metadataPaceSecPerKm` (slower = larger sec/km). Whichever template ships, it is the ONE definition both surfaces read — never two independently-worded sentences. |
| **Row-surface "Pace disputed" badge visible text** (list/table/Overview surfaces, `appendPaceDisputedBadge`) | Unchanged: `"Pace disputed"` — short, space-constrained, matching the existing badge vocabulary's length (`"Low confidence"`, `"Excluded from records"`). D-01/D-03 change WHICH rows carry this badge and WHAT its hover/`.sr-only` explanation says (previous row), never the visible row-badge text itself. |
| **Splits-table rebase footnote** (D-09; unchanged position, below `.splits-scroll`, rendered only when the activity is flagged) | `"Splits above are compared against the running pace ({avgFormatted}), not the disputed metadata average."` — replaces today's `"…against the stream-derived average ({avg})…"` for the same ambiguity reason the badge text changes: "stream-derived average" no longer uniquely names one number now that the comparator itself changed meaning under D-01. `{avgFormatted}` is the SAME `rebasedAveragePaceSecPerKm` value already in scope at the call site (`detail.ts:809`) — no re-derivation. |

**Accessibility constraint carried into every copy row above (from the phase brief and Phase 26's
binding precedent):** the exclusion line is plain visible `.text-label` text, not hover-only —
RPACE-02 requires a "plain statement," and burying it in a `title` attribute alone would fail that
requirement for keyboard/touch users who never hover. The retargeted badge text and explanation
keep the existing accessible shape (`appendAccessibleBadge`: visible span + `title` + `.sr-only`
sibling wired by `aria-describedby`) unchanged — no new accessibility pattern is introduced.

## Layout & Responsive Notes

- **The `.stat-grid` gains one more conditionally-rendered tile, nothing else.** The grid is
  `display: grid; grid-template-columns: repeat(auto-fit, minmax(200px, 1fr)); gap: var(--space-lg)`
  (`styles.css:335-339`) — it already tolerates a variable tile count (the Gear tile is
  conditionally appended today), so adding a conditionally-appended Running Pace tile is a
  zero-risk reflow change, not a new layout concern.
- **Tile order is load-bearing for ROADMAP criterion 2's "beside."** Running Pace must be the
  fourth tile, immediately after Pace (third), so the two adjacent `.text-display` numbers read
  side-by-side (or stacked directly beneath, at narrow widths where `auto-fit` wraps to one
  column) — never separated by Elevation Gain or another tile.
- **No new column, no new table.** The splits-table stays at its existing 7 columns
  (`Km | Pace | Elapsed | Avg HR | Avg Cadence | Elev Δ | vs. Avg`, confirmed unchanged by this
  phase) — D-09's rebase is a value-and-footnote-text change to an existing call, not a structural
  change.
- **The exclusion line wraps naturally** like any other `.text-label` paragraph inside a
  `.stat-grid` tile — no truncation, no new breakpoint. At the narrowest supported width
  (~500px iframe emulation, this project's documented checkpoint floor), a tile's fixed
  `minmax(200px, 1fr)` column plus normal text wrapping already handles the Pace tile's existing
  badge text at this width; the exclusion sentence is longer but uses the identical wrapping
  behavior — no measurement surprise expected, but the browser checkpoint (below) confirms it does
  not visually collide with the value above it or the next tile.
- **No new `@media` block is needed.** Existing breakpoints (`380px`, `430px`, `640px`,
  `720px`/`721px`, `1000px`) are untouched.
- **Badge population growth (D-03) is a data change, not a layout change.** Whether the "Pace
  disputed" badge reaches ~1 row (today) or ~20-45 rows (widened), the badge component, its CSS,
  and its position in each row are identical — no list/table/card layout is touched by population
  size alone.
- Theme-awareness: every new element uses existing CSS custom properties
  (`var(--text)`, `var(--text-secondary)`, `var(--border)`, `var(--surface)`), all already declared
  per-theme — no theme-conditional logic is needed in TypeScript.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**Framework & architecture**
- **D-01:** **Vanilla TypeScript, no framework.** Consistent with all 11 existing widgets and 3 standalone pages — zero new runtime dependencies. A small hand-rolled hash router + view modules.
- **D-02:** **Param routes from day one.** The router supports `#/view/:id` and query params (e.g. `#/activity/3475726256`, `#/list?year=2024`) so views are bookmarkable/shareable and Phase 17's detail view and filters slot in without router rework.
- **D-03:** **View registry.** Each view is a self-contained module registering `{route, title, nav entry, render/mount}`. Adding a future view (e.g. Phase 18 Trends) = drop in one module + one registry line. Mirrors how `build-widgets.mjs` enumerates widgets.
- **D-04:** **Plain light DOM** (no Shadow DOM for dashboard views). One global stylesheet driven by CSS custom properties. Shadow DOM stays with the embeddable widgets, which have different isolation needs.

**Navigation & shell layout**
- **D-05:** **Top nav bar**, collapsing to a hamburger or scrollable row on mobile. Nav entries: list, calendar, records, trends (+ overview home). Detail is a drill-in route, not a nav entry.
- **D-06:** **Landing view (`#/`) is an overview home**: headline stats (total km, streaks, recent PRs) + recent activities. Source data already exists in `data/stats/*.json` (all-time-totals, streaks, best-efforts).
- **D-07:** **One proving slice through the data contract.** Unbuilt views render titled stubs ("coming in Phase 17/18"), but one real path must work end-to-end: landing/list shows real activities from the index manifest, and clicking one lazy-fetches that activity's detail JSON. This de-risks Phase 17's contract assumptions.
- **D-08:** **Dashboard lives at the site root** — it becomes `index.html` of the published Pages site. Existing pages (heatmap.html, pinmap.html, routes.html) keep their current URLs alongside it.

**Data contract (activity index + lazy detail)**
- **D-09:** **Browse-complete index fields.** Each of the ~1,867 rows carries everything Phase 17 sorts/filters on plus display extras: id, date, name, distance, moving time, pace, avg/max HR, cadence, elevation gain, location, stream-availability badge (from `data/streams/manifest.json`) and low-confidence flag (from best-efforts data). Roughly 300–500KB raw, well under 100KB gzipped. Whatever isn't in the index can't be sorted/filtered without fetching everything — so the index is deliberately complete.
- **D-10:** **Detail views reuse the committed files directly**: `data/activities/<id>.json` (canonical summary) and `data/streams/<id>.json` (~70–80KB, schema locked in Phase 14). Zero new per-activity pipeline output — the Phase 14 stream schema IS the contract. Client decimates for charts (already the Phase 14 decision, Chart.js Decimation plugin).
- **D-11:** **CI copies data into the publish dir.** The deploy step copies the index manifest + `data/activities/` + `data/streams/` (+ `data/stats/` for the overview home) into `dist/` before publishing. Self-contained same-origin site, no CORS, no raw.githubusercontent coupling. Accepts ~150MB on the gh-pages branch.
- **D-12:** The index manifest is **generated by a compute step in CI and gitignored**, following the existing `data/stats/` conventions (`compute-stats.ts` pattern).

**Theming & visual identity**
- **D-13:** **Same visual identity as the widgets.** Reuse the widget color tokens (Strava orange accent `#fc4c02` light / `#ff6b35` dark, white / `#1a1a2e` backgrounds, system font stack) as global CSS custom properties so dashboard and embedded widgets read as one product family.
- **D-14:** **Theme toggle + auto default.** Follows `prefers-color-scheme` by default; a header toggle (light/dark/auto) persists the choice in localStorage. Same semantics as the widget `ThemeManager`, applied at document level via `data-theme` on the root element.

## Summary

Phase 16 has almost no external-library research surface — D-01 through D-14 already lock the architecture to vanilla TypeScript, hand-rolled hash routing, plain light DOM, and zero new npm dependencies. The real research value here is **codebase archaeology**: finding the exact existing conventions (build wiring, compute-step CLI pattern, theme tokens, CI copy/commit steps) this phase must extend, and surfacing two integration risks the discussion phase didn't fully resolve: (1) `dist/widgets/index.html` is currently a **hand-committed static file** (the widget-showcase demo page), not a build artifact — Phase 16 replacing it with the SPA entry point needs an explicit decision about where that showcase content goes; (2) `build-widgets.mjs`'s `copyDataFiles()` and the CI workflow's git-ignore/commit rules currently exclude `data/activities/` and `data/streams/` from the publish path entirely — D-11's "CI copies data into publish dir" is new wiring, not an extension of an existing copy list.

Everything else is confirmed against the actual repo: the stream file average size (76.6KB, matching D-10's 70-80KB estimate), the compute-step CLI pattern (`src/index.ts` case statements → dynamic `import()` → typed options object), the exact theme tokens to lift from `ThemeManager`, and the per-activity city-geocode source (`data/geo/activity-cities.json`) that satisfies D-09's "location" index field without new computation.

**Primary recommendation:** Build the dashboard as a new Vite multi-page entry (root `index.html` + a `src/dashboard/` source tree) that plugs into the *existing* `build-widgets.mjs` pipeline rather than inventing a parallel build; extend `copyDataFiles()` for the new data families; add one new CLI subcommand (`compute-dashboard-index`) following the `compute-best-efforts.ts` pattern exactly; and resolve the `dist/widgets/index.html` collision by moving the current widget-showcase content to a new static path (e.g. `widgets.html`) before wiring the SPA as the new root.

### Pattern 1: Hash router with param routes, resolved on load AND on change
**What:** Parse `location.hash` into `{path segments, query params}`, match against the view registry, call the matched view's mount function. Must run once on `DOMContentLoaded` (initial URL) in addition to the `hashchange` listener.
**When to use:** Every navigation, including the very first page load with a hash already in the URL (e.g., a bookmarked `#/activity/3475726256` link).
**Why the dual-trigger matters:** `hashchange` does not fire for the hash present at initial page load — confirmed via MDN. A router that only listens for `hashchange` will render a blank/default view for any deep link until the user manually navigates once.
```typescript
// Source: MDN Window: hashchange event — https://developer.mozilla.org/en-US/docs/Web/API/Window/hashchange_event
function resolveRoute(): void {
  const hash = location.hash.slice(1) || '/';        // '#/activity/123?x=1' -> '/activity/123?x=1'
  const [pathPart, queryPart] = hash.split('?');
  const params = new URLSearchParams(queryPart ?? '');
  const match = matchRegisteredRoute(pathPart);       // e.g. '/activity/:id' pattern matcher
  mountView(match, params);
}

document.addEventListener('DOMContentLoaded', resolveRoute); // initial load — hashchange won't fire
window.addEventListener('hashchange', resolveRoute);          // subsequent navigation
```

### Pattern 2: View registry module shape (D-03)
**What:** Each view is a self-contained module exporting one record; a central registry array is the single enumeration point — mirrors how `build-widgets.mjs` enumerates the `widgets` array.
```typescript
// Source: pattern lifted from scripts/build-widgets.mjs's `widgets` array structure
export interface DashboardView {
  route: string;              // '/', '/list', '/activity/:id', '/calendar', ...
  title: string;               // document title + nav label
  navEntry?: { label: string; order: number }; // omitted for drill-in routes (Detail — D-05)
  mount: (container: HTMLElement, params: URLSearchParams, routeParams: Record<string,string>) => void | Promise<void>;

```

### Pattern 3: Document-level theme bootstrap mirroring `ThemeManager` (D-14)
**What:** Same three-state semantics (`light` | `dark` | `auto`) as the existing Shadow-DOM `ThemeManager`, but applied to `<html data-theme="...">` instead of a Shadow Root, and persisted to `localStorage` instead of being attribute-driven per-widget-instance.
**Source of truth for exact tokens:** `src/widgets/shared/theme-manager.ts` — the light/dark hex values (`#ffffff`/`#1a1a2e` bg, `#333333`/`#e0e0e0` text, `#fc4c02`/`#ff6b35` accent) are already locked by D-13 and match this file exactly.
```typescript
// Source: pattern derived from src/widgets/shared/theme-manager.ts, adapted to document scope
type ThemeMode = 'light' | 'dark' | 'auto';
const STORAGE_KEY = 'dashboard-theme';

function applyTheme(mode: ThemeMode): void {
  document.documentElement.setAttribute('data-theme', mode);
  localStorage.setItem(STORAGE_KEY, mode);
}

// Must run BEFORE first paint (inline <script> in <head>, not a deferred module)
// to avoid a flash of the wrong theme — the existing widgets don't have this
// problem because ThemeManager runs inside connectedCallback before Shadow DOM
// content paints; a document-level page needs the equivalent guarantee.
```

### Anti-Patterns to Avoid
- **Fetching the full index on every route change:** the index manifest must be fetched once and cached in module-level state (or `sessionStorage`), not re-fetched per navigation — defeats D-02's "compact index up front."
- **Building `data/activities/<id>.json` fetch URLs by string concatenation without validating `id` is numeric:** the route param comes from user-controlled URL input; an unvalidated id could be used to probe arbitrary same-origin paths (see Security Domain below).
- **Deferred `<script type="module">` for the theme bootstrap:** causes flash-of-wrong-theme on load since module scripts run after DOM parsing completes and typically after first paint; the theme-read-and-apply step must be synchronous and inline, or in `<head>`.
- **Re-introducing Shadow DOM for dashboard views "for consistency" with widgets:** explicitly rejected by D-04 — the widget isolation need (safe embedding on third-party pages) doesn't apply to a self-contained dashboard.

## Common Pitfalls

### Pitfall 1: `hashchange` does not fire for the initial URL
**What goes wrong:** A bookmarked deep link (`#/activity/3475726256`) loads a blank page or the default `#/` view until the user clicks something.
**Why it happens:** The `hashchange` event only fires on a *change* to the fragment; the hash present at initial navigation never triggers it.
**How to avoid:** Call the route-resolve function once on `DOMContentLoaded` in addition to registering the `hashchange` listener (Pattern 1 above).
**Warning signs:** Manual test — paste a `#/activity/<id>` URL directly into the address bar and hard-reload; if the detail view doesn't render, this pitfall is present. `[CITED: developer.mozilla.org/en-US/docs/Web/API/Window/hashchange_event]`

### Pitfall 2: `dist/widgets/index.html` is a hand-committed file, not a build artifact
**What goes wrong:** The planner assumes `npm run build-widgets` already produces `dist/widgets/index.html` and that adding a new Vite entry will cleanly "just work." In fact this file is currently tracked directly in git (`git ls-files` confirms `dist/widgets/index.html` and `dist/widgets/test.html` are committed, per `.gitignore`'s explicit `!dist/widgets/index.html` / `!dist/widgets/test.html` exceptions), hand-authored as a widget-showcase/embed-docs page, and is **not** touched by `build-widgets.mjs` or `vite.config.pages.ts` today.
**Why it happens:** The widget showcase page predates the Vite pages build (added directly in an early commit, `2da5c28`) and was never migrated into the build pipeline.
**How to avoid:** The plan must explicitly (a) decide where the widget-embed-code documentation content goes (candidates: a new `widgets.html` static page built alongside heatmap/pinmap/routes; or a section within the new dashboard's overview/footer), (b) add `index.html` as a genuine Vite build entry so the dashboard SPA becomes the generated file at that path, and (c) remove or update the `.gitignore` exception for `dist/widgets/index.html` — since it becomes build output (like `heatmap.html`), it should no longer be a manually-committed source file. Verify: `git ls-files dist/widgets/index.html` currently returns a match; after this phase, either the file's content is fully generated and the ignore exception is removed, or the plan documents why it stays hand-maintained.
**Warning signs:** If a plan task writes `src/dashboard/index.html` and expects `git status` to show no changes to `dist/widgets/index.html` pre-build, that's the signal this wasn't accounted for.

### Pitfall 3: `data/activities/` and `data/streams/` are not currently in the publish path
**What goes wrong:** Assuming D-10's "detail views reuse the committed files directly" means those files are already reachable at the published site's URL. They are committed to the **git repo's main branch**, but `build-widgets.mjs`'s `copyDataFiles()` only copies `data/stats`, `data/geo`, `data/routes`, `data/heatmap` into `dist/widgets/data/` — `data/activities/` (7.5MB, 1867 files) and `data/streams/` (142MB, 1843 files) are absent from that list today.
**Why it happens:** Those two data families were committed for the backfill/best-effort *compute* pipeline (local, git-tracked), not for direct browser consumption — no prior phase needed them served over HTTP.
**How to avoid:** D-11 requires extending `copyDataFiles()` (or the CI workflow directly) to add these two directories to the publish copy. Budget CI time/storage: copying 150MB of JSON in the build step is a real cost — verify the GitHub Actions runner and `peaceiris/actions-gh-pages` (which does a git push to the `gh-pages` branch) can handle a ~150MB branch; GitHub soft-warns on repos over 1GB and hard-blocks pushes over 2GB per **single push** — 150MB total is comfortably under both, but this repo's `gh-pages` branch will grow every day the workflow runs unless `peaceiris/actions-gh-pages`'s default force-push/orphan behavior is confirmed (it force-pushes a single commit by default, so the branch does not accumulate history — verify this default hasn't been overridden in the existing step config, which it has not per the read `daily-refresh.yml`).
**Warning signs:** A "View Activity" click in the proving slice (D-07) returns 404 for `data/activities/<id>.json` on the live site even though the file exists in the git repo — confirms the copy step was never added.

### Pitfall 4: Flash of wrong theme on load
**What goes wrong:** Page paints in light mode for a frame (or the previous session's theme) before the persisted/auto theme is applied, especially jarring for `auto` users with the system in dark mode.
**Why it happens:** If the theme-read-and-apply logic lives in a deferred `<script type="module">` (which by spec runs after HTML parsing, close to `DOMContentLoaded`), the browser may have already painted the default (light) styles.
**How to avoid:** Put the theme bootstrap in a small, non-module, synchronous inline `<script>` in `<head>`, before the stylesheet's `<link>` or immediately after — read `localStorage`, compute effective theme, set `data-theme` on `<html>` before any CSS referencing `[data-theme]` is evaluated for paint.
**Warning signs:** Visually testable — hard refresh with dark theme selected and watch for a light flash; not automatable without visual regression tooling this repo doesn't have (flag for manual verification only).

### Pitfall 5: Unvalidated route params used to build fetch URLs
**What goes wrong:** `#/activity/<anything>` constructs `fetch('data/activities/' + id + '.json')` without validating `id`. Because GitHub Pages serves everything same-origin and read-only, actual path traversal to sensitive files isn't really exploitable here (no `../` will escape the static `data/` tree meaningfully, and there are no secrets served), but malformed IDs will produce confusing 404s rendered as the generic error state, and — more importantly for defense-in-depth — any later phase that renders the route param directly into the DOM (e.g., an error message echoing "activity 3475726256<script>... not found") reopens a DOM XSS path.
**Why it happens:** Treating the hash fragment as trusted internal state instead of user-controlled input (it is directly editable in the address bar).
**How to avoid:** Validate `id` matches `/^\d+$/` before using it in any fetch call or DOM insertion; never render the raw route param back into `innerHTML` — use `textContent` or template literals routed through a text node, not `innerHTML`, for anything containing user-influenced text (including the route param and the Strava-sourced `activity.name` field, which is free text the athlete could have set to anything).
**Warning signs:** grep the dashboard source for `innerHTML =` combined with any variable sourced from `location.hash`, `URLSearchParams`, or an activity JSON field.

# Phase 16: Dashboard Shell & Data Contract - Context

**Gathered:** 2026-08-10
**Status:** Ready for planning

<domain>
## Phase Boundary

A navigable, themed SPA shell deployed to GitHub Pages, plus the data contract the whole v2.0 dashboard runs on. Concretely: hash-based routing between the five views (list, calendar, detail, records, trends), a compact activity index manifest loaded up front, lazy per-activity detail fetching, and dark/light theming consistent with the existing widget system (DASH-01, DASH-02, DASH-03).

The view *content* is out of scope — Phase 17 fills the browser/detail views, Phase 18 fills records/trends. This phase ships the shell, the routing, the data pipeline to the published site, and one thin proving slice through the data contract.

</domain>

<decisions>
## Implementation Decisions

### Framework & architecture
- **D-01:** **Vanilla TypeScript, no framework.** Consistent with all 11 existing widgets and 3 standalone pages — zero new runtime dependencies. A small hand-rolled hash router + view modules.
- **D-02:** **Param routes from day one.** The router supports `#/view/:id` and query params (e.g. `#/activity/3475726256`, `#/list?year=2024`) so views are bookmarkable/shareable and Phase 17's detail view and filters slot in without router rework.
- **D-03:** **View registry.** Each view is a self-contained module registering `{route, title, nav entry, render/mount}`. Adding a future view (e.g. Phase 18 Trends) = drop in one module + one registry line. Mirrors how `build-widgets.mjs` enumerates widgets.
- **D-04:** **Plain light DOM** (no Shadow DOM for dashboard views). One global stylesheet driven by CSS custom properties. Shadow DOM stays with the embeddable widgets, which have different isolation needs.

### Navigation & shell layout
- **D-05:** **Top nav bar**, collapsing to a hamburger or scrollable row on mobile. Nav entries: list, calendar, records, trends (+ overview home). Detail is a drill-in route, not a nav entry.
- **D-06:** **Landing view (`#/`) is an overview home**: headline stats (total km, streaks, recent PRs) + recent activities. Source data already exists in `data/stats/*.json` (all-time-totals, streaks, best-efforts).
- **D-07:** **One proving slice through the data contract.** Unbuilt views render titled stubs ("coming in Phase 17/18"), but one real path must work end-to-end: landing/list shows real activities from the index manifest, and clicking one lazy-fetches that activity's detail JSON. This de-risks Phase 17's contract assumptions.
- **D-08:** **Dashboard lives at the site root** — it becomes `index.html` of the published Pages site. Existing pages (heatmap.html, pinmap.html, routes.html) keep their current URLs alongside it.

### Data contract (activity index + lazy detail)
- **D-09:** **Browse-complete index fields.** Each of the ~1,867 rows carries everything Phase 17 sorts/filters on plus display extras: id, date, name, distance, moving time, pace, avg/max HR, cadence, elevation gain, location, stream-availability badge (from `data/streams/manifest.json`) and low-confidence flag (from best-efforts data). Roughly 300–500KB raw, well under 100KB gzipped. Whatever isn't in the index can't be sorted/filtered without fetching everything — so the index is deliberately complete.
- **D-10:** **Detail views reuse the committed files directly**: `data/activities/<id>.json` (canonical summary) and `data/streams/<id>.json` (~70–80KB, schema locked in Phase 14). Zero new per-activity pipeline output — the Phase 14 stream schema IS the contract. Client decimates for charts (already the Phase 14 decision, Chart.js Decimation plugin).
- **D-11:** **CI copies data into the publish dir.** The deploy step copies the index manifest + `data/activities/` + `data/streams/` (+ `data/stats/` for the overview home) into `dist/` before publishing. Self-contained same-origin site, no CORS, no raw.githubusercontent coupling. Accepts ~150MB on the gh-pages branch.
- **D-12:** The index manifest is **generated by a compute step in CI and gitignored**, following the existing `data/stats/` conventions (`compute-stats.ts` pattern).

### Theming & visual identity
- **D-13:** **Same visual identity as the widgets.** Reuse the widget color tokens (Strava orange accent `#fc4c02` light / `#ff6b35` dark, white / `#1a1a2e` backgrounds, system font stack) as global CSS custom properties so dashboard and embedded widgets read as one product family.
- **D-14:** **Theme toggle + auto default.** Follows `prefers-color-scheme` by default; a header toggle (light/dark/auto) persists the choice in localStorage. Same semantics as the widget `ThemeManager`, applied at document level via `data-theme` on the root element.

### Claude's Discretion
- Exact index manifest schema (field names, nesting, single file vs year-chunked), `schemaVersion` and `generated_at` metadata conventions — follow `data/stats/` precedent.
- Router implementation details and the exact view-module interface shape.
- Build wiring: extend `vite.config.pages.ts` vs a sibling config for the root `index.html`; how the SPA entry coexists with widget bundles in `dist/widgets/`.
- CI copy mechanics (which paths, whether streams copy is complete or filtered to manifest-listed files).
- Overview home's exact stat cards and layout; responsive breakpoints and nav collapse mechanics.
- Which activity the proving slice uses and how deep the detail stub renders (raw numbers vs a first chart).

### Folded Todos
- **Garmin export adapter when export arrives** (`.planning/todos/`, area: api) — user folded into this phase. Add a garmin source branch in `src/exports/consolidate.ts` following the strava adapter pattern when the Garmin Connect bulk export lands in `export_data/garmin/`. **Probe the real export structure before coding** (repeated project lesson — the intervals.icu latlng stream took four attempts on guessed shapes). Join by start_date epoch or provenance external_ids; validate geometry via `IntervalsProvider.validateGeometry`; re-run idempotent `consolidate-exports` + regenerate stats if anything imports. Independent of the SPA shell — plannable as a standalone ride-along plan in this phase.
- **Manual exclusion of activities from best-effort/PR calculations** (`.planning/todos/`, area: analytics) — user folded into this phase. A committed exclusion list (e.g. `data/best-effort-exclusions.json`: activity IDs, optional per-distance, reason field); `computeBestEfforts` skips excluded activities for PR marking/ranking (still computing efforts, flagged `excluded`) and promotes the next-best genuine effort. Known bad devices: `3475726256` (400m/30km), `3475725513` (1k). Touches `src/analytics/compute-best-efforts.ts` / `best-effort-utils.ts`; the dashboard data contract (D-09 low-confidence badge, records data) should represent exclusions rather than pretend they don't exist.

## Existing Code Insights

### Reusable Assets
- `ThemeManager` (`src/widgets/shared/theme-manager.ts`): exact light/dark/auto semantics and color tokens to lift into the global stylesheet
- `data/stats/*.json` (all-time-totals, streaks, weekly-distance, best-efforts…): ready-made data for the overview home — no new computation needed

### Established Patterns
- All frontends are vanilla TS + Vite; standalone pages (Phase 13) build via `vite.config.pages.ts` with `emptyDir: false` to protect widget bundles
- Compute steps are CLI subcommands in `src/index.ts` run in CI (`compute-all-stats` chain), outputs gitignored under `data/stats/`
- Deploy is single-workflow (`daily-refresh.yml`): sync → compute → build → publish `dist/widgets` to gh-pages

### Integration Points
- New SPA entry (root `index.html`) joins the Vite pages build; publish dir gains data copies (D-11)
- New `compute-dashboard-index`-style step joins the CI compute chain (D-12)
- Index badges read `data/streams/manifest.json` and best-efforts output at generation time

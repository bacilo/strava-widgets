<interfaces>
Standing checkpoint conventions on this project, learned the hard way — all of them apply:
- **Verify the SERVED digest, not the build log.** `build-widgets` silently no-ops on any
  locally-edited `dist/` file (mtime skip), so a green build log can be describing a stale bundle.
  Record the served asset hash and confirm it matches the freshly built one.
- **Hard-reload after every fixture edit.** A stale `index.html`/`index.json` in a staged build has
  produced false evidence here before; serving from `127.0.0.1` alone is NOT enough.
- `data/stats/` and `data/dashboard/` are gitignored, so the documents the page reads are the LOCAL
  ones plan 33-12 regenerated on the merged tree. Confirm they are current before serving.
- Viewport clamps to 500..941 in the available capture path; gestures need a human.
- **Verdicts are transcribed verbatim.** A blanket approval is recorded as a blanket approval — it
  is never expanded into invented per-row observations (house rule T-31-33).
- **A failing row is recorded and left unpatched** (house rule since 16-09). Patching under
  checkpoint pressure is what produces a row rewritten until it certifies the defect (Phase 28 R3).
- **A row can be unsatisfiable as well as vacuous** (Phase 24 R19/R26). If a row's own setup
  empties the discriminator it exists to test, record BLOCKED with the reason — do not record PASS
  on incomplete evidence, and do not record FAIL for a defect in the row rather than the code.
</interfaces>

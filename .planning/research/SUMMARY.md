# Project Research Summary

**Project:** strava-widgets — v2.2 Pace Data Quality
**Domain:** Data-quality/statistical refinement of an existing static analytics pipeline (brownfield integration, not greenfield product research)
**Researched:** 2026-09-08
**Confidence:** HIGH overall, with one explicitly-owned exception (smoothing window choice — see below)

## Executive Summary

This milestone is not a build-something-new problem, it is a fix-the-derivative problem inside a codebase that already has the right shape. `src/analytics/best-effort-utils.ts` already has the plausibility-guard pattern (`isPlausible`, `WORLD_RECORD_SPEED_MPS`), `detail-charts-logic.ts`'s `derivePaceSeries` already has the right primitive (a Δt-weighted windowed average over an irregular grid via `interpValueAtTime`), and the CI pipeline (`COMPUTE_ALL_STATS_STEPS`) already has the precompute-and-shard pattern (`best-efforts.json` + per-activity shards). All four researchers converge on the same verdict: **hand-roll every algorithm needed (quantile, Hampel/rolling-median-MAD, gap classification, composite quality signal) as 15-40 line pure functions in `src/analytics/`, no new dependency, and unify the two divergent pace derivations onto that module rather than adding a third.** The root cause the project itself already diagnosed — `derive-stream.ts`'s `MAX_SAMPLES = 3000` decimating by index selection and aliasing 53% of the archive — is confirmed by direct measurement, not assumption, and it is a self-inflicted artifact, not primarily a device-noise problem, though it manifests worst on the Suunto-era cohort (all 154 worst stair-step activities are 2020-2021, the Suunto years) because that device's ~2s distance-update cadence interacts especially badly with index-selection decimation.

The recommended approach, synthesized across all four files: (1) extract one shared, gap-aware pace-derivation module in `src/analytics/pace-derivation.ts` that both the chart and the histogram become thin wrappers over — this is the foundational fix everything else depends on; (2) precompute per-activity quality signals as compact scalar fields on the dashboard index (for list-level badges/filtering) plus a lazily-fetched per-activity shard (for detail-view depth), following the `best-efforts.json`/`best-efforts/{id}.json` sharding precedent exactly; (3) restructure `compute-best-efforts.ts` into a strict three-pass shape (accumulate → derive a personal ceiling from the already-filtered accumulation → flag-and-demote against it) to avoid the circularity of computing a rejection threshold from the very population containing the outliers it should reject; (4) extend the existing `/__curate/*` local-only write path for a review queue rather than inventing a second write surface. Every one of these four steps has direct, load-bearing precedent already living in this repository.

The key risk this research surfaces is not technical difficulty, it is scope discipline: quality-signal work is exactly the kind of feature that accretes into noise (Pitfall 11 — too many flags stop meaning anything) or into an uninterpretable composite score (Pitfall 12), and the plausibility ceiling is exactly the kind of feature that quietly becomes an auto-exclusion mechanism if flag-and-review isn't kept structurally separate from demote-and-hide (Pitfall 13). All three risks have concrete, already-established prevention patterns in this codebase (severity tiers with an archive-wide dry-run rate cap, disclosed individual signals over a blended score, and the CUR-01 flag-never-auto-correct precedent) — the research confirms the milestone's own non-goals are the correct guardrails, not obstacles to relax.

## Key Findings

### Recommended Stack

**No new dependency for any of the four algorithm categories this milestone needs** (gap-aware smoothing, outlier/spike detection, personal-percentile plausibility ceiling, quality-score composition). Every technique is a small, well-documented, textbook function over an array of at most ~3,000 floats, run once per activity in CI or once per chart render in the browser — squarely inside the size/complexity envelope this codebase already hand-rolls repeatedly. Two libraries (`simple-statistics`, `d3-array`) were seriously evaluated for the quantile function specifically and rejected: both would still need wrapping/testing to this project's conventions, and a single ~15-line quantile call doesn't clear the bar for a new runtime dependency. No npm package for Hampel filtering exists at all (confirmed via live registry lookup) — reinforcing hand-roll as the only real option, not just the preferred one. Kalman filtering and Savitzky-Golay were both considered and explicitly rejected: Kalman solves streaming state estimation this batch/committed-data milestone doesn't have, and S-G assumes a uniform sampling grid this project's streams explicitly, deliberately do not have.

**Core technologies:**
- Plain TypeScript, zero runtime dependency — every technique (Δt-weighted windowed averaging, rolling-median/MAD outlier flagging, R-7 linear-interpolation quantile, weighted-signal composition) is textbook and small enough to hand-roll, matching the existing `best-effort-utils.ts`/`detail-charts-logic.ts` house style
- `vitest` (already installed) — sufficient for all needed property-style tests, no new tooling

### Expected Features

**Must have (table stakes, per FEATURES.md):**
- One consistent pace-derivation method used everywhere (no platform researched shows two silently-different numbers for the same activity, which is exactly what this project ships today)
- Gaps stop manufacturing pace — universal pattern across every platform's moving-time logic
- Visible flag when data looks physically implausible, never a silent correction — the only pattern actually found to be user-facing anywhere in the industry
- Device `moving_time` treated as authoritative when the device made an explicit choice (mirrors Strava's own documented two-tier moving-time policy: trust an explicit device signal, apply independent judgment only to undecided spans)

**Should have (differentiators — no direct industry precedent found):**
- Personal plausibility ceiling for PRs — no commercial platform implements this; the closest analogue (Strava segment-leaderboard flagging) is segment-*population*-relative, not athlete-*personal*-relative. Academic anomaly-detection literature (MAD / Bayesian-hierarchical framing) is the only conceptual precedent, not a product to copy.
- Per-activity quality badge set (device era, stair-step ratio, impossible-sample count, gap profile, elapsed-vs-moving divergence) — no platform surfaces a general quality/confidence badge; this is a genuine market gap, high design risk, no reference implementation
- Elevation as a quality signal via impossible-altitude flagging — modeled on Runalyze's raw/corrected-altitude toggle, the single most concrete external precedent found in the entire research pass, but scoped to flagging only (no DEM-based correction, no infrastructure for one)
- Review queue in local curation mode — no external precedent (closest analogue is Strava's own internal, non-user-facing moderation queue), but directly consistent with "flagged, never deleted" and extends Phase 24's existing exclusion mechanism

**Confirmed out of scope (validated, not just asserted):**
- Grade-adjusted pace / GAP — explicitly deferred; raw grade (computable from committed altitude) should only suppress false-positive speed-implausibility flags on genuine steep downhills, never compute full GAP
- Geometric GPS-spike rejection (Kalman-gated position filtering, map-matching) — structurally impossible here regardless of preference, since committed streams carry no per-sample lat/lng, and (per this scoping's own measurement) even *if* position were committed, its coverage is asymmetric by device family (100% Garmin fēnix 6 Pro vs. 51.3% Suunto 9) — precisely the era that would need it most. Derivative-only detection is not a compromise choice, it is the only uniform option across this archive.

### Architecture Approach

This is a subsequent-milestone integration study, not a greenfield design — every recommendation cites a real file/function this repo already has. The shared pace-derivation logic belongs in `src/analytics/` (never `src/dashboard/` — the dependency arrow in this codebase only ever runs `analytics/ → dashboard/`, never the reverse), following the exact precedent of `best-effort-utils.ts` already being imported by three dashboard view modules and one CI compute step. Precompute-vs-derive-on-read splits cleanly along the existing `DashboardIndexRow`/per-activity-shard boundary: compact scalar quality signals belong in the index (drives list badges/filtering, matches the existing `lowConfidence`/`excludedFromRecords`/`streams` field shapes), detailed gap/sample-level data belongs in a new `data/stats/pace-quality/{id}.json` shard fetched lazily exactly like `best-efforts/{id}.json` already is. Nothing about quality signals should be computed in the browser — the only thing that legitimately stays browser-computed is the full-resolution pace *series* for chart rendering (already true today), because it's view-specific (window, zoom, x-axis mode) in a way fixed scalar summaries are not.

**Major components:**
1. `src/analytics/pace-derivation.ts` (NEW) — gap classification + shared gap-aware `derivePaceSeries`/`computePaceDistribution`; both `detail-charts-logic.ts` and `detail-zones.ts` become thin wrappers over it. `detail-splits.ts` is a third, already-correct, structurally different computation and is explicitly *not* one of the two divergent implementations in scope — leave it alone (flagged as an open question below, not a requirement).
2. `data/stats/pace-quality/{id}.json` + `pace-quality-client.ts` (NEW) — per-activity quality shard and lazy-fetch client, mirroring the `best-efforts` sharding pattern exactly; compact `quality: {...}` summary fields added additively to `DashboardIndexRow` (schema version unchanged, same precedent as the existing `gearName` addition).
3. `compute-best-efforts.ts` / `best-effort-utils.ts` (MODIFIED) — restructured into a strict three-pass shape: Pass 1 (existing, unchanged) accumulates `byDistance` per activity through `isPlausible` + `isExcluded`; Pass 2 (new) derives one personal-ceiling statistic per distance from Pass 1's already-filtered, fully-materialized array (no re-read, no iteration to convergence — deterministic by construction); Pass 3 (new) re-filters against the ceiling, flagging (never deleting) entries that exceed it before `markPRs`/`rankTopN` run.
4. `scripts/curate-server.mjs` + `scripts/curate-overlay/` (MODIFIED) — new `/__curate/pr-overrides/:id`-style routes reusing the exact `isTrustedOrigin`/`writeAtomic`/`readJsonBody`/`isValidCurateActivityId` machinery the exclusion tickbox already uses; both structural publish guards (`curation-guard.mjs`, `verify-dashboard-publish.mjs`) cover new routes automatically since they scan by prefix/content, not an enumerated route list.

**Suggested build order** (from ARCHITECTURE.md, matching FEATURES.md's independently-derived MVP sequencing): shared derivation → per-activity quality signals → PR-ceiling three-pass restructure → curation review queue → (elevation signal can run in parallel with quality signals since it needs only committed altitude). `export_data/`-driven re-derivation work is explicitly out of critical path this milestone — no new local-only compute step should be introduced (see non-goals below).

### Critical Pitfalls

1. **Two divergent pace formulas persisting as "one plus a fallback"** — the milestone's entire premise is eliminating this; any code path that still computes `dt/dd` outside the new shared module (including future ones, e.g. inside quality-signal code) recreates the exact bug being fixed. Grep-based audit ("Single pace derivation" checklist item) should be a standing verification step, not a one-time check.
2. **Smoothing bleeds across a pause/gap boundary** — a windowed average that reaches across a gap (1,233 activities have a >10s recording gap; one activity has a single 35-hour gap with +0m) manufactures a distorted pace value spanning a period with no real samples. The fix is a hard wall: clip the window at the gap boundary rather than bridging it. This is the literal headline requirement ("one gap-aware pace derivation"), not optional scope.
3. **Circular percentile ceiling** — deriving a rejection threshold from a raw percentile of the same population containing the outliers it's meant to catch is self-defeating (structurally the same failure as the currently-shipped `WORLD_RECORD_SPEED_MPS` guard admitting a 44.0s 400m). The resolution this research converges on: compute the ceiling over the population *already* coarse-filtered by the existing absolute plausibility guard and exclusion list (Pass 1's output), never over the raw unfiltered archive, and pin the known-bad 44.0s/400m case as a permanent regression fixture.
4. **Silent-drop coverage invariant violated** — this is the bug that already shipped (72% coverage presented as if complete). Any future filter (smoothing edge effects, gap exclusion, outlier rejection) has the same failure mode unless covered-time + excluded-time (by named category) is asserted to sum to exactly elapsed-time, watched failing against the real defect before being trusted.
5. **Flags become noise / auto-exclusion removes a legitimate PR** — two related risks (Pitfalls 11 and 13) that both stem from skipping the "design one coherent, prioritized signal + human-reviewed dry run" step. The milestone's own non-goals (flag-not-delete, demotion-not-recalculation) are the correct guardrail; an archive-wide dry-run flag-rate/PR-diff report reviewed by a human before ship is a required deliverable, not optional polish.

## Implications for Roadmap

Based on combined research (all four files independently converge on the same ordering), suggested phase structure:

### Phase 1: Shared gap-aware pace derivation
**Rationale:** Foundational — every other phase either consumes this module's output or reuses its gap-classification primitive. Building quality signals or a PR ceiling before this exists means scoring them against a still-noisy input.
**Delivers:** `src/analytics/pace-derivation.ts` (gap classification + unified `derivePaceSeries`/`computePaceDistribution`); `detail-charts-logic.ts` and `detail-zones.ts` become thin wrappers.
**Addresses:** Table-stakes feature "one consistent pace-derivation method"; FR-01 as named in PROJECT.md.
**Avoids:** Pitfalls 1-6 (differentiate-then-smooth vs smooth-then-differentiate, fixed-width-blind-to-sample-rate, smoothing across pause boundaries, over-smoothing intervals, cumulative-vs-differentiated inequivalence, silent-drop coverage invariant).
**Open question to settle here:** the exact gap-threshold value(s) that gate window clipping — this research surfaces both a >10s "recording gap" threshold and a ≥30s "pause gap" threshold from the project's own prior investigation, but does not resolve whether both gate smoothing-window clipping identically or whether they play different roles (e.g. recording-gap clips the window, pause-gap additionally excludes the span from coverage accounting). Needs a REQUIREMENTS-level decision, tested against a synthetic fixture built specifically to make each threshold's effect observable independently.

### Phase 2: Honest coverage + per-activity quality signals
**Rationale:** Depends on Phase 1's gap classifier for the gap-profile signal; otherwise independent of PR-ceiling work. Ships the visible-badge/filtering goal and gives the later review queue something to explain *why* an activity is flagged.
**Delivers:** Compact `quality: {...}` fields on `DashboardIndexRow` (additive, schema version unchanged) plus a per-activity `data/stats/pace-quality/{id}.json` shard and `pace-quality-client.ts`, mirroring the `best-efforts` sharding pattern.
**Addresses:** "Honest coverage" and "per-activity quality signals and badges" target features from PROJECT.md.
**Avoids:** Pitfall 8 (absolute thresholds that don't survive 15 years / 4 watches — validate against a stratified device/era fixture set, not just recent activities), Pitfall 9 (inferring device capability from file format and treating a missing channel as zero — this scoping's own measurement confirms field presence differs *by device family*, not by format, so any "device era" signal must treat the 716 no-device-name activities as an explicit category, never a silent default), Pitfall 11 (flag noise — design severity tiers, run an archive-wide dry-run flag-rate report, treat a top-tier rate much above low-single-digit as a signal thresholds need tightening), Pitfall 12 (uninterpretable composite scores — show individual signals in their own units, not one opaque number).
**Open question to settle here:** severity-tier thresholds and the target top-tier flag-rate ceiling — no default exists in research; must be calibrated against this archive's own dry-run numbers (995/1,864 decimated, 662/1,864 with an impossible sample, 1,233/1,864 with a >10s gap — a naive union of "any signal present" would flag a majority of the archive, which defeats the point).

### Phase 3: PR plausibility ceiling (three-pass restructure)
**Rationale:** Functionally independent of Phases 1-2's signal work, but should follow them so a later review-queue UI can show quality context alongside a ceiling rejection. This is the single most consequential threshold in the milestone (gates PR validity) and carries the highest circularity/ordering risk — needs its own fixture-based regression coverage before anything downstream depends on its output shape.
**Delivers:** Restructured `compute-best-efforts.ts` (accumulate → derive ceiling from already-filtered accumulation → flag-and-demote, never delete); new `personalPlausibilityCeiling(entries)` beside `isPlausible`/`markPRs`/`rankTopN` in `best-effort-utils.ts`; new `flaggedImplausible` field on `BestEffort` and a distinct `effortsFlaggedImplausible` totals counter (parallel to, not overloading, the existing `effortsExcluded` counter).
**Uses:** STACK's R-7 linear-interpolation quantile sketch (same method as numpy/Excel/D3), applied to the coarse-filtered population per Pitfall 7's anti-circularity fix — this reconciles STACK's quantile recommendation with PITFALLS' circularity warning: the quantile must run over Pass 1's output (already passed through `isPlausible`'s absolute world-record guard and the exclusion list), never over the raw archive.
**Implements:** ARCHITECTURE's three-pass structure (Q3).
**Avoids:** Pitfall 7 (circular percentile — pin the 44.0s/400m case as a permanent regression fixture), Pitfall 10 (silent historical PR movement — a full-archive before/after diff must be a required phase deliverable, reviewed by a human, not discovered by a user), Pitfall 13 (auto-exclusion removing a legitimate PR — ceiling ships demote-and-flag-only; exclusion requires a subsequent explicit human action via Phase 4).
**Open question to settle here:** ceiling input population precisely — this research confirms the population must exclude raw-outlier contamination (Pitfall 7) and should be Pass 1's output, but does not resolve whether Pass 1's population should be "all non-excluded efforts" (current default, includes anything that merely passed the loose world-record guard) or a tighter intermediate set. This is a REQUIREMENTS-level decision with a direct effect on how aggressive the ceiling is out of the gate.

### Phase 4: Curation review queue
**Rationale:** Strictly depends on Phase 3 existing (nothing to review without ceiling-rejected efforts) and benefits from Phase 2's quality context. Requires a schema decision before implementation starts.
**Delivers:** New `/__curate/*` routes (e.g. `PUT /__curate/pr-overrides/:id`) reusing the exclusion tickbox's exact write-path machinery (`isTrustedOrigin`, `writeAtomic`, `readJsonBody`, `isValidCurateActivityId`); a review-queue panel in `curate-overlay/`; the override file added to the nightly workflow's push-paths filter alongside `best-effort-exclusions.json`.
**Uses:** The existing Phase 24 curation-mode publish-safety pattern (two independent guards: build-time content scan + HTTP-layer assertion), extended with test coverage for the new route(s), not weakened or reinvented.
**Avoids:** Pitfall 13 (jointly with Phase 3 — the ceiling hands off to the queue rather than acting unilaterally) and the Security Mistakes table's named risk (a review-queue write path reachable from the published bundle repeating the exact gap Phase 24 closed).
**Open question to settle here (the most consequential unresolved schema decision across all four research files):** whether the accept/override write extends `best-effort-exclusions.json`'s existing schema (e.g. an `overrideCeiling: true` field) or introduces a new sibling file (e.g. `data/pr-overrides.json`). ARCHITECTURE.md explicitly flags this as unresolved and needing a REQUIREMENTS/ROADMAP decision before Phase 4 implementation starts — whichever is chosen needs a corresponding loader following `best-effort-exclusions.ts`'s exact tolerant-parse contract, and must be added to the nightly workflow's push-paths filter or it silently never propagates past the developer's machine.

### Phase 5: Elevation as a quality signal
**Rationale:** Needs only committed altitude data, independent of the PR-ceiling work — can run in parallel with Phase 2/3 if sequencing allows, though listed last here to match PROJECT.md's target-feature ordering.
**Delivers:** Altitude-rate-of-change implausibility flagging (the "impossible-altitude case"), surfaced the same way speed implausibility is — flag, never correct.
**Addresses:** The one differentiator with a concrete external precedent (Runalyze's raw/corrected-altitude toggle pattern), scoped to flagging only.
**Avoids:** The Integration Gotchas table's named trap — elevation has its own device/GPS failure modes (barometric drift, missing elevation channel on some sources; this scoping's own measurement found `derive-stream.ts`'s `ALT_MIN = -500` threshold is loose enough to admit a −282m reading on a sea-level Lisbon run) — treat as its own signal with its own fixture-derived thresholds, not a copy-paste of the speed ceiling with different units.

### Phase Ordering Rationale

- **Dependency-driven, not feature-list-driven:** Phase 1 unblocks everything (the gap classifier is reused by Phases 2 and, transitively, by any coverage-accounting Phase 3/4 needs); Phase 3 depends on nothing from Phase 2 functionally but is sequenced after it so the review queue (Phase 4) has quality context to show; Phase 4 hard-depends on Phase 3's rejected-efforts output existing.
- **Cross-cutting discipline, not a separate phase:** stratified device/era test fixtures (fēnix 6 Pro, Suunto 9, GPX, intervals.icu-only, no-device-name) and the "watched failing before trusted" assertion convention should be built once (ideally as part of Phase 1's fixture library) and reused by every later phase, rather than deferred to a standalone "cross-era consistency" phase at the end — PITFALLS.md explicitly frames this as "a standing test-fixture requirement across every phase that introduces a threshold," not a phase of its own.
- **No local-only compute step, no stream re-derivation, this milestone:** confirmed independently by ARCHITECTURE (Q5) and by this scoping's own measurement (re-derivation moves best efforts by only −1.6s to +5.0s, makes bogus efforts *faster*, and costs ~200MB of permanent git weight) — every named quality signal is computable from the committed stream alone. If a future milestone revisits `export_data/`-driven re-derivation, it should follow `backfill-streams.ts`'s existing standalone-script precedent, kept out of `COMPUTE_ALL_STATS_STEPS`.

### Research Flags

Needs deeper research during planning:
- **Phase 3 (PR plausibility ceiling):** the exact statistic (percentile value, margin, or a robust trimmed/MAD-based estimate) is not settled by this research — STACK sketches a generic R-7 quantile function, PITFALLS insists on anti-circularity via pre-filtering, but no specific p-value or margin is recommended. Needs calibration against the archive during planning, with the 44.0s/400m case as a hard regression gate.
- **Phase 4 (review queue):** the override schema shape (extend exclusions vs. sibling file) is an explicit open decision, not a research gap per se, but should be resolved in REQUIREMENTS before planning begins so Phase 3's `BestEffort` field additions and Phase 4's write path agree on shape from the start.
- **Phase 2 (quality signals):** severity-tier thresholds and the target flag-rate ceiling need an archive-wide dry-run computation during planning/early implementation, not researched from outside sources (no product researched ships this feature at all, so there is no external number to borrow).

Standard patterns, low research risk:
- **Phase 1 (shared derivation):** the Δt-weighted windowed-average primitive and gap-boundary-clipping logic are both direct extensions of code that already exists and is already tested in this repo.
- **Phase 4 (review-queue write path):** mechanically follows the Phase 24 exclusion-tickbox precedent almost line-for-line (same guards, same atomic-write discipline).
- **Phase 5 (elevation signal):** straightforward derivative-based flagging once Phase 1's fixture-library pattern exists; the correction half of the Runalyze pattern (DEM overlay) is explicitly out of scope, removing the only genuinely hard part.

### Reconciliations (where direct measurement supersedes researcher assumption)

- **PITFALLS.md flagged device-specific claims (FIT sensor-fused speed channel, GPX raw-diffing noise) as LOW-MEDIUM, "verify against the actual archive."** This scoping's direct measurement did exactly that and found something sharper than what was assumed: field *presence* differs by **device family**, not by file *format* — a Garmin fēnix 6 Pro FIT file has 0.0% `speed`/`altitude` presence (uses `enhancedSpeed`/`enhancedAltitude` instead) despite being the same FIT format as a Suunto 9 file, which has 99.8% `speed` presence but only 51.3% `positionLat` presence. A naive `record.speed` read returns nothing for the entire 907-activity fēnix cohort. Any future quality signal that branches on file format as a proxy for data richness will silently misbehave — device family (not format) is the correct branch key, and even that must treat "no device name" (716 activities, 38% of the archive) as its own explicit category per Pitfall 9, never a default.
- **FEATURES.md's "no platform does geometric spike rejection without position" framing is confirmed, and sharpened into a stronger argument.** The scoping measurement shows position coverage itself is asymmetric by era (100% Garmin vs. 51.3% Suunto) — so even a hypothetical future milestone that added position to committed streams would not get uniform geometric-check coverage; the Suunto era, which most needs a spike-rejection assist (device-noise spikes like the 17 m/s Suunto case), is precisely the era with the weakest position signal. This is not a caveat on the "derivative-only" approach, it is independent confirmation that derivative-only is the right call regardless of the position-privacy non-goal.
- **PITFALLS.md's Pitfall 2 (decimation aliasing) is confirmed as the dominant mechanism (995/1,864 activities, 151/154 worst stair-step cases) rather than a contributing factor among several.** The scoping measurement additionally narrows *where* it manifests worst: all 154 severe stair-step activities date to 2020-2021 (the Suunto 9 era specifically), because that device's ~2s distance-update cadence aliases especially badly under index-selection decimation. Device era and decimation severity are correlated but decimation — not the device itself — is the root mechanism; any "device era" quality signal must not be mistaken for a "decimation severity" signal, they need separate sub-signals per Pitfall 12's disclosed-individual-signals guidance.
- **STACK.md's quantile-function recommendation and PITFALLS.md's circularity warning (Pitfall 7) are not in tension** once the population feeding the quantile is specified correctly (see Phase 3 above) — this required reconciling two documents that each addressed only half the problem (STACK: how to compute a quantile; PITFALLS: what population is safe to compute it over).
- **Validation, not correction:** FEATURES.md's Q3 finding ("nobody silently auto-corrects and hides it — every genuinely user-facing correction found across six platforms is explicit, user-triggered, and reversible") is independently confirmed by this project's own established Phase 24 precedent (flag-never-auto-correct, CUR-01) and is not challenged by anything in the additional archive measurement. This is worth recording as validation: the milestone's flag-and-review design is not an internal-only convention, it matches what the credible, user-facing parts of the industry already do.

### Gaps to Address

Collected here in one place, as the most directly actionable output of this synthesis:

1. **Gap threshold for window clipping (Phase 1).** Whether the >10s "recording gap" threshold and the ≥30s "pause gap" threshold play identical or distinct roles in smoothing-window clipping vs. coverage accounting is not resolved by research — needs a REQUIREMENTS decision, tested with a fixture that makes each threshold's individual effect observable.
2. **Ceiling input population (Phase 3).** Whether the personal-plausibility-ceiling quantile should be computed over "all non-excluded efforts" (current default understanding) or a tighter, explicitly-defined intermediate set is unresolved — has a direct effect on ceiling tightness at ship time.
3. **Override schema shape (Phase 4).** Extend `best-effort-exclusions.json` with a new field vs. introduce a sibling `data/pr-overrides.json` — explicitly flagged as unresolved by ARCHITECTURE.md and needing a REQUIREMENTS/ROADMAP decision before Phase 4 implementation.
4. **Whether `detail-splits.ts` gains gap-flagging (Phase 1, open question).** `detail-splits.ts`'s per-km computation is already correct and is not one of the two divergent implementations named in scope — ARCHITECTURE.md explicitly leaves whether it should also surface gap-flagging as an open question, not a requirement, deferred to planning.
5. **Severity-tier thresholds and top-tier flag-rate cap (Phase 2).** No external number exists to borrow (no platform researched ships this feature); must be calibrated against this archive's own dry-run numbers during planning/early implementation, with a low-single-digit-percentage top-tier rate as the working target to justify or revise.
